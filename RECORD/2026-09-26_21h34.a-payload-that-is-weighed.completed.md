# 2026-09-26 21h34 · A payload that is weighed

Takes register **item 7** — *"`wasm-opt`, brotli, and a real payload number"* — and the brotli
zero the previous file found.

## Where this repo actually was

- `make web` printed three lines about one file: `ls` for the raw size, `gzip -9 | wc -c`, and a
  brotli line that said **0.00 MiB** on any machine without `brotli`, because its `|| true`
  guarded the pipe and not the count.
- `make web-opt` existed, depended on `make web`, ran `wasm-opt -O3` into a *second* file nothing
  served, and printed "wasm-opt not installed on host" whenever it failed — which, it turns out,
  was every time anybody had the distribution's binaryen: Ubuntu Noble's is **108**, and it cannot
  parse this module at all (`invalid code after misc prefix: 17` — `table.fill`, from the
  reference-types feature rustc enables by default for wasm32). Nothing deployed was ever
  optimised, and the one target that claimed to try failed silently.
- No number existed for what a visitor downloads. The register's figures were the module alone,
  and "upper bounds and lazy ones".
- `rustc` was the 1.98.1 stable the previous file updated to; nightly 1.100.0 was installed for
  the threaded variant.

## Walkthrough · as built

**`wasm-opt`, pinned.** `make binaryen` fetches binaryen `version_124`'s Linux release, checks it
against a SHA-256 in the Makefile, and unpacks it into `tools/.binaryen/` (gitignored). It is a
target of its own, not a step of the build, for the reason `make occt-headers` is: a build that
reaches the network by itself is not reproducible. `make web` and `make web-threaded` now run
`wasm-opt -O3` **in place** — the unoptimised module is not served, so it is not kept — and fail
if there is no `wasm-opt`, naming both ways out: `make binaryen`, or `WASM_OPT=none`, which builds
unoptimised and prints that it did. The threaded module is optimised *before*
`tools/wasm_threads.py` reads it, so the shared memory is checked on the file that ships.

`-O3`, not `-Oz`, measured on the same input: `-Oz` is 114 KiB smaller raw, 7 KiB smaller gzipped
and 1 KiB *larger* under brotli, and trades speed for it in a program whose browser workload is a
boolean and a tessellation.

**The artifact is asked, not the Makefile.** `tools/wasm_payload.py` replaces the three lines. It
prints raw, `gzip -9` and brotli quality 11 — and when there is no `brotli` it says *not measured*,
never zero. It lists the largest sections, and it **fails if the module still has a `name`
section**, which is what a module that skipped `wasm-opt` looks like: wasm-bindgen keeps function
names and `wasm-opt` drops them. On this build that section was **1.02 MiB of 4.58**. The shape of
`tools/wasm_threads.py`, for the same reason: the recipe saying it ran a tool is not evidence about
the file. `make web-opt` is gone.

**The real payload number is measured in the browser.** `make web-test`'s first run now records
every response the page's origin served during load — through Playwright's `requestfinished`,
with the bytes received and the bytes transferred — and a closing section weighs each file raw,
gzipped and brotli'd in Node, which has both compressors built in. It is a list of what a load
*fetched*, not of what somebody believes it fetches. It asserts no size. It asserts that every
request was a 200, that every module served is byte-for-byte the size of the one on disk, and one
more thing, below.

**What it found first: the module was downloaded twice.** The table's first run showed
`/dist/w3d_web_bg.wasm` requested **twice**, 4 495 244 bytes transferred each time: the page and
its tessellation worker each called wasm-bindgen's `init()`, each fetched, and the two requests
start together so neither can be served from a cache the other has not filled. Every first visit
since the worker became the boot path on 2026-09-15 has paid for the module twice, and compiled it
twice. Nothing measured the network, so nothing saw it.

The fix is in `web/loader.js`: `compileSingle()` fetches and compiles the single-threaded module
once, with `WebAssembly.compileStreaming` (and an `arrayBuffer` fallback for a host that serves
`.wasm` with the wrong type), before the worker is created. The `WebAssembly.Module` is posted to
the worker with the document, and both sides hand it to `init({ module_or_path })`. If it cannot be
compiled, each side falls back to fetching its own — the old behaviour, slower and still correct.
The threaded variant loads its own module, because it is a different one with a shared memory.
`make web-test` now asserts **each module is requested once**, and with `web/worker.js` put back to
a bare `init()` that check fails, `×2`.

## Bugs found by building, not by reading

- **Every first visit downloaded and compiled the module twice.** Cause above. Found by the first
  measurement of the network anybody made, which is the argument for the table.
- **`make web-opt` had never worked on the machines it was likely to run on.** Ubuntu's binaryen
  is too old for rustc's output, and the target turned the parse failure into "not installed".
- **`make web` reported a brotli size of zero without `brotli`.** From the previous file; fixed by
  the tool that replaced the line.

## Verified, and not

**Verified** — rustc 1.98.1 stable, nightly 1.100.0 for the threaded build, binaryen 124,
headless Chromium on the software path, `web/serve.py` (no compression):

| | before | after |
| --- | --- | --- |
| module, raw | 4.58 MiB | **3.36 MiB** |
| module, gzip -9 | 1.39 MiB | **1.26 MiB** |
| module, brotli 11 | 0.97 MiB | **0.91 MiB** |
| a single-threaded first visit, bytes transferred | 8.88 MiB (module ×2) | **3.67 MiB** |
| the same visit, every file gzipped | — | **1.31 MiB** (1 344.6 KiB) |
| a threaded first visit, every file gzipped | — | **2.62 MiB** (2 682.1 KiB) |

- `make web-test` passes every check with **both variants built and optimised** — the threaded
  page chose `threaded`, started a pool larger than one, and `wasm_threads.py` read a shared memory
  from the optimised module — and again with only the single variant. The picture, the pick, the
  worker's stall measurement and the document path all pass on the optimised module.
- `tools/wasm_payload.py` refuses the unoptimised module and accepts the optimised one.
- `float_roundtrip`, owed by the previous file: **+51 KiB raw, +17 KiB gzipped** after `wasm-opt`
  (3 466 238 → 3 518 049 bytes).

**Not verified**

- **What GitHub Pages actually sends.** This container's network policy refuses `github.io`, so
  whether Pages serves the module gzipped, brotli'd or raw is not known from here. The table gives
  all three; the one a visitor pays is the host's choice. Worth one `curl -H 'Accept-Encoding: br,
  gzip' -I` from anywhere that can reach it.
- **Speed.** `-O3` is chosen for speed and no speed was compared. The suite prints boot timings,
  but one run each on a software rasteriser is not a measurement, and none was taken as one.
- **A panic in the browser has no function names now.** The `name` section was what the console
  used for a stack trace. A symbolised build is `WASM_OPT=none`, or `wasm-opt -g`, and neither is
  wired to anything.
- **The x86-64 Linux binaryen only.** `make binaryen` fetches one platform's archive; on macOS it
  fails at the hash, loudly, and `WASM_OPT=/path/to/wasm-opt` is the way round.

## Loose ends, deliberately left

- **A threaded visit downloads both modules** — 1.28 MiB gzipped for the threaded one and 1.27 MiB
  for the single one its tessellation worker loads — because `web/worker.js` imports the
  single-threaded build unconditionally. Sending the worker the threaded module needs a shared
  memory of its own and a pool, or a worker that does not exist on that path; either is a design
  change to the boot path, not a payload fix.
- **The threaded glue is requested five times**, 133 KiB raw each over `serve.py`: once by the page
  and once per rayon worker. Whether a real host's cache headers make the four repeats free is the
  same unknown as Pages' compression.
- **The JS glue is requested twice** on a single-threaded visit (page and worker), 22 KiB gzipped.
  Small, and a module import cannot be handed across the way a compiled module can.
