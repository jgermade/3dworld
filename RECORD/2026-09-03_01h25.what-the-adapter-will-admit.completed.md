# 2026-09-03 01h25 · What the adapter will admit

Takes no register item. It started as a question — *is hardware acceleration being used when it is
detected?* — and the answer turned out to be two answers, one of which is a defect.

## Where this repo actually was

`Gpu::open` asked for `PowerPreference::HighPerformance` with `force_fallback_adapter: false`,
opened a device on whatever answered, and read five things off it into `Capabilities`: the
backend, the adapter's name, `compute`, `vertex_storage_buffers`, and two limits. `web/`'s loader
then did the one thing none of that can do — drew a frame and looked at whether the canvas was
more than one colour — and fell back to WebGL2 on the evidence.

So the honest state of "acceleration" was:

- **Rendering did run on whatever adapter answered.** There is no path in this repository that
  rasterises on the CPU by choice; everything goes through wgpu.
- **Nothing branched on a single detected capability.** `compute` and `vertex_storage_buffers` are
  read from the adapter and then only *printed* — `Display`, `degradation()`, `shell.rs`, the
  browser's `report()`, the status line on the page. Grep finds no other reader. There are no
  compute pipelines in the tree at all: `render/src/shade.wgsl` has `@vertex` and `@fragment`
  entry points and nothing else, and the BVH, culling and silhouette work those flags were
  detected *for* exists in neither a GPU nor a CPU form. `degradation()` therefore describes a
  fallback that has nothing to fall back from, which is a fair thing to say early and a
  misleading thing to leave unsaid.
- **Nothing distinguished a GPU from a CPU rasteriser.** `AdapterInfo::device_type` was never
  read anywhere in the workspace. lavapipe in CI, SwiftShader in the browser job and a discrete
  card were the same report, separated only by a name string that `Capabilities`' own doc comment
  says must never be branched on.

The last of those is what this file is about, and looking at it turned up the defect below.

## Walkthrough · as built

**`Acceleration`, a three-valued answer.** `Hardware`, `Software`, `Unknown`, mapped from wgpu's
five `DeviceType` variants in one place — `Capabilities::acceleration()` — with `VirtualGpu` and
`Other` both landing on `Unknown`. Three values rather than a boolean because the honest answer on
the web is usually "nobody would say": WebGPU does not tell a page what is behind its adapter, so
wgpu reports `Other`, and flattening that into "not hardware" would be a claim nothing supports.
It is `Software` only where a driver said so — a Vulkan ICD reporting `PHYSICAL_DEVICE_TYPE_CPU`,
or wgpu's GL backend recognising llvmpipe or SwiftShader by name.

**`software_rendering()`, the note.** Shaped like the existing `degradation()`: `Option<String>`,
`Some` for exactly the `Software` case. `Unknown` produces no warning, deliberately — a warning
shown on every browser that declines to answer is a warning nobody reads, and the loader's frame
check is the thing that catches the case where the adapter lied.

It is shown where the other one is: the desktop shell prints it under the capabilities line, the
browser exposes `acceleration` and `softwareRendering` on `report()`, and `index.html` puts the
acceleration on the adapter line and the note in the warning block.

**The capabilities are read after `request_device`, not before.** That is the bug below.

**Two assertions in `render/tests/headless.rs`**, both invariants rather than claims about the
machine they run on: that a note exists for exactly the reported-software case, and that
`max_buffer_size` never exceeds what `device.limits()` grants. **One check in
`web/test/browser.mjs`**, in the WebGPU run: the reported acceleration is one of the three
strings, and the note is present for exactly the software one.

## Bugs found by building, not by reading

**The upload guard promised eight times what the device would accept.** `Capabilities` took
`max_buffer_size` from `adapter.limits()` — the adapter's *advertised* maximum — while the device
was created with `Limits::downlevel_webgl2_defaults().using_resolution(limits)`, and
`using_resolution` copies only the three texture-dimension limits. Every buffer limit therefore
stayed at the downlevel default. That number is the guard on every upload path:
`GpuMesh::upload(&device, gpu.capabilities.max_buffer_size, …)` in `web/src/lib.rs`, twice in
`app/src/shell.rs`, checked in `render/src/scene.rs`. A mesh between the two numbers passed the
check and was then handed to a device that refuses it — a validation error or a device loss, which
is exactly the failure the comment above the field says the check exists to prevent.

Measured on this container, on lavapipe: **the adapter advertises 2047 MiB and the device is
granted 256 MiB**. An 8× over-promise on the least capable thing in the matrix; on a real card the
adapter's number is larger and the device's is the same 256 MiB, so the gap widens with the
hardware.

Reading the field would not have found it. The doc comment was right, the call site was right, and
the two numbers are the same on any adapter weak enough to be granted everything it has — which is
none of the ones in CI. It came out of asking a different question and following
`max_buffer_size` back to where it is set.

## Verified, and not

**Verified.**

| | |
| --- | --- |
| `cargo test` | 65 native tests pass. |
| `render/tests/headless.rs`, **with an adapter** | `mesa-vulkan-drivers` installed into this container, so the four render tests *ran* rather than skipping — which is the point, since two of the assertions are new. lavapipe is correctly reported as `software (CPU rasteriser)`, the note appears, and the buffer limit is asserted against the device's own. |
| The number in the bug above | Printed from a throwaway test against both `adapter.limits()` and `device.limits()` on the same run, then deleted. |
| `cargo clippy --all-targets -- -D warnings`, `cargo fmt --all --check` | Clean, on Rust 1.98. |
| `make wasm` | The changed `web/src/lib.rs` type-checks for `wasm32-unknown-unknown`, with `glow` still in the tree. |
| `make app-test` | A real X11 window under Xvfb, thirty frames, chrome and scene drawn separately — and the two new lines printed above them: `vulkan on llvmpipe (…) (software (CPU rasteriser)) — … max buffer 256 MiB`, and the note. |
| The browser, in four runs | `node web/test/browser.mjs` against `make web`. **The new check passes on the evidence that matters**: Chromium's ANGLE/SwiftShader adapter is reported as `software (CPU rasteriser)` and carries the note, where before it was a name string that read like a GPU. |

**Not verified, and the risk taken with each.**

- **No hardware has been seen by this change.** Everything above ran on a CPU rasteriser, so the
  branch that says `Hardware` has never been taken anywhere. The mapping from `DiscreteGpu` and
  `IntegratedGpu` is one line and is not the risky part; what is untested is that a real driver
  reports what this assumes it does. Register item 8 is unchanged by this work.
- **`Unknown` on WebGPU is reasoned, not observed.** It follows from what the WebGPU API exposes
  and what wgpu can therefore map, and the browser run did not test it: in this container WebGPU
  reports an adapter, draws nothing, and the loader falls back — so what was observed was the
  **GL** backend's answer, on SwiftShader. No run anywhere has yet printed `unreported`.
- **The browser run was 32 checks, not the 33 CI runs.** `make web-threaded` needs a nightly
  toolchain that is not installed here, so `web-both` was not run and the two variant checks took
  their single-threaded branch. **Two checks fail — "the canvas is not blank", 5 colours against a
  threshold of 8, in both runs with a graphics path.** Both are the failures the register already
  records as pre-existing on `main`; nothing in this work touches what is drawn. With the threaded
  variant built, CI's count becomes 34.
- **The 256 MiB is this device's, not a constant.** It is `downlevel_webgl2_defaults` as wgpu 30
  defines it. Nothing here pins that number, and nothing should: the fix is to read the device,
  which is what it now does.
- **Nothing about the compute half changed.** `compute` is still detected and still has no reader.
  This work made the report honest about *what is drawing*; it did not make anything use what is
  reported, because there is nothing yet to use it.

## Loose ends, deliberately left

- **`degradation()` and `software_rendering()` are two methods and the page shows both.** They
  answer different questions — "this API cannot do compute" and "there is no GPU here" — and
  merging them into a list of degradations would be tidier and would break the invariant the
  headless test asserts. Worth doing when there is a third.
- **The limits asked for are still `downlevel_webgl2_defaults` on every target.** That is
  deliberate and documented, but it means a desktop with 8 GiB of VRAM is capped at a 256 MiB
  buffer, and the first import large enough to care will meet it. Asking for more on native, and
  handling not getting it, is a decision nobody has needed to make yet.
- **`Acceleration` is not in the `.w3d` file, the NOTICE, or any report that outlives a session.**
  It is a line on a page and a line on a terminal.

## Next

- When the first compute pass is written, `compute` acquires its first reader and the limits

## Walkthrough · as completed

The report now answers two questions it could not answer before — *is a GPU doing this?* and *what
will this device actually accept?* — and one of them was being answered wrongly rather than not at
all.

What landed: `Acceleration` with three values and one mapping point; `software_rendering()` beside
`degradation()`, shown by the desktop shell, the browser's `report()` and the page; `Capabilities`
read after `request_device` so its limits are the device's; two invariants in the headless test
and one in the browser test; and the rule written into `STACK.md`, where the next person to reach
for `adapter.limits()` will meet it.

What did not land, and is now the register's: the limits request is still `downlevel_webgl2_defaults`
on every target, and no run anywhere has printed `hardware`. Both are in the register's small
items and in item 8. Nothing here is pending in this file.
