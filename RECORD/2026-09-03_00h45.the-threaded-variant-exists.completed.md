# 2026-09-03 00h45 · The threaded variant exists

Takes register item 4, **the threaded variant**, which
[`2026-09-02_23h07.cross-origin-isolation-on-github-pages.completed.md`](./2026-09-02_23h07.cross-origin-isolation-on-github-pages.completed.md)
named as the only thing left between that work and threads on the deployed page.

## Where this repo actually was

The host-side blocker had been gone since the service worker landed: the page on GitHub Pages is
cross-origin isolated, `SharedArrayBuffer` is available, and `crossOriginIsolated` is true. What
was missing was the build.

So the two-entry build matrix had one entry, and every part of the machinery around it was
already written and already dispatching into nothing. `loader.js` probed threads, probed
isolation, decided `threaded`, sent a `HEAD` to `./dist/threaded/w3d_web.js`, got a 404 on every
page load, fell back to `single`, and said so. `make web-test`'s fourth run asserted that this
happened — a check whose own comment said it was the one that would have to change.

Two things in the register were also out of date, and only one of them is fixed by this work.
The browser has drawn `TruckKernel` geometry since 2026-08-27, not a `FakeKernel` bounding box;
item 6 still said otherwise. And what "real geometry" means there turned out to be much narrower
than it reads — see the boolean below.

## Walkthrough · as built

1. **`kernel-truck`: a `parallel` feature, and a tessellator that can use it.** The face loop is
   split into three free functions — `face_mesh` builds one face's mesh with indices from zero,
   `mesh_surface` meshes a surface at a sag, and `append_face` merges one into another, shifting
   indices past what is already there. `tessellate` then sorts the faces exactly as before, meshes
   them (`par_iter` under the feature, `iter` without it), and merges the results **in the sorted
   order, never in the order they finished**.

   That last clause is the whole design. `face_of_triangle` is face *identity* — what a selection
   and a per-face fillet are stored against — so a mesh whose face numbering moved with the core
   count would move a user's selection between two runs of the same build. It is the same rule as
   the relaxed-SIMD ban in `AGENTS.md`, for the same reason: a result a machine is allowed to
   disagree about is not a result.

2. **`kernel-truck/tests/tessellation.rs`.** Fingerprints of a box and a cylinder — counts, an
   order-sensitive checksum over raw `f32` bits, and one over the face ids — pinned as literals
   and asserted under *both* feature settings. `make check`, `make clippy` and `make test` each run
   the crate twice, once each way. A literal rather than two runs compared in one process, because
   a build with the feature and a build without it are different programs and the only way one
   test can hold both to the same answer is for the answer to be written down. The file also
   asserts `TruckKernel: Send + Sync`, which the browser's threaded build silently depends on and
   which the seam deliberately does not require of a backend.

3. **`w3d-web`: a `threads` feature.** `wasm-bindgen-rayon`'s `init_thread_pool` re-exported so JS
   can start the pool, `w3d-kernel-truck/parallel` turned on with it, and `report().threads`
   carrying `rayon::current_num_threads()` — *read from rayon*, not from which directory the
   module was loaded from. A threaded module whose `initThreadPool` was never awaited reports 1
   there and would report "threaded" everywhere else. `report().tessellateMs` times the
   tessellation with the GPU upload outside the clock.

4. **`make web-threaded`, and `make web-both`.** Nightly, `-Z build-std=std,panic_abort`, and eight
   flags in `THREAD_RUSTFLAGS` that are each load-bearing — three target features, three linker
   flags and four symbol exports, argued above the target rather than listed. Output into
   `web/dist/threaded/`, which is where `loader.js` has been looking since the loader was written.

5. **`tools/wasm_threads.py`.** Parses the wasm and asserts the module's memory — defined or
   imported — is shared. The build saying yes and the artifact being right are different
   questions, and this is the second one. Same argument as the `glow` grep in `make wasm`.

6. **`tools/rayon_worker_entry.py`.** Rewrites one import specifier in wasm-bindgen-rayon's
   generated worker bootstrap. It fails loudly when the pattern is absent, and is idempotent. See
   the bug below for why it exists at all.

7. **`web/loader.js`.** `poolSize()` reads `hardwareConcurrency` and caps it, with the cap written
   down as a guess. `boot()` awaits `initThreadPool` after instantiating, before anything asks
   rayon for work — and falls back to loading the single-threaded variant if the pool throws,
   because rayon on wasm has no single-threaded path to degrade into.

8. **`web/index.html`.** The status line shows the pool's size next to the variant's name, and the
   tessellation time next to the triangle count. Both on purpose: a threaded build whose workers
   never started reads as `variant threaded · pool 1`, and showing only the first would flatter it.

9. **`web/test/browser.mjs`.** `THREADED_BUILT` decides which assertions run, and **both branches
   assert**: with the build, the page must end up threaded with a pool larger than one and with no
   note to explain; without it, the page must say the build is missing and report a pool of one.
   Runs 1 and 4 both check it — run 4 because that is the GitHub Pages case, and it is where the
   service worker stops being a page that says "isolated" and becomes a page that is faster for it.

10. **`tools/licences.py` and `tools/notice.py` now iterate builds, not targets.** See below.

11. **`.github/workflows/nightly.yml`, `STACK.md`, `README.md`.** The browser job installs nightly
    and `rust-src`; `make web-test` depends on `make web-both`, so both entries of the matrix are
    built before the browser sees them.

## Bugs found by building, not by reading

- **The build produced a module with a private memory, and every step succeeded.** `+atomics` is a
  *target feature*; `--shared-memory` is a *linker flag*; enabling the first does not imply the
  second. cargo was happy, rustc was happy, and `tools/wasm_threads.py` — written minutes earlier
  on the argument that this class of failure exists — failed on its first real run, against my own
  build. Without it the page would have booted, said "threaded", and run on one core.
- **`__wasm_init_tls` was garbage-collected.** wasm-bindgen needs it to give each worker its own
  thread locals. It is synthetic, nothing in the module calls it, and the linker drops it unless it
  is exported by name. The failure arrives from wasm-bindgen after a minute of linking and names
  the symbol, which is the kind of error one can act on — unlike the next one.
- **rayon's worker bootstrap imports a directory.** `workerHelpers.js` reaches the main module with
  `import('../../..')`, which a bundler resolves to a package entry and a web server answers with
  404. The worker then never posts `wasm_bindgen_worker_ready`, and `initThreadPool` waits on a
  promise that will never settle. **The page hangs, with no error, on the one path where everything
  else has already succeeded** — no exception to catch, no failed check, nothing in the status
  line. The upstream comment says the technique "works well with bundlers today"; this build has no
  bundler. It cost the most of anything here and produced the least evidence while it was
  happening.
- **`make licences` and `NOTICE` never saw the threaded build's crates.** `cargo metadata
  --filter-platform` prunes an optional dependency that is off, so `wasm-bindgen-rayon` and
  `wasm_sync` — two crates that reach a user's browser in the variant this file is about — were in
  the lockfile, in the artifact, and in neither audit. Both tools now iterate a list of *builds*
  rather than targets, with the wasm target appearing twice. 305 crates became 308, all
  compatible, and `NOTICE` was regenerated. Nothing about this was caused by the threads work; it
  was uncovered by it, and it would have been equally true of any future feature-gated dependency.
- **`TruckKernel::boolean` is not a boolean.** `BooleanOp::Difference` returns a copy of its first
  operand. `Union` and `Intersection` return an axis-aligned *bounding box* of the operands'
  bounds. Found by building a "drilled plate" test fixture that tessellated to 24 vertices and 12
  triangles, which is a box. The consequences are larger than this file:
  - The scene the browser has been drawing since 2026-08-27 — described in `w3d-web` as a plate
    with a hole — is a plate. The page is real tessellation of real B-rep surfaces, and every solid
    in it came from `create_box` or `create_cylinder`; nothing in it came from modelling.
  - **The conformance suite passes anyway.** That is a finding about the suite, not a reprieve for
    the backend: whatever `conformance` asserts about `boolean`, a function that ignores its second
    operand satisfies it. This is exactly the case register item 12 predicted a second backend
    would expose, arriving from the second backend itself.
  - It is not fixed here, and fixing it is not small: `truck` 0.6 has no boolean in
    `truck-modeling`, so this is `truck-shapeops` at best and a real piece of geometry work at
    worst. It goes to the register named for what it is.
- **`make web-test` has two failing checks on `main`.** "The canvas is not blank" fails in the
  WebGPU and WebGL2 runs, at 5 distinct colours against a threshold of 8. Verified against a
  stashed tree built from `main`: the same two checks, the same count of 5. Not caused by this work
  and not fixed by it — and the identical count is also the strongest evidence that the
  tessellator refactor changed no pixel. The threshold was **not** lowered; a check that is
  adjusted until it passes is not a check.

**Not verified, and the risk taken with each.**

- **No speed claim is made, and none is available.** `tessellateMs` reported 0–2 ms. The scene has
  one solid of twelve triangles and six faces; the pool has four threads. There is nothing in it to
  parallelise, and the number is noise. It exists so that a scene worth measuring has something to
  be compared against — **it is not evidence that threads made anything faster, and nothing in this
  repository is.** The register's "measure something" is untouched by this file.
- **Four cores, one browser, one machine.** `hardwareConcurrency` is 4 in this container and the
  browser is Chromium under SwiftShader. No Firefox, no Safari, nothing with a real core count.
- **Nothing pins the nightly.** `-Z build-std` and `+atomics` are unstable; a nightly that changes
  either breaks `make web-threaded` with no warning, and no date is recorded anywhere. Built on
  `1.100.0-nightly (5db7f4be8 2026-09-01)`, which is a fact about one run and not a pin.
- **The `initThreadPool` failure path has never run.** It is written from the failure modes the
  platform documents — a CSP without `worker-src`, an undeployed `snippets/`, an engine out of
  memory — not from one that was observed. The failure that *was* observed, the hang, is a
  different shape and this code would not have caught it: a promise that never settles is not a
  rejection. A timeout would cover both and is not written.
- **The cap on the pool at 8 is a guess.** Written down as one, in the function.
- **`wasm_threads.py` reads the memory and not the code.** A module with a shared memory and no
  atomic instructions is not something this toolchain can produce, so the cheaper check was taken.
  If that stops being true the checker will say yes to something it should not.
- **The threaded page has only been served by `web/serve.py`.** GitHub Pages serves the
  `snippets/` directory as ordinary files and should behave identically, but the deployment has not
  been through a browser since this landed.

## Loose ends, deliberately left

- **Only tessellation uses the pool.** Booleans, STEP import, the mesh upload and the frame loop
  are all on the thread that asked. The threaded variant is a floor, not a fast modeller.
- **`web/dist/threaded/` is not relocatable.** The worker resolves `../../../w3d_web.js`, so the
  entry's name and the snippet's depth are now coupled. `rayon_worker_entry.py` takes both as
  arguments and fails loudly rather than silently, which is the mitigation rather than the fix.
- **`make web-both` relinks.** Both halves write
  `target/wasm32-unknown-unknown/release/w3d_web.wasm`, so alternating between them costs a link
  each time. A separate `--target-dir` fixes it and costs several GB of disk and a second CI cache.
- **The loader's `HEAD` 404 is gone only where both variants are deployed.** A deployment that
  runs `make web` alone still logs one per page load, and still degrades correctly.
- **`w3d-kernel-fake` is still a dependency of `w3d-web` and is no longer used by it.** Noticed,
  not touched: removing a dependency is a separate change with a separate reason.

## Walkthrough · as completed

The browser's build matrix has two entries. `make web-threaded` produces a module with an imported
shared memory, atomic instructions and a rayon pool; the loader starts that pool, reports the size
rayon actually has rather than the name of the directory the module came from, and falls back if it
will not start. The pool's one job today is meshing a solid's faces at once, which a pinned
fingerprint holds to the same bytes as the sequential path — because face ids are identity and a
mesh that depends on a core count is not a mesh. In Chromium the deployed configuration — no
headers from the host, the service worker supplying them — comes up threaded with a pool of four,
which is what the previous file's work was for.

Four of the five things that had to be got right were invisible from the build's exit code: a
private memory where a shared one was wanted, a garbage-collected TLS symbol, a worker bootstrap
that resolves a directory only a bundler can serve, and two distributed crates that neither the
licence check nor `NOTICE` could see. Each is now checked by something that reads the artifact
rather than the command.

The largest finding is not about threads at all: `TruckKernel::boolean` returns a copy for
`Difference` and a bounding box for the other two, the conformance suite passes it anyway, and the
scene the browser has been drawing for a week is a plate with no hole in it. That is on the
register, named, with what it says about the suite.

No claim is made here that anything is faster. There is a pool, there is a number on the page, and
there is not yet a workload worth measuring.
