## Where this repo actually was

`GeometryKernel` had **one** bit about itself, `does_geometry`, and it was
written for the conformance suite: it decides whether to weigh an answer or
merely check its shape. Nothing else could ask a backend anything.

A button asks a different question, and by the previous session there were
seven of them behind that one bit. The register had been saying so since
2026-09-14 and said it more loudly on 2026-09-18:

> **The Ribbon still offers all three**, because there is no capability query on
> the seam for a button to ask. `does_geometry` is one bit and this needs six; a
> user finds out by pressing and reading the status bar. **It needs more than
> six since 2026-09-18**: `fillet_edges` and `chamfer_edges` joined the seam.

Read in the code rather than in the list, the state was:

- `truck` — the backend the **browser and the default desktop build both
  run** — declines `fillet`, `chamfer`, `fillet_edges`, `chamfer_edges`,
  `shell`, a sweep along a path of more than two points, a loft of more than two
  sections, and STEP in both directions. Every one of those refusals is honest
  and in words, and every one of them arrives *after* the press.
- The Ribbon's `Fillet [R]`, `Chamfer [C]` and `Shell [H]` were enabled on any
  non-empty selection; `Sweep`, `Loft`, `Import STEP...` and `Export STEP...`
  were enabled unconditionally.
- The edge-blend gizmo drew its two handles whenever an edge was selected, on
  every backend. A user could grab one, drag it, watch a radius follow the
  cursor, release — and be told the build has no rolling-ball surface.

**The environment cost the first twenty minutes again**, in the same two ways
the previous session recorded and one new one. This container starts at rustc
1.94.1 and `egui 0.36.1` needs 1.95, so `make test` fails in `check` before any
test; `rustup update stable` (1.98.1) fixes it. OpenCASCADE, `xvfb` and
`libxkbcommon-x11-0` are absent. The new one: the apt index is stale, so the
install the previous record prescribes 404s on a package version that no longer
exists — `apt-get update` first, and then it is exactly the four `libocct-*-dev`
packages the Makefile names.

## Walkthrough · as built

1. **`Capability`, and what it is careful not to promise (`kernel/src/lib.rs`).**
   Seven variants, and the doc comment spends most of its length on the limit
   rather than the feature: this answers *"this build never does X"* and not
   *"this build will do X to this solid"*. That is not a gap to close later. A
   query that covered `truck`'s boolean — which declines a body with a pole, and
   two boxes sharing a coplanar face — would have to be handed the operands, at
   which point it is the operation with the work taken out, and the backend has
   two code paths that must agree about what it can do. So a capability takes no
   arguments and is stable for the life of the process, and the status bar keeps
   its job.
2. **`supports(cap)` on the seam, with no default.** `does_geometry`'s reason
   applies — a backend says what it is — and there is a second one. A default
   has to be `true` or `false` and each is wrong invisibly: `true` makes a new
   backend claim everything until somebody notices a disabled button that should
   be enabled, which nobody reports; `false` greys out controls that work.
   Requiring the match means **a capability added to the enum stops every
   backend compiling**, and its author has to go and ask each one.
3. **Named for the case that is actually declined.** `BentSweep`, not "Sweep":
   `truck` sweeps along a straight line and declines a path that turns, so a
   capability called "Sweep" would be `false` for it and would grey out a
   control it can serve. Same for `MultiSectionLoft` against a two-section loft.
   This is not tidiness — see the third bug below, where the Ribbon's own
   buttons split on exactly that line.
4. **One capability for four blends.** The seam already binds `fillet`,
   `chamfer`, `fillet_edges` and `chamfer_edges` into "all four or none";
   splitting the query would let a build describe a state the contract forbids.
5. **`EdgeIdentity`, which is not an operation.** It is here because a button
   needs it: turning a click into a per-edge blend takes a backend that blends a
   named edge *and* one that can name the edge under the cursor. `FakeKernel`
   has the first and not the second, and `TruckKernel` has the second and not
   the first — the two backends between them prove these are different
   questions, and a single "can this do edges" bit would be wrong about half of
   each.
6. **The three backends.** `truck` answers `false` six times and `true` to
   `EdgeIdentity`; `fake` answers `true` to the four it performs as bookkeeping
   and `false` to STEP and to edge identity; OpenCASCADE answers `true` to
   everything, which is a claim the probe then tests rather than a shrug.
7. **The conformance probe, in both directions
   (`kernel/src/conformance.rs`).** `supports` is a second description of a
   backend written by hand beside the one the code gives, and the only thing
   keeping them together is this. Every capability is probed on every backend;
   a `true` that answers `Unsupported` fails, **and so does a `false` the
   operation then performs** — without that half a backend passes by denying
   everything, which is exactly the migration a busy author writes. Only
   `Unsupported` counts as the contradiction: a probe answering `Degenerate` or
   `Failed` was *attempted*, which is what `true` claimed. The answer is also
   read before and after, because a capability that changed under an operation
   would describe a state no caller can reason about.
8. **The negative control (`kernel-fake/tests/conformance.rs`).** A `Liar`
   wrapping `FakeKernel` with exactly one answer inverted, run once in each
   direction, and the assertion is `assert_eq!` against a **one-element** list:
   the capability check must be the only failure. That is a claim about what the
   probe does not disturb as much as about what it catches. The delegation is
   twenty-five methods written out, because a wrapper that could not be held to
   the rest of the suite could not support that claim.
9. **`Document::supports` and `Editor::supports`.** Forwarding, and documented
   as forwarding: the callers that need this are UI, and `document().kernel()
   .supports(..)` asks them to reach through the seam for something the
   document can answer. Neither caches nor adds an opinion.
10. **The Ribbon (`app/src/shell.rs`).** `capable()` wraps
    `ui.add_enabled` and keeps the two reasons a control can be off apart,
    because they mean opposite things: `enabled` is about the *document*
    (nothing selected — press something else), a missing capability is about the
    *build* (it will not come back today). The capability is checked second and
    its sentence wins, since "select an object first" is actively misleading
    advice for an operation that is not there. The words are
    `Capability::absence`, which lives beside the enum so a tooltip, a log and a
    status bar cannot drift.
11. **The blend handles are not drawn where a blend cannot happen.** A handle a
    user can grab, drag and read a radius off, that then reports the build has no
    rolling-ball surface, is worse than no handle — it takes the gesture before
    it gives the answer.
12. **`Editor::blend_selected_edge` asks before it meshes**, and still handles
    `edge_of_line` returning `None` afterwards. Those are two different
    questions and the code says so: the capability is about the *build*, the
    `None` is about the *mesh in hand* — a wireframe that came from
    `line_edges()`'s fallback has segments invented from triangle boundaries,
    and those are not edges.
13. **`AGENTS.md`** gains the rule and the conformance row gains the probe. The
    rule states both halves of what this is not: not a substitute for handling a
    refusal, and not a licence to name a capability loosely.

## Bugs found by building, not by reading

- **`Editor::run` threw away whether the command worked.** It collapses `Ok`
  and `Err` into one status string, which is right for the shell and leaves
  every other caller unable to tell a refusal from a success except by reading
  the prose. Found by needing to assert "an operation this build denies is one
  that *fails*" and discovering the assertion could only be spelled as a
  substring match — which would have made it a test of the wording. `try_run`
  returns the outcome; `run` is now two lines over it.
- **The capability test shared one document across its cases, and OpenCASCADE
  caught it.** `Fillet` rounds every edge of the box, so `Chamfer` on the next
  iteration met a solid with no sharp edges and OCCT answered *"There are no
  suitable edges for chamfer or fillet"* — and the test read that as the build
  failing to do something it claimed. The failure was legible **only because the
  contract separates `Failed` from `Unsupported`**: the message was the
  operation reporting on that solid, not on the build, which is the distinction
  the probe is built on, arriving as a bug report about the probe's own test.
  Each case now gets the box the button would be pressed on.
- **A capability named for the operation instead of the decline would have
  greyed out a working button.** The Ribbon's `Sweep` builds a **three-point**
  path and the Ribbon's `Loft` joins **two** profiles — so Sweep needs the
  capability and Loft does not. A query called "Loft" would be `false` on
  `truck` and would disable a control that works there today. Greying out a
  control that works is the same failure as offering one that does not,
  arriving by way of the fix; it has a test of its own.
- **The negative control's two direction labels were swapped in the first
  draft.** Inverting `Blend` — which `FakeKernel` performs — *denies* a
  capability; inverting `StepExport` *claims* one. The test passed either way,
  because the label appears only inside the failure message, which is precisely
  the kind of error that survives: it is wrong exactly when somebody is reading
  it under pressure. Caught on re-reading, not by running.

## Verified, and not

**Verified.**

- `make test` — check, clippy (`-D warnings`), `fmt --check`, licence and
  notice checks, the suite and the `parallel` build: passes, **208 tests**
  against **203** on the branch point, measured by running the same count on a
  stashed tree rather than trusting the previous record's number. The five are
  one negative control and the four app-level tests; `make test` covers
  `w3d-app`, which the Makefile says out loud it is arranged to do.
- `make test-occt` passes, **28** — unchanged, because the probe runs inside
  the conformance test that already existed rather than adding one.
- `cargo test -p w3d-app --features occt` passes, **72**, against 68.
- `make wasm`, `cargo clippy -p w3d-kernel-occt --all-targets -D warnings`, and
  clippy over `w3d-app --features occt`: all clean.
- **The probe catches a lie in both directions**, and the capability check is
  the *only* check it fails when it does. This is the assertion the whole change
  rests on: without it, `supports` is a second opinion about the backend kept in
  a different file.
- **Every backend's answers agree with its behaviour**, on all seven
  capabilities, on all three backends — which is what `make test` and
  `make test-occt` now mean.
- **The answers reach the editor**, asserted against the recorded table rather
  than derived from `supports` (a test that computed its expectations from the
  thing under test would assert nothing). The day `truck` grows a rolling-ball
  surface, that test fails, and the failure is the reminder to re-enable the
  buttons.
- **A denied operation is one the editor refuses**, through the editor's own
  commands on the document's own solid — the path the button takes — with a
  fresh document per case.
- **A two-section loft is not gated**, and the capability is still `false` on
  the backend that declines a third section. The negative control for the
  naming.
- It runs: `make app-test` — window, egui, and the scene drawn on llvmpipe,
  with the gated Ribbon in it.

**Not verified.**

- **Nobody has hovered a disabled button, or failed to grab a handle that is no
  longer drawn.** There is no pointer and no display in this environment. This
  is the **third** body of work in a row resting on that, and it is now the
  larger part of what is unverified about the app: what is tested is that the
  editor refuses and that `supports` answers, not that the widget is grey or
  that the tooltip appears.
- **`capable()` itself has no test.** The helper that decides a button's
  enabled state and attaches the hover text is exercised only by `make
  app-test`, which draws the Ribbon and counts colours — it would not notice a
  button enabled that should be disabled. The gating is *correct by
  construction* from `Editor::supports`, which is tested; that the construction
  was applied to the right eleven call sites is read, not checked.
- **The probe's fixtures are one box and one circular profile.** A backend that
  declined a bent sweep of a *polygon* while performing one of a circle would
  pass. Every probe is the smallest call that can only be refused for the reason
  the capability names, which is what makes the two directions meaningful, and
  it is also the narrowest evidence for a `true`.
- **`EdgeIdentity` is probed on a box.** `edge_of_line(0)` on a tessellated cube
  says a backend attributes *some* segment to *some* edge. That the ids are the
  right edges is checked elsewhere — `kernel-truck/tests/edge_identity.rs` and
  `app/tests/blend_edges.rs` — and not by this probe, which asks only whether
  the backend answers at all.
- **The boolean has no capability and deliberately never will**, so the
  commonest thing a user meets on the browser build — a union of two cylinders,
  a cut along a coplanar face — is still found out by pressing. That is the
  limit stated in `Capability`'s own documentation rather than an oversight, and
  it means the Ribbon's boolean buttons are honest about the build and silent
  about the operands.
- **The browser asks nothing.** `w3d-web` has no Ribbon and no buttons, so
  nothing there consults the query, although its backend is the one with six
  `false`s. The query is on the seam the browser uses; the caller does not
  exist yet.
- **The keyboard shortcuts bypass the gating entirely.** `R` still reaches
  `Command::Fillet` and `H` still reaches `Command::Shell` on a build that has
  neither. Deliberate — a key has no disabled state to show and the refusal in
  the status bar is the honest answer — but it means the capability query
  governs the mouse and not the keyboard, and nothing enforces that the two
  offer the same set.

## Loose ends, deliberately left

- **Nothing still decides which *form* of blend a button offers.** The blend
  file left this and it is not taken: `Capability::Blend` says this build
  blends, and there are four blends — two whole-solid, two per-edge. The Ribbon
  drives the whole-solid pair and the gizmo drives the per-edge pair, and that
  split is a decision nobody made.
- **`Capability` is a flat enum with no notion of one implying another.**
  Nothing stops a backend claiming `EdgeIdentity` and denying `Blend`, which is
  right (`truck` does exactly that), or claiming `MultiSectionLoft` while
  declining a two-section loft, which is not right and is not checked. The
  probes would catch the second only by accident.
- **`absence()` is in English and the editor's refusals are in Spanish.** The
  Ribbon's labels are English, the status bar is mostly Spanish, and this change
  puts an English sentence into a Spanish refusal in
  `blend_selected_edge`. The app has no localisation and this is one more place
  that will have to be looked at when it gets one.
- **STEP's two capabilities are separate and no backend differs on them.**
  Kept apart because they are separate methods with separate failure modes; a
  reader may reasonably ask why, and the answer is that the check tying them
  together is better as a check than as a missing variant.

## Walkthrough · as completed

Closed 2026-09-21. It landed as **#18**, `21d6937`.

What stands: a build can be **asked** what it does. `Capability` has seven
variants and `GeometryKernel::supports` has **no default**, so a capability
added to the enum stops every backend compiling and its author has to go and ask
each one — the alternative being a default that is wrong invisibly in one
direction or the other. The variants are named for **the case actually
declined**, `BentSweep` and `MultiSectionLoft` rather than "Sweep" and "Loft",
and that is not tidiness: the Ribbon's own Sweep builds a three-point path while
its Loft joins two profiles, so a query named for the operation would have greyed
out a control that works on `truck` today.

The conformance suite holds every backend to its own answers **in both
directions**, because without the second half a backend passes by denying
everything, and that is exactly the migration a busy author writes. Only
`Unsupported` counts as the contradiction — a probe answering `Degenerate` or
`Failed` was attempted, which is what `true` claimed — and the negative control
in `kernel-fake` inverts exactly one answer, runs it each way, and asserts a
**one-element** failure list, which is a claim about what the probe leaves
undisturbed as much as about what it catches.

On the surface a user meets: the Ribbon's `Fillet`, `Chamfer`, `Shell`, `Sweep`
and the two STEP buttons are disabled with a reason on a build that cannot serve
them, the reason coming from `Capability::absence` so a tooltip, a log and a
status bar cannot drift; and the edge-blend handles are **not drawn** where a
blend cannot happen, because a handle that takes the gesture before it gives the
answer is worse than no handle.

Three things it found are worth more than the feature. `Editor::run` had been
throwing away whether a command worked, which is right for the shell and left
every other caller reading prose to tell a refusal from a success —
`try_run` exists now. OpenCASCADE caught a shared document across the probe's
cases, and the failure was legible **only because the contract separates
`Failed` from `Unsupported`**: a box with no sharp edges left is the operation
reporting on that solid, not on the build. And the negative control's two
direction labels were swapped in the first draft, which the test could not
catch, because the label appears only inside the failure message — wrong exactly
when somebody is reading it under pressure.
