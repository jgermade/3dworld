# 2026-09-02 23h07 · Cross-origin isolation on a host that sends no headers

## Where this repo actually was

`web/loader.js` has probed for cross-origin isolation since the viewport landed, and
`web/serve.py` exists precisely so the *absence* of the headers can be tested. Both were written
against a host that could send `Cross-Origin-Opener-Policy` and `Cross-Origin-Embedder-Policy` and
had forgotten to.

Since 2026-08-27 the page is deployed to **GitHub Pages**, which is not that host. It serves static
files and offers no mechanism — no config file, no `_headers`, nothing — for adding a response
header. So `https://jgermade.github.io/3dworld/` was permanently on the degraded branch: threads in
the engine, no isolation on the page, `SharedArrayBuffer` unavailable, and the loader's line about
the server not sending the headers shown to every visitor with no way for anyone to act on it. The
message was accurate and useless, which is the worst combination a diagnostic can have.

The prompt for this work was a gist proposing the service-worker technique
([gzuidhof/coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker), simplified). The
technique is sound and the simplification had three defects; both halves are below.

## Walkthrough · as built

1. **`web/coi-serviceworker.js`** — new. A service worker that re-issues every response with the
   two headers, and the registration code for it, in one file that branches on whether it is
   running in a page or in a worker. Once the worker controls the page the browser sees the headers
   and the document is cross-origin isolated, whatever the host did.
2. **`web/index.html`** — loads it as a **classic** script before the module, and, crucially,
   `await`s `__w3dCOI.ready` *before* `boot()`. On a first visit the worker is about to reload the
   page; booting first would fetch and instantiate a wasm module that is thrown away milliseconds
   later. On the reloading path that promise deliberately never resolves.
3. **`web/loader.js`** — `probe()` gains `isolatedBy`: `'server headers'` or `'service worker'`.
   The status line shows it. A user who cannot tell the two apart cannot tell a working worker from
   a host that quietly started sending headers, and cannot notice when the worker stops working.
4. **`web/test/browser.mjs`** — a fourth run: no COOP/COEP from the server, service worker allowed.
   It asserts the page ends up isolated, that it says the worker did it, and — the check most
   likely to be dropped as pedantic — that the variant is *still* `single` because the threaded
   build does not exist. Run 3 keeps asserting visible degradation, now via the page's own
   `?coi=off` hook, because with the worker in play a header-less host is no longer a page that
   cannot be isolated.
5. **`STACK.md`, `README.md`** — the consequence a host has to know about now has a second half:
   what to do when the host cannot comply, and that a host which *can* send the headers should.

### What was changed from the gist, and why

- **`respondWith` given a promise that resolves to `undefined`.** The gist's `fetch` handler ends
  `.catch((e) => console.error(...))`, which returns `undefined`; `respondWith` then fails with a
  `TypeError` about its argument and the page sees a network error with a misleading message. It
  returns `Response.error()` here — the network error the request was already going to be.
- **A reload on `updatefound`, unconditionally.** A new worker version is found on a page the old
  worker is already isolating correctly; reloading is at best pointless and at worst a loop. Here
  the only reload is the one that puts the page under a worker for the first time, and it is
  counted in `sessionStorage` with a limit of two. Past that the page runs degraded and says the
  headers are being stripped, because a reload loop is worse than a slow modeller and much harder
  to diagnose from the outside.
- **`window.document.currentScript.src` with no guard.** It is `null` in a module, in a deferred
  script and in any async one, and the expression then throws before the registration is attempted.
  It is read once, synchronously, and a missing value produces a sentence saying the file must be a
  classic script rather than a `TypeError`.

## Bugs found by building, not by reading

- **The first load must not boot.** Found by watching the network: with the registration left to
  race the module, the first visit fetches `w3d_web_bg.wasm`, instantiates it, and reloads. It
  works, and it downloads the payload twice on the one visit where the user has nothing cached.
  The fix is the `ready` promise that never resolves on the reloading path, which is why
  `index.html` awaits something before `boot`.
- **`?coi=off` breaks run 3 of the browser test if it does not exist.** Adding the worker silently
  turns "no COOP/COEP: the degradation must be visible" into a run where the degradation correctly
  never happens — a check that passes for a reason it was not testing. The hook exists so the old
  question can still be asked; that it does not *uninstall* an already-registered worker is stated
  in the file, because a flag that silently uninstalls things is a worse hook than one that does
  not.

## Verified, and not

**Verified.**

- Driven in headless Chromium against `python3 -m http.server`, which sends no COOP/COEP — the
  GitHub Pages situation exactly. The page comes back `crossOriginIsolated === true`,
  `isolatedBy === 'service worker'`, and
  `new WebAssembly.Memory({ shared: true }).buffer instanceof SharedArrayBuffer` — the thing all of
  this is for, and not a proxy for it.
- **Exactly one extra navigation.** Three `framenavigated` events across two `goto`s: the first
  visit reloads once, the second visit is isolated on arrival with no reload. The reload counter is
  cleared on the isolated load, so a later visit starts with its full budget.
- `?coi=off`: not isolated, no `SharedArrayBuffer`, and the note says why.
- `make web-test`, all four runs: the six checks of the new run pass, and so does everything in
  runs 2 and 3. **Two checks fail, and they failed before this change** — "the canvas is not blank"
  in runs 1 and 2, 5 distinct colours against a threshold of 8, on the container's SwiftShader.
  Confirmed pre-existing by stashing this work and re-running: same two failures, same counts.
  Nothing here touches rendering.

**Not verified, and the risk taken with each.**

- **Those two failures are not diagnosed.** They are named here because a record that reports a
  green run when the run was not green is worth nothing, and because the next person to run
  `make web-test` in a container will see them and need to know they are older than this file.
  Whether the threshold is wrong or the scene really is drawing five colours under SwiftShader is
  an open question this work did not open and did not answer.
- **Chromium only.** Firefox and Safari also honour headers injected by a service worker, and
  neither has been run — this repository has never run either, which is already in the register.
  Safari is the one to doubt: it has the most history of restricting service workers, and a failure
  there degrades to what the page did before this change, so the risk is a lost speed-up rather
  than a broken page.
- **Nothing has been observed on the deployed site yet.** The next push to `main` deploys it; this
  was verified against a local server that behaves the same way, not against
  `jgermade.github.io`.
- **`require-corp` is now a standing constraint on the page**, and nothing enforces it. Every
  subresource today is same-origin, so nothing is blocked. The first cross-origin script, font or
  image added without CORP or CORS will be blocked by a policy this commit introduced, and the
  error will not name the commit. No check catches that; only the comment at the top of
  `coi-serviceworker.js` warns about it.
- **It buys no speed today, and cannot.** The threaded variant is not built — register item 4 —
  so the loader now finds the page isolated, asks for `dist/threaded/w3d_web.js`, gets a 404, and
  says the variant is what is missing rather than the platform. That is a *better* sentence than
  the one before it and it is still a single-threaded modeller. The browser test asserts this
  rather than glossing it.

## Loose ends, deliberately left

- **The worker does not cache anything.** It is a header-rewriting proxy and nothing else: every
  request still goes to the network. Offline support would be a separate argument about staleness
  and a cache version, and it is not needed to answer the question this file exists for.
- **`Cross-Origin-Resource-Policy` is not added to outgoing responses.** It would let another
  origin embed this page's resources. Nothing needs that, and adding a header nobody asked for is
  how policies become mysterious.
- **The heuristic in `isolationSource()` can be fooled** by a host that sends the headers *and* a
  worker installed on an earlier visit — it reads as the worker's doing. Distinguishing them means
  re-fetching the document to inspect its headers, which the worker also rewrites. Documented at
  the function rather than fixed.

## Next

- Register item 4, **the threaded variant**, is now the only thing between this and threads on the
  deployed page. Its host-side blocker is gone; what is left is `wasm-bindgen-rayon`,
  `+atomics,+bulk-memory,+mutable-globals` and a nightly `build-std`.

## Walkthrough · as completed

GitHub Pages cannot send COOP and COEP, so `web/coi-serviceworker.js` supplies them from a service
worker and the page reloads once, before the wasm is fetched, to come back under it. The loader
reports which of the host and the worker did it, and the browser test grew a fourth run that
asserts the isolation, its source, and the fact that it still buys nothing until the threaded
variant is built. Three defects in the gist this started from — a `respondWith(undefined)`, an
unbounded reload on `updatefound`, and an unguarded `document.currentScript` — are named in the
file that replaces it. Nothing leaves the register: item 4 stays, with its host-side blocker gone.
