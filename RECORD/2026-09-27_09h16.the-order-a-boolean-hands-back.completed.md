# 2026-09-27 09h16 · The order a boolean hands back

Takes the small item *"`truck-shapeops` iterates other `FxHash` containers, and nobody has
looked"*, and the case the previous day handed it: the order of a boolean's faces changes
between runs.

## Where this repo actually was

- `vendor/truck-shapeops/` patched one map, the one in `polyline_construction` shown to reach the
  output. `healing/`, `divide_face/`, `loops_store/` and `faces_classification/` use `FxHash`
  containers too, and nobody had read whether any of them is iterated.
- Since the day before, `save_body` wrote a canonical order and `make xarch` asserted the saved
  cut's bytes — one scene, the drilled plate.
- Face ids were positions in a sort by `face_key` — a face's surface parameter range and the point
  at its middle — and edge ids were the order in which the sorted faces' loops were walked.
- The toolchain was the 1.98.1 stable and 1.100.0 nightly of the day before.

## Walkthrough · as built

**The audit, by reading.** Every map in the crate, and what is done to it:

- `divide_face/` and `loops_store/` touch their maps only through `entry`, `get`, `insert` and
  `remove`: caches and lookups. Nothing iterates them, so their order reaches nothing.
- `faces_classification/` looks faces up in its map and iterates the `Shell` beside it, a `Vec`.
- `healing/` iterates one map and sorts what it gets by parameter, so only an exact tie keeps the
  hash's order. It is keyed by `usize`, whose hash differs by target — but `healing` is exported
  for imported shapes and **is not on the boolean's path**; nothing in this repository calls it.

So nothing left in `truck-shapeops` reaches an output. What does is one call out of it:
`and` and `or` end in `truck_topology::Shell::connected_components`, which walks an `FxHashMap`
keyed by `&Face` — by address — and that walk is the order of the result's faces. That is the case
the previous day measured, now with its cause named. It orders faces; it does not change them.
`PATCHED.md` says all of this.

**Then the question the audit exists for: does that order reach anything?** The save no longer
shows it. The mesh sorts faces by `face_key` — but the sort is stable, so on a *tie* the input
order survives, and a tie needs two faces on one surface, which the drilled plate does not have. A
slot cut across the plate's top does: two top faces on one plane. Measured over six processes: the
same solid, the same saved bytes, and **the two top faces swapped face ids** between runs — ids 5
and 6, in three runs each. Face ids are what picking, the selection and every per-face badge hold.

The fix is a tiebreak in `face_key`: the face's boundary vertices, sorted. Two faces on one
surface with the same vertices are the same region. The sort, which was written out twice, is now
one function, `sorted_faces`.

**And the test for it found the edges.** `kernel-truck/tests/face_order.rs` loads a saved solid
twice — once as written and once with every free order reversed or rotated — and requires both to
number faces and edges the same, compared as the centre of each id's triangles or segments. Faces
passed with the tiebreak. **Edges failed on both scenes, with or without it**: `number_edges`
numbered edges in the order it walked each face's loops, and which edge a loop starts at is the
topology's order. The consequence was measured before it was fixed — with the old numbering, a
body and the same body saved and reopened **gave different edge ids, on the drilled plate and on
the slot**. And it was this repository's own doing: the previous day's canonical save rotates each
loop to a start of its choosing, where plain `compress` had kept the start the solid had. Before
that change a reopen preserved the walk; after it, a reopened document renumbered its edges and a
stored per-edge selection named another edge. The branch it landed on has not been merged, so no deployment carried it.

Edges are now numbered by a key of where they are — both ends, sorted, and the point at the middle
of the absolute curve, which tells apart two halves of a circle that share their ends — sorted,
with the walk's order kept only between exact ties.

**`make xarch` gains the slot, and ids.** Eight rows for the second scene — topology, triangles,
positions, face ids, edge ids, the saved numbers and the saved bytes — and face-id and edge-id rows
for the drilled plate too. The ids had never been compared across architectures: two builds that
drew the same picture and numbered it differently would disagree about what a user selected.

**`kernel-truck/tests/tessellation.rs`'s fingerprints moved, one component of each.** The edge
component of all three, and only that; positions and face ids are unchanged on the serial and the
parallel path. Re-recorded, as that file asks, with the reason beside the literals. The scramble
the two order tests share moved into `kernel-truck/tests/common/`.

## Bugs found by building, not by reading

- **Two faces on one surface swapped ids between runs.** Cause: a stable sort whose key could tie,
  over an input ordered by address. Found by building the first fixture with a tie in it.
- **A save and a reopen renumbered edges.** Cause: edge ids followed each loop's starting edge,
  and the canonical save of 2026-09-26 chooses that start. A regression of the previous day's, not
  of anything older — found by the test written for faces.
- **The first version of the face test could not fail.** It compared the solid the boolean returned
  with the scrambled reload, and the boolean's order happened to agree with the scramble's for the
  tied pair: with the tiebreak removed, it still passed. It now compares two loads of one file —
  canonical, and reversed — so a tied pair always arrives in opposite orders, and it fails without
  the tiebreak.

## Verified, and not

**Verified**

- The slot's face ids, mesh and saved bytes are identical across six processes after the change;
  before it, the mesh hash split three and three.
- `face_order.rs` fails without the face tiebreak (the slot) and without the edge sort (both
  scenes), and passes with both.
- `make xarch`: all **41** rows agree between x86-64 and wasm32, the slot's and the new id rows
  among them.
- `make test` passes: 223 tests in 43 suites, clippy with `-D warnings` and fmt included.

**Not verified**

- **Two scenes.** The drilled plate and the slot. A face-key tie between faces that also share
  their vertex set would still fall back to the input order; the argument that it cannot happen on
  a valid solid is an argument.
- **Existing documents' edge ids change once.** Any selection stored against an edge id numbered
  the old way names a different edge now. Nothing stores one across a save today — a `.w3d` holds
  no selection — so this is a note for the day something does, not a migration owed.
- **The `boundary[0][0]` choice in `integrate_by_component`** is decided by the address-keyed
  order too. It is harmless when a component of unclassified faces borders only one class, which
  every valid input gives; a degenerate input that made one border both would be classified by
  whichever edge came first. Not constructed, not tested.
- **`healing/`'s one iteration** is unreachable from here, and was read, not run.

## Loose ends, deliberately left

- **`truck-topology` is not patched.** `connected_components`' order is contained where it is
  consumed rather than fixed at the source; a second vendored crate for an order that no longer
  shows is not worth its maintenance.
- **The upstream report** still stands as a small item; it now has a second observation to carry.
