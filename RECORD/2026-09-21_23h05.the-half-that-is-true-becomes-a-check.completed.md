## Where this repo actually was

The cause of register item 4 was known and written down: the two builds cut the
same plate into different solids because `truck-shapeops` chains the
intersection polyline through an `FxHashMap`, and `rustc-hash` multiplies by a
different constant when `usize` is 32 bits wide, so the loop is entered at a
different vertex. Everything that establishes that — the operands being
bit-identical, the interference segments coming out in the same order, libm and
the optimizer being ruled out — existed only as a scratch crate in a container
that is reclaimed when the session ends, with a vendored, hand-instrumented
`truck` behind it.

That is the shape of claim this repository has a rule about. A measurement in a
record file cannot fail when it stops being true.

## Walkthrough · as built

**`xarch/` — `w3d-xarch`, one `measurements()` built twice.** A `Vec<Row>` of
`(name, rule, value)`, where the crate is compiled as a native binary *and* as a
`cdylib` for `wasm32-unknown-unknown`. The same function runs on both; the
comparison is what is new.

**Every value crosses as `to_bits()`.** The native binary prints the bit pattern
beside the decimal and `tools/xarch.py` compares *those*. A probe that compares
printed doubles cannot see a difference of an ulp, and an ulp is the whole
subject.

**A row carries its own rule**, so adding a measurement is one edit and not two:

- `Rule::Exact` — must agree bit for bit. Everything before the boolean.
- `Rule::Close` — within 1%, the tolerance `make web-test` already uses between
  the page's two copies of the demo scene, and for the same reason.
- `Rule::Report` — printed, never asserted. A number whose disagreement *is* the
  finding.

**What is asserted, and it is chosen rather than collected.** The operands as
saved solids (`save_body`, which writes the solid with no mesh in it, so two
identical blobs are two identical solids), their `f64` bounds, their topology,
and their meshes at four sags — 0.04 first, because that is
`max(1e-7, 40 * 1e-3)`, the tolerance `truck-shapeops` triangulates both shells
at before it looks for an intersection at all. Then the **topology of the cut**,
which does agree: the two builds disagree about where a curve starts, not about
what the solid is, and a result with a different number of faces would be a
different bug wearing this one's clothes.

**And each build is held to itself, in two processes.** Not ceremony: the first
version of this measurement, three hours earlier, hashed the *saved cut* — which
varies from run to run on one machine, because `TruckKernel` writes its vertices
in the iteration order of a pointer-keyed map — and produced one confident wrong
reading before anybody checked. A cross-architecture claim resting on a number
that is not stable *within* an architecture is not a claim. So `cut.blob.len` is
a row and `cut.blob.hash` deliberately is not.

**Five negative controls, and they run first.** An `exact` row that differs must
fail; a `close` row 5% apart must fail; a `report` row that differs must **not**
fail; two identical runs must not report drift; a drifting run must. The way a
script like this stops asserting is a rule name that quietly stops matching, and
then it prints a table of `same` forever.

**No `wasm-bindgen-cli`, and no `unsafe`.** Exporting three functions to a wasm
host is what `#[unsafe(no_mangle)]` is for, and AGENTS.md says a second crate
wanting `unsafe` is a design conversation. It did not need one: `wasm-bindgen`'s
macro is the route `w3d-web` already takes under the same `forbid`, and because
the exports take and return numbers, the raw module is directly callable — no
glue is generated and the CLI is not installed. The cost is one line in
`tools/xarch.js`: the macro appends a hash to an export name until that CLI
strips one, so a function is found by prefix and an ambiguous prefix is an error
rather than a guess.

**Every wasm import is stubbed with a function that throws.** Nothing in the
measurement should reach into JS; a run where something did is a run whose
numbers mean nothing, so it fails loudly instead of returning them.

**`make xarch`, and it is in CI.** In the `make test` job, after `make wasm` —
that job already adds the wasm32 target and the runner image has a node, so it
costs a build and no setup. It is not part of `make test` itself, which is the
repository's no-setup gate.

## Bugs found by building, not by reading

- **A `pub extern "C" fn` in a `cdylib` is not exported at all on
  wasm32-unknown-unknown.** Checked rather than assumed, because the whole
  design of the harness turned on it: a module built that way exports `memory`
  and nothing else. That is what sent this to `wasm-bindgen`'s macro instead of
  to an `unsafe_code` opt-out, which would have been a rule bent for no reason.
- **The rule and the index have to be checked, not trusted.** The two builds are
  aligned by position, because the wasm half cannot hand a string to its host.
  A row added on one side and not the other would silently compare the wrong
  pairs, so the wasm half exports its rule as a small integer and the script
  refuses to compare two lists whose rules disagree at any index.

## Verified, and not

**Verified.**

| What | How |
| --- | --- |
| `make xarch` passes | Run here: 29 rows, 25 `exact` all bit-identical, the four item-4 rows reported |
| Each build is deterministic | Two processes each, native and wasm32 |
| The table can fail | Five negative controls, run first, on every invocation |
| Nothing else regressed | `make test` green — **208 tests**, the same count as `21d6937` — and `make wasm` clean |
| The new crate is in the gate | A default workspace member, so `check`, `clippy -D warnings` and `fmt --check` cover it |
| It needs no new tooling | A wasm32 target, which `make wasm` already adds, and a node |

**Not verified, and the risk taken with each.**

- **The mesh rows are `f32` evidence and are labelled as such.**
  `w3d_kernel::Mesh` carries `f32` positions, so those rows would not notice a
  disagreement at 1e-14 — which is exactly the size of the one item 4 is about.
  The `f64` evidence is the blob and the bounds. This is stated in the crate's
  own documentation rather than left for a reader to work out, and it means
  `drill.mesh@0.04.hash` agreeing is a weaker sentence than it looks.
- **The stage that actually diverges is not in the check.** The interference
  segments coming out of `extract_interference` identical and *in the same
  order*, and the polyline then differing by a rotation, is the evidence that
  makes the diagnosis specific — and it needed a vendored `truck` with tracing
  compiled into it. None of that is here, and it is not clear it should be:
  pinning a fork of a dependency to hold a diagnosis is a heavier commitment
  than the diagnosis is worth.
- **One scene, one pair of solids.** A plate and a cylinder. The mechanism is
  general; the evidence is this cut, and a second fixture would cost a minute
  and was not added because nothing about the second one is known.
- **The 1% tolerance is a number.** It is four triangles in 6294 — 0.06% — so
  there is a factor of sixteen of slack, and a real regression inside the
  boolean that stayed under 1% would pass. The tolerance was chosen to match
  `make web-test`'s rather than to be tight.
- **The export-by-prefix lookup depends on a `wasm-bindgen` implementation
  detail.** Today the macro emits `prepare_<hash>`; if it stops, the prefix
  match still finds `prepare`, and if it emits two candidates the script fails
  rather than guessing. It is pinned by nothing but that error path.
- **CI has not run it.** It passes here, on this container; the step is written
  and the first run is the next push.
- **It says nothing about a browser.** Node's V8 and Chromium's V8 are the same
  engine and not the same build, and no page was involved.

## Loose ends, deliberately left

- **The dependency decision is untouched**, and it is the only thing that can
  actually make the desktop and the browser the same modeller. Fork, pin a
  `[patch.crates-io]`, or report upstream and wait. When it is taken, the three
  `Rule::Close` rows and the one `Rule::Report` row become `Rule::Exact`, and
  `make xarch` becomes the check this one could not be — the Makefile comment
  and the crate's documentation both say so where somebody will be standing.
- **`make web-test`'s 1% drift check is still 1%**, for the same reason and in a
  second place. It should become equality on the same day.
- **`TruckKernel::save_body`'s vertex order** was found three hours ago and is
  in the register; this work only made it visible, by having to route around it
  when choosing which rows to hash.

## Walkthrough · as completed

Closed the day it opened. What landed is a crate, a node runner, a comparison
script, a `make` target, a CI step, and four lines of documentation — and what
it is *for* is that one sentence in a record file is now a command that fails.

The sentence: **everything before the boolean is bit-identical on x86-64 and
wasm32, the topology of the cut is too, and each build is deterministic in
itself.** The day that stops being true, the diagnosis in the 22h10 file stops
being the explanation, and `make xarch` says so in CI rather than in nobody's
memory.

What it deliberately does not say is that the two builds agree, because they do
not, and a check that asserted it would have to be landed red. The four rows
that disagree are printed with their distance and the item number, which is the
honest shape for a defect that lives in a dependency: visible on every run,
asserted by nothing, and impossible to forget.

The register's small item *"Nothing re-checks what the two architectures agree
about"* is rewritten rather than removed: what is left of it is CI's first run
and the stage that needed a vendored `truck`.
