# 2026-09-14 21h34 · What an assembly costs

Takes **item 9** of [the register](./2026-08-25_21h59.what-is-not-built-yet.md) — "measure
something" — which has been pending since the first session under one form or another, and which
every other item that argues about performance has been waiting on.

## Where this repo actually was

Three files open in `RECORD/` where the convention says there should normally be one: the plan, and
two bodies of work that had landed and merged. Both are closed by this session before anything else
happened, because a folder whose open files are finished work cannot answer the question it exists
to answer.

And every performance number in the repository was somebody else's. Not *none* — that is what the
register said and it was not quite right. `make benchmark-step`, from 2026-08-27, timed
`cargo run -p w3d-kernel-occt --example import_step` as a subprocess, once per sample, and reported
a wall-clock duration and the child's peak RSS. What it could not do is say **which phase** the
time was in: process start, OpenCASCADE's static initialisers, part-21 parsing, the XDE walk and
the tessellation the example prints came back as one number. It also had no `.w3d` in it, ran the
debug build, and its output went to a terminal and was written down nowhere. A number nobody can
attribute to a phase is not a measurement; it is a stopwatch.

What was known about the workload: AS1 imports as eighteen bodies in ten assemblies, three levels
deep, and eighteen tessellations of five distinct shapes run synchronously on the thread that
asked. The `.w3d` it saves is 97 KiB. Nothing had ever been timed, and the 15 MB assembly that sits
beside AS1 in the same upstream had never been fetched, let alone opened.

## Walkthrough · as built

**`kernel-occt/examples/assembly_cost.rs`, run by `make measure`.** Nine phases, each timed on its
own, because they fail differently and a caller can only act on one at a time: the file off disk,
`import`, `tessellate` (a mesh per body through `Document::mesh`, cache cold), `pack` (into the
28-byte interleaved vertices a worker would post, via `w3d-render`'s `PackedMesh`, so the byte
count is *measured* rather than multiplied out of a triangle count), `save cold`, `save warm`,
`open cold`, `open warm`, and `draw again`.

Three derived rows sit under them and each answers a question the register had been arguing about
without evidence:

- **`stall`** is `import + tessellate + pack` converted to frames at 60 Hz. All of it is
  synchronous and on the thread that asked, which in the app is the thread that draws, so this is
  not a curiosity — it is how long the program is frozen.
- **`repetition`** groups the meshes by triangle, vertex and line count and reports what one blob
  per group would weigh. Two placements of one part are two bodies whose geometry differs by a
  location, so nothing here can compare them *as shapes*; equal counts are evidence of repetition
  and not proof of it, and the saving is therefore an upper bound on what instancing would buy.
- **`peak RSS`** is sampled **twice**: once with exactly one document imported and meshed, which is
  what a modeller would be holding, and once at the end of the run, which holds three copies and is
  the harness rather than the program. Reporting only the second would have been a number about
  this file.

**It refuses to print a debug timing.** Without `--debug-anyway` a debug build prints why and exits
non-zero: a number in a table like this is a number somebody quotes six months later, and the same
rule makes `SKIPPED:` loud in `w3d-render`.

What a debug build actually costs was then measured rather than assumed, by passing the flag.
`pack` is **29x** slower and `open warm` **5.7x** — and `import` and `tessellate` are *within noise
of release*, because they are OpenCASCADE's own C++ and it is compiled optimised whatever the Rust
profile says. The guard protects the Rust half, which turns out to be the small half; that is the
same fact as the one below, arrived at from the other side.

**It asserts nothing about durations, and it is not a `cargo test`.** There is no golden number for
a millisecond, a busy machine would fail one, and the samples are fetched rather than committed —
a test that passes when its input is missing is a test that says yes for a living. What it *does*
assert is the shape of what it measured: that the number of cached meshes equals the number of
bodies (so nothing was meshed twice or skipped), and that both files come back with the node count
that went in. A measurement of the wrong thing is worse than no measurement.

**The 15 MB workload is in `tools/step-samples.txt` under a third verdict, `measure`**, pinned by
SHA-256 like the rest and fetched by `make step-samples-big` rather than by `make step-samples` —
no check needs it, `make step-check` runs on every push, and 15 MB downloaded on every CI run to
sit unopened is a cost with nothing on the other side. `tools/licences.py` names it beside the
other three.

**`make benchmark-step` and `tools/benchmark_step.py` are gone.** Superseded rather than broken:
everything it timed, `make measure` times per phase, in release, with the `.w3d` included.

## What it measured

`AS1` — 136 KiB of AP203 from Pro/ENGINEER, eighteen bodies in ten assemblies, three levels deep.
One run on one machine, in release, unrepeated and unaveraged.

```
  read               0.3 ms   139752 bytes off disk
  import            74.1 ms   18 bodies in 10 groups
  tessellate       859.5 ms   18 meshes · 51920 triangles · slowest body 481.4 ms
  pack               1.5 ms   2.49 MiB across the worker boundary · 0 of 18 de-indexed
  save cold          6.2 ms   97 KiB of .w3d, nothing meshed yet
  save warm        246.8 ms   4.95 MiB of .w3d, the same document after it was drawn — 52x
  open cold          3.6 ms   28 nodes back
  open warm         79.8 ms   28 nodes back
  draw again       102.2 ms   12% of the first tessellation
  stall            935.1 ms   56 frames at 60 Hz, on the thread that asked
  repetition                  18 meshes in 5 groups by count · 996 KiB instead of 2.49 MiB
  peak RSS          79 MiB    one document, imported and meshed
```

`RC_Buggy_2_front_suspension` — 14.55 MiB of STEP, the 15 MB assembly the register has been asking
for since 2026-08-26, in the same upstream as the three check samples. Two hundred and eleven
bodies. Nothing here asserts that it imported *correctly*: it is a workload, not a check.

```
  read              14.2 ms   15257496 bytes off disk
  import         18170.4 ms   211 bodies in 30 groups
  tessellate     37939.1 ms   211 meshes · 2807440 triangles · slowest body 16976.5 ms
  pack              61.4 ms   84.26 MiB across the worker boundary · 0 of 211 de-indexed
  save cold       1665.1 ms   40.30 MiB of .w3d, nothing meshed yet
  save warm       7626.7 ms   230.29 MiB of .w3d — 6x
  open cold        798.0 ms   241 nodes back
  open warm       3850.1 ms   241 nodes back
  draw again     33378.8 ms   88% of the first tessellation
  stall          56170.9 ms   3370 frames at 60 Hz, on the thread that asked
  repetition                  211 meshes in 83 groups by count · 38.92 MiB instead of 84.26 MiB
  peak RSS         524 MiB    one document, imported and meshed
                   964 MiB    end of the run, three copies — the harness, not a modeller
```

**Fifty-six seconds.** Opening one file from the wild freezes this program for the better part of a
minute, and in the app that is the thread that draws: no frame, no cursor, no cancel, no progress.
It is the single most important number this session produced, and nothing in the repository had it.

**524 MiB for one document**, from a 14.55 MiB file — thirty-six times the input, in a process that
also holds OpenCASCADE. `AGENTS.md` rejects wasm64 and says to revisit it only when a real document
is measured against the 4 GB ceiling: this is that measurement, and it says eight assemblies of this
size, or one an order of magnitude larger, is where the ceiling is. It does not overturn the
decision — it puts a floor under it, which is what the rule asked for.

**84 MiB across the worker boundary**, against the 256 MiB buffer the device is capped to by
`downlevel_webgl2_defaults`. One assembly is a third of what the weakest target in the matrix will
grant, and the cap is the same on a desktop with gigabytes of VRAM. That is item 4's problem stated
in bytes for the first time.

**The import is not the expensive half. Tessellation is.** On AS1 the STEP read and the whole XDE
walk are 74 ms against 860 ms of meshing — eight percent of the stall. Every argument in this
repository about import cost has been about the wrong phase.

**And one body dominates.** 481 ms of AS1's 860 ms is a *single* body — 56% — and on the large
assembly one body is 17.0 s of 37.9 s. This is the number that matters to the threaded design: sharding
tessellation across bodies has a hard floor at the slowest one, and the pool in the browser today
meshes **faces within a body**, which is the axis that actually divides this workload. A
body-per-worker scheduler would have looked obvious and bought half of what it promised.

**Packing is free and the payload is not.** `pack` is 1.5 ms and produces 2.49 MiB for an assembly
whose STEP file is 136 KiB — eighteen times the input, before it crosses anything. The large
assembly turns 14.55 MiB of STEP into 84 MiB of packed mesh against a 256 MiB buffer cap, so the
payload is the constraint and the packing is not.

## Bugs found by building, not by reading

**A `.w3d` weighs fifty-two times more if somebody looked at the document.** AS1 saves as 97 KiB
before anything is meshed and **4.95 MiB** after, from the same document with the same nodes and
the same geometry — and the save goes from 6 ms to 247 ms with it. OpenCASCADE attaches a
triangulation to the faces it meshes, its BREP writer writes whatever is attached, and the blobs
are the kernel's own bytes, which the format deliberately does not interpret. So `Document::mesh`,
which is documented as a *cache*, is persisted by a writer that never agreed to store it and a
format that does not mention it.

**What it buys back is not reliable, and that is the second half of the finding.** Reopening AS1's
warm file and meshing every body again takes **102 ms against 859 ms** — seven eighths of the first
draw, paid for with 4.85 MiB. Doing the same to the large assembly takes **33.4 s against 37.9 s**:
eighty-eight percent of the work happens anyway, for 190 MiB. Same kernel, same code path, same
quality, and the benefit ranges from most of it to almost none of it with nothing here explaining
which. So the cost is paid every time and the saving is a lottery, which is worse than either
answer would have been on its own. What is wrong with it is that nobody chose it:

- `FORMAT.md` specifies a geometry blob and says nothing about a mesh being inside one, so a second
  implementation written from that page would produce files a fifty-second the size and be
  conforming.
- **The quality the mesh was made at is not recorded beside it.** A document saved by a session at
  one `Quality` reopens carrying that tessellation, and nothing compares it to the quality the
  reopened document asks for. What `draw again` proves is that a mesh comes back fast, not that it
  is the mesh this document would have made. That is unexamined and it is the part to distrust.
- The cost is not linear in anything a user can see: it is paid per face meshed, so a document
  saved after a look at one part differs from the same document saved after a look at all of them.
- And on the evidence above, whether it buys anything back is not predictable from the document
  either. A trade whose benefit varies by a factor of seven between two files is not a trade
  anybody can reason about at the call site.

Left unfixed deliberately — see `Loose ends`.

| clippy, fmt | Clean over `w3d-kernel-occt`, which is what `make test-occt` lints — the example included, since it lints `--all-targets`. |

**Not verified, and the risk taken with each.**

- **One machine, one run, no repetition.** Nothing is averaged and no variance is known, so a ten
  percent difference between two runs of this harness means nothing and a tenth of a millisecond in
  its output implies a precision it does not have. What the numbers support is order of magnitude
  and *ratio between phases*, which is what they are used for above and is all they should be used
  for.
- **This machine is a container with no GPU**, and the numbers are OpenCASCADE native. The browser
  has no OCCT in it and models on `TruckKernel`, whose tessellation is a different algorithm at a
  different density — the register's note that truck's meshes are 2.5x denser is still the only
  thing known about that, and it is still unmeasured.
- **The peak RSS is a process high-water mark**, with OCCT's heap, the allocator's slack and the
  binary inside it. It is an upper bound on what a document costs and **not** the wasm32
  linear-memory figure the wasm64 argument in `AGENTS.md` asks for. It is the first real number
  anywhere near that ceiling, and it should be quoted as what it is.
- **The repetition grouping is a heuristic**, stated as one in the code and in the output. Equal
  triangle, vertex and line counts are evidence that two bodies are the same part; they are not
  proof, and the saving is an upper bound.
- **Nothing here asserts the large assembly imported *correctly*.** It is a workload. AS1 has a
  known arrangement and `assembly_tree` weighs it; the buggy has neither, and a wrong-but-plausible
  import would be measured happily.
- **The `draw again` row does not prove the reused mesh is the right mesh**, and on the large
  assembly it does not even show much reuse. Why the two files differ by a factor of seven here is
  **not known**, and guessing at it — deflection recorded per face, a tolerance comparison inside
  OCCT, faces whose triangulation is discarded on read — is exactly the kind of story that gets
  written down as a fact. It is a question, and it is the first one the format decision has to
  answer.
- **`make measure` is in no CI job**, deliberately: a threshold on a shared runner is a check that
  fails on a busy machine, and a check nobody trusts gets disabled. Which also means **nothing
  re-runs these numbers**. They are a snapshot of one commit on one machine, and the way they go
  stale is silently.
- **This container could not run `make test` as it stood.** `Cargo.lock` carries egui 0.36.1, whose
  floor is rustc 1.95, and the image had 1.94.1 — a resolver error before any code was compiled,
  unrelated to anything here and fixed for this session by `rustup update`. Worth knowing before
  somebody reads a red `make test` in a fresh container as a regression. The repository pins no
  toolchain file, so the floor is whatever the lockfile's dependencies say that day.

## Loose ends, deliberately left

- **The 52x is not fixed.** The two candidate fixes are `BRepTools::Clean` before writing — which
  gives back the small file and loses the fast reopen — and a mesh that the format stores *on
  purpose*, with the quality it was made at beside it, which is a `FORMAT.md` change and a version.
  Both are decisions about the format; neither belongs in the session that found the number.
- **Nothing is measured on `TruckKernel`**, which is the only kernel the browser has.
- **Nothing is measured on the threaded build**, so what the rayon pool buys is still an argument —
  though a narrower one now that one body is known to be half the work.
- **The import is not incremental and nothing streams.** A 15 MB file is read, walked and meshed
  before anything is drawn, and the harness measures that as one stall because that is what it is.
- **No allocation count, no per-phase memory.** Peak RSS is the whole process, so the cost of the
  mesh cache specifically — which is the thing most likely to be worth evicting — is not separated
  from OCCT's own copy of the geometry.
