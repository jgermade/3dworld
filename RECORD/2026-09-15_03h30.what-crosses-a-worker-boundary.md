# 2026-09-15 03h30 · What crosses a worker boundary

Takes **item 4** of [the register](./2026-08-25_21h59.what-is-not-built-yet.md) — "the tessellation
format across the worker boundary" — which is the item
[`what-an-assembly-costs`](./2026-09-14_21h34.what-an-assembly-costs.completed.md) named first in its `Next`,
and the one that measurement was owed to.

## Where this repo actually was

`STACK.md` has said since the first session that bulk work runs in a worker with its own linear
memory and that "exchange is by transferable `ArrayBuffer`, which is a move". That sentence was the
whole design. Nothing said what was *in* the buffer.

What did exist was a `PackedMesh` in `render/src/scene.rs`, with a doc comment describing it as
"designed for Transferable ArrayBuffer messaging between kernel worker threads and the main GPU
render thread". It is a `Vec<PackedVertex>` and three more `Vec`s. A `Vec` does not cross a worker
boundary — it is a pointer into a heap that does not exist on the other side — so what that comment
described was the *shape* of a payload and not a payload. Nothing serialised it, nothing parsed it,
and it had one caller: `make measure`, which used it to count bytes.

Beside it, three numbers from the day before, which are the only reason this item was ready to be
taken:

- a 14.55 MiB STEP assembly packs to **84 MiB** of vertices, against a 256 MiB device buffer cap;
- import and tessellation of it stall the calling thread for **56 seconds**;
- **one body was 45% of the entire tessellation**, so dividing the work by body has a floor at
  about half and the axis that pays is the face.

And one more thing was true and worth saying: `w3d-render` owned the packing, so anything that
wanted to pack a mesh had to link wgpu to do it. A worker that tessellates has no device.

## Walkthrough · as built

### `WIRE.md`, which is the deliverable

A specification, written the way `FORMAT.md` is: someone can write a second implementation from
that page without reading a line of this one. It opens by saying what it is *not* — a message
format inside one run of one program, not a file format — because the two have different
obligations and conflating them is how a wire format acquires a compatibility promise nobody
intended to make.

One buffer: a 64-byte header, then up to four sections. Every field little-endian at a fixed
offset, so a `DataView` can read the header — though nothing does, and the page says so: **both
ends are Rust**, and JavaScript's only job is `postMessage(buffer, [buffer])`. The alternative, a
JSON sidecar beside the buffer, is two descriptions of one payload, and two descriptions disagree.

The parts that are decisions rather than layout:

- **One buffer rather than four.** Four sections in four `ArrayBuffer`s are four entries in a
  transfer list and four chances for a consumer to hold three and wait forever for the fourth. One
  buffer makes the transfer atomic.
- **Sections are found by offset, never by walking in order.** The order is documented so a hexdump
  is readable, and a reader that relies on it breaks the first time one is omitted.
- **Every section offset is a multiple of 4**, which is what lets JavaScript build a typed-array
  view without copying. In practice no padding is ever inserted — 28, 4 and 12 are all multiples of
  4 — and a reader must still read the offsets rather than compute them.
- **`NO_INDICES` and `DEINDEXED` are two flags, not one.** The first is structural: is there an
  index section. The second is the diagnostic that says the mesh cost up to three times what it
  should, because a face id has to be a vertex attribute and a vertex shared between two faces
  cannot carry two. A merge produces the second without the first, which is the case that proves
  they are different facts.
- **An unknown flag bit is refused, not ignored.** A flag a reader ignores is a promise the
  producer thinks it has made.
- **An absent section is offset 0 and count 0, together.** Absence with two spellings is two code
  paths, of which one gets tested.
- **No checksum.** The risk on this channel is a wrong offset in a producer, which the O(1) header
  checks catch; it is not a flipped bit in transit, which a transferable buffer inside one process
  does not have. Every structural check is O(1) and read from the header.
- **Index range validation is O(n) and is not part of decoding.** It is a separate call, and the
  GPU upload path makes it — because the failure it prevents is a lost device three frames later,
  and the upload beside it is already a linear pass over the same bytes, so the check does not
  change what the upload costs in order.

### `wire/`, a new crate, and why it is one

`w3d-wire` depends on `w3d-kernel` and `bytemuck`. It does **not** depend on wgpu, and that is the
entire reason it is a crate rather than a module: the producer end of this boundary has no device,
and the browser's payload is already 4.25 MiB. `PackedVertex`, `PackedMesh`, `validate`, `expand`,
`per_vertex_faces` and `MeshError` moved here out of `render/src/scene.rs`, unchanged in behaviour;
`w3d-render` now depends on `w3d-wire` and re-exports every name that moved, so no caller changed.
`AGENTS.md`'s crate table and its rules both say so in the same commit, as that file requires.

A consequence worth noting because it went the right way: **`w3d-render` no longer uses `bytemuck`
at all** — every cast was in the code that left — so the dependency is gone from its manifest. The
crate is still in the tree under `w3d-wire`, so `NOTICE` is unchanged.

The layout is now declared once. `VERTEX_SIZE` is `w3d-wire`'s, `w3d-render`'s vertex buffer layout
is written against it, and a `const` assertion in each crate holds the `repr(C)` and the constant to
each other. A drifted stride would otherwise be found by a wrong-looking picture.

### Chunks, and the axis they divide on

`split_by_face` divides a body into at most *n* messages. Whole faces only, and the reason is not
parallelism: `face_of_triangle` is face identity — what a selection and a per-face fillet are stored
against — and a face renumbered independently in two chunks cannot be put back together by anything
downstream.

Faces are ordered by **where their first triangle appears**, not by face id, so that when a producer
emits a face's triangles contiguously — which both backends do — a split followed by a merge
preserves the triangle order exactly rather than permuting it. The partition is balanced by
*triangle count* rather than face count, greedily in face order, so the partition is a function of
the mesh alone.

`merge` puts chunks back **in the order they were numbered, never the order they arrived**. This is
`AGENTS.md`'s rule for a parallel tessellation, one level up: a result a machine is allowed to
disagree about is not a result. It refuses, by name, chunks that are incomplete, duplicated, from
two different bodies, or from two different requests.

Where chunks disagree about indexing, **the de-indexed chunk is promoted rather than the indexed
ones expanded**: giving a de-indexed chunk the indices `0, 1, 2, …` costs 4 bytes a vertex, and
expanding the others to match would cost 28 bytes a triangle corner. Unless *every* chunk is
de-indexed, in which case there is nothing to promote to and the merge has no index section either.

### The consumer end

`GpuMesh::from_wire` uploads the vertex section to the device **as it arrived** — no `Mesh`
rebuilt, no `PackedMesh` in between. That is what the format is for: 84 MiB behind one assembly,
and every intermediate copy of it is a copy on the thread that draws.

## Bugs found by building, not by reading

- **The chunk balancer left empty chunks in the middle.** Balancing by triangle load alone, a face
  carrying 40 of 45 triangles puts the *next* face in chunk 3 of 4 and leaves chunks 1 and 2 empty
  — and since slots are handed out in order, a chunk skipped is a chunk never filled. It needed a
  bound on each side: a floor so that enough faces remain for the chunks after this one, and a
  ceiling of one chunk further than the last face went. Found by the test asserting no chunk is
  empty, on a fixture shaped deliberately like the 45% body `make measure` found.
- **A test premise was wrong, and the truth is the more interesting half.** The test named
  "chunks that are all de-indexed merge without an index section" built its chunks by splitting a
  body whose two faces share a vertex — and the chunks came back *indexed*. De-indexing is caused
  by a vertex belonging to two **faces**; a chunk holds whole faces, so a split that separates them
  duplicates the shared vertex and removes the reason either chunk would have been expanded. See
  below: this is a finding, not a defect.

**Not verified, and the risk taken with each.**

- **No worker has ever run.** This is the important one. There is no `worker.js`, no second wasm
  entry point, and nothing in `web/` posts a message. What is verified is the *format* and both
  ends of it inside one process: the producer's bytes, the consumer's upload, and the picture. The
  claim "this survives a transferable `ArrayBuffer`" rests on the buffer being a plain byte array
  with no pointers in it, which is true by construction and is not the same as having been done.
- **`make wasm` passes and that is a type-check, not a build.** The target was added to this
  container and the whole workspace — the new crate included — checks for
  `wasm32-unknown-unknown`, and the `glow` grep that guards the WebGL2 fallback still finds it.
  What did *not* run is `make web`, which needs `wasm-bindgen` installed, or `make web-threaded`,
  which needs nightly and a `std` rebuild. Nothing in `web/` calls into this crate yet, so the
  browser payload is unchanged by construction and unmeasured in fact.
- **Nothing is measured.** Not one number in this session is a measurement. The 84 MiB, the 56
  seconds and the 45% are quoted from `make measure` on 2026-09-14 and are the *inputs* to the
  design. What encoding costs, what decoding costs, what a chunk count does to either — all
  unmeasured. `make measure` needs OpenCASCADE, which is not installed in this container, so
  extending it was not possible without writing code that could not be compiled here.
- **The header's cost is arithmetic, not a measurement.** 64 bytes a message. Eighteen bodies at
  eight chunks each is 144 messages, 9 KiB against 84 MiB — which is a division, stated as one.
- **The chunk count is a parameter and nothing chooses it.** `split_by_face` takes `want`. What a
  good value is, how it depends on the pool size, the body, or the device's buffer cap, is not
  known and nothing here suggests one.
- **`tag` is a correlation value with no policy attached**, deliberately — staleness is a
  scheduler's decision and a policy in a format cannot be changed without a version. So nothing
  here *implements* the rejection of a stale answer. It only makes it possible.
- **The de-indexing saving is measured on a fixture**, two triangle fans sharing one rim vertex,
  not on a real body from a real backend. It is a real property with a made-up magnitude.
- **The pixel-identity test ran on a CPU rasteriser.** lavapipe agreeing is strong evidence about
  the primitive stream and no evidence at all about a driver, which is item 5 of the register and
  is not touched here.
- **`make test-occt` was not run**, for the same reason `make measure` was not: no OCCT. The one
  crate outside the default members that uses a moved name — `kernel-occt/examples/assembly_cost.rs`,
  through `w3d_render::scene::PackedMesh` — still resolves, because `render` re-exports it, but
  that is a reading of the re-export rather than a compile.
- **The toolchain floor moved again.** The lockfile needed rustc ≥ 1.95 and this container had
  1.94.1; `rustup update` brought 1.98.1 and everything below was built and run on that. The
  repository still pins no toolchain file, so the floor is whatever the lockfile's dependencies say
  that day, and a fresh container is red before any code is compiled.

## Loose ends, deliberately left

- **The worker itself.** The format is the half that had to be designed; the half that remains is
  a wasm entry point that tessellates and posts, a `worker.js` to own it, and a loader change to
  start it. That is where the 56-second stall actually moves off the thread that draws, and it is
  now unblocked.
- **`make measure` should grow `encode` and `decode` phases** beside `pack`, and a chunk-count
  sweep. It is four lines beside the existing `pack` row and it needs a container with OCCT.
- **Nothing chooses a chunk count**, per above.
- **A second implementation of `WIRE.md` has not been written**, so the claim that the page is
  sufficient to implement from is a claim about the page made by the person who wrote it. The
  header test is the closest thing to a check on it.
- **`line_positions` go wholly into chunk 0.** It is deterministic and documented, and it is also
  an imbalance: chunk 0 carries the whole wireframe on top of its share of the faces.
- **16-bit indices are not taken, and the first draft of `WIRE.md` dismissed them with wrong
  arithmetic.** It said the index section is "at most a seventh of the vertex section", which is
  the per-*element* ratio read as if it were the per-mesh one. A closed triangle mesh has about
  twice as many triangles as vertices, so its indices are `3 × 2V × 4 = 24V` bytes against the
  vertices' `28V` — six sevenths, and halving them would take something like 12% off a message.
  The paragraph now says so and says the decision waits on a measurement. Worth recording because
  the wrong version read perfectly well.
- **Nothing streams.** A chunk can be uploaded before its siblings arrive — the indices are
  chunk-local precisely so it can — but nothing does that yet. `merge` waits for all of them.

## Extension · 2026-09-15 · The worker exists, and the boundary has been crossed

The section above closes with "**No worker has ever run.** This is the important one." It has now
run, in Chromium, and this extension is what that changed. The paragraphs above stand as they were
written — they were true of the commit they describe.

### Where this repo actually was, an hour later

The format and both ends of it, merged. What was missing was the thing that makes the boundary a
boundary. The container had no wasm toolchain when the section above was written; it has one now —
`wasm32-unknown-unknown`, `wasm-bindgen-cli` 0.2.127 pinned to the lockfile's version, Node 22,
Playwright and the Chromium at `/opt/pw-browsers`, and lavapipe for the native headless tests. None
of that is a repository change; it is why the claims below are checks rather than arguments.

### Walkthrough · as built

**`tessellateScene(chunksPerBody)` in `w3d-web`, and it is a free function.** A `Viewer` owns a
wgpu surface and a worker has no canvas to put one on, so the producer cannot be a method on it.
What the producer touches is `w3d-core`, `w3d-kernel-truck` and `w3d-wire`, none of which knows a
GPU exists. It returns the chunks **and three separate timings** — modelling, meshing, encoding —
for the reason `make measure` gives at the other end of this repository: they fail differently, and
one wall-clock number would have been uncomparable with the page's own `tessellateMs`, which covers
the mesh loop alone. The first version returned one number and it was 1273 ms against the main
thread's 718 ms, which reads as overhead and is not: it was the boolean and the encoding included.

**`web/worker.js`.** A module worker that loads `./dist/w3d_web.js` — the **single-threaded**
variant, deliberately. The threaded build imports a shared memory, and sharing one is the opposite
of what `STACK.md` means by a worker with its own 4 GB. So this is a second instantiation of the
same module with a linear memory of its own, which is the architecture that page describes, running
for the first time.

It copies each chunk out of the wasm memory into a buffer of its own before posting. That is not an
oversight: `tessellateScene` hands back `Uint8Array`s that are *views into the module's linear
memory*, and posting their `.buffer` would offer the engine the whole wasm heap — refused by
Chromium, and on an engine that allowed it, it would detach the memory the worker is still running
in. The comment in the file says so, because the wrong version is the shorter one.

**`Viewer::replaceWithWire(chunks)`.** Groups the arrived chunks by the node id in their own
headers, merges each group by chunk number, and uploads with `GpuMesh::from_wire`. Arrival order
cannot change the result and does not need to be preserved by the caller.

**One copy happens on the way in, and it is not the transfer.** The transfer is free — the buffers
are moved. What costs is getting the bytes from a JS `ArrayBuffer` into the consuming module's
linear memory, which `Uint8Array::to_vec` does. Avoiding it needs a pointer exported from wasm and
written through from JS, which needs `unsafe`, which this workspace forbids outside the FFI crate.
That is a rule buying a memcpy per chunk, knowingly, against a tessellation measured in seconds.

**A fifth run in `web/test/browser.mjs`.**

### The numbers, measured in a browser

One scene, one machine, headless Chromium on a CPU rasteriser. Facts, not targets.

| Phase | ms |
| --- | ---: |
| Instantiating a second wasm module in the worker | 55 |
| Modelling — `scene()`, which is a boolean on `TruckKernel` | 551 |
| Meshing, in the worker | 728 |
| Meshing the same scene on the main thread, for comparison | 730 |
| **Encoding** — split by face into 4 chunks and encode all of them | **6** |

Two of those are worth saying out loud. **The worker meshes at the same speed as the main thread**
— 728 against 730 — which is what says the second instance is doing the work rather than being
starved. And **encoding costs 0.8% of meshing**: 6 ms against 728, for 178 KiB in four chunks. The
question "what does this format cost" now has a number on the platform it is a claim about, which
is more than `make measure` can say, because `make measure` has no browser in it.

The payload grew from **4.25 MiB to 4.29 MiB** — about 40 KiB for `w3d-wire` and the two entry
points, against item 7's standing complaint about payload.

### Bugs found by building, not by reading

- **The first worker posted the wrong buffers.** Posting a wasm view's `.buffer` offers the engine
  the entire linear memory. Chromium refuses it; the failure mode on an engine that did not would
  be a worker that detaches the heap it is running in. Fixed by copying each chunk out first, which
  is the copy the comment in that file now explains.
- **A `postMessage` with a wrong transfer list still delivers, by copying, and the receiving side
  cannot tell.** Every byte arrives, the counts match, nothing throws — and 84 MiB was cloned. The
  only place the difference is observable is the *sender*, after the post: a transferred
  `ArrayBuffer` is detached and its `byteLength` is 0. So the worker sends a second message with
  that verdict in it, and the test asserts on it. A boundary that silently copies is exactly the
  failure this design exists to prevent, and nothing else in the stack would have said a word.

### Verified, and not · the extension

**Verified**, all in `web/test/browser.mjs`, run against Chromium:

| What | How |
| --- | --- |
| A tessellation crossed a heap | A second wasm instantiation with its own linear memory produced 4 chunks and 178 KiB, and the page rebuilt its bodies from them. |
| Every byte arrived | 182 788 sent, 182 788 received. |
| The transfer was a **move** | The worker's own buffers are detached after the post. This is the check that cannot be made from the receiving end. |
| The mesh survived the round trip | 6290 triangles before, 6290 after — the same triangles, by a completely different route — and the canvas still shows 92 distinct colours. |
| The format is cheap | Encoding asserted to cost no more than meshing; it costs 0.8% of it. An inversion here would mean the format got expensive and nothing else would notice. |
| Nothing else regressed | All five browser runs pass; `make wasm`, `make test`, clippy and fmt are green. |

**Not verified, and the risk taken with each.**

- **The page still tessellates on the main thread at startup.** `start()` meshes the scene for
  itself, and the worker path is a method a caller invokes afterwards. That is deliberate — the
  scene the main thread made is the only thing there is to compare the worker's result *against*,
  and the comparison is the test — but it means **the 56-second stall is not removed**, only shown
  to be removable. Making the worker the boot path is a new register item rather than this one.
- **The worker builds the scene itself rather than being sent one.** The page's scene is a fixed
  document, so both sides can construct it. Sending a *document* across needs the document to be
  serialisable across the same boundary, which is a second format and a later problem.
- **One body, four chunks, 178 KiB.** Two orders of magnitude below the 84 MiB the design is for.
  Nothing here says what happens at that size, and the one thing that would — a wasm OCCT, item 3 —
  does not exist.
- **`chunksPerBody` is 4 because it is a number.** Still nothing measures what it should be.
- **Headless Chromium on a CPU rasteriser, one browser, one machine.** No Firefox, no Safari, and
  the timings say nothing about hardware.
- **The threaded variant was not built or tested with this**, because it needs nightly and a `std`
  rebuild. The worker deliberately loads the single-threaded module, so what a pool does *inside* a
  worker is untouched and unknown.
- **Nothing is measured about memory.** The claim in `STACK.md` that this is what gets past the
  4 GB ceiling rests on two heaps existing, which is now true, and on neither of them having been
  filled, which nobody has tried.

### Correction · 2026-09-15 · CI ran what this container could not

Two caveats above were about this container's missing pieces rather than about the work, and CI
settled both. The original text stands — it was true of the machine it was written on, and the
distinction between "nobody has run this" and "the runner ran it" is the kind that gets lost when a
record is tidied.

**`make test-occt` ran, and green**, on [#13](https://github.com/jgermade/3dworld/pull/13), for
both commits. So the sentence in `Verified, and not` — that
`kernel-occt/examples/assembly_cost.rs` compiling against the moved `PackedMesh` was "a reading of
the re-export rather than a compile" — is superseded: it is a compile now, against real
OpenCASCADE, and the example that `make measure` runs still builds after the packing changed crate.
`make step-check` and the FreeCAD job are green beside it, which says nothing about this work and
is worth knowing anyway: nothing in the format or the STEP path moved under each other.

**`make app-test + app-test-step` is green too**, which is the desktop shell drawing in a real X11
window under Xvfb through the same `GpuMesh::upload` path the packing moved out from under. The
headless tests in this container had covered it on lavapipe; this covers the program.

Still not run anywhere: **`make measure`**, which needs OCCT *and* the STEP samples, and
**`make web-test`**, which is not in any CI job — so the five browser runs, the worker boundary
among them, are checked on the machine this was written on and nowhere else. That is unchanged by
this correction and is the one that goes stale silently.
