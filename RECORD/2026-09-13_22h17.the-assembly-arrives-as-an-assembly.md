## Where this repo actually was

The register had read the code on 2026-09-05 and found two thirds of the old item 2 already
landed: `w3d_occt.cpp` ran `STEPCAFControl_Reader` with XDE and read each label's
`TDataStd_Name`, so **product names arrived**; and the document had grown a tree it could hold —
`Node::parent`, `Node::children`, `add_group`, `reparent`, `children_of`. What was missing was the
wire between them. The register's number for it was that the AS1 assembly from Pro/ENGINEER holds
five distinct solids and imported as **eighteen sibling bodies**, and the work it described was
narrow: a parent on `ImportedBody`, the indices to fill it, and `Document::import` building the
tree.

The number was wrong, and finding that out was the first thing this session did. AS1 imported as
**thirty-six** bodies, not eighteen — with 320 faces where the file has 160 — and eighteen of them
were called `AS1_PE_ASM` after the root product. The register had counted the placements in the
file, reasonably, and nobody had counted what came out.

## Walkthrough · as built

**The seam carries a tree.** `import_step` returns `Import { bodies, assemblies }` in place of
`Vec<ImportedBody>`. Two lists rather than one, because an assembly node has a name and a place
and no solid: an `ImportedBody` for one would be a body that does not exist. `ImportedBody::parent`
and `ImportedAssembly::parent` are indices into `assemblies`, or `None` at the file's root.

`Import::validate` is the whole of the structural contract — every index in range, and every
assembly's parent *earlier in the list than itself*. The second half is what makes a cycle
unrepresentable rather than merely detectable, so a caller may walk parents without a visited set
and know it terminates; it is also what lets `Document::import_step` build the tree in one pass,
because a parent's `NodeId` always exists by the time a child needs it. It is called on both sides
of the FFI boundary and by the conformance suite on everything it imports, and it has four negative
controls in `kernel/src/lib.rs`.

A backend that reads a flat file, or whose reader cannot see a tree, answers with no assemblies and
`None` parents. That is conforming and is what `OcctKernel` does for a file this program wrote.

**The XDE walk was rewritten.** `extract_label` took the solids of every label it met and then
recursed into that label's components. An assembly's label holds a compound of its whole subtree,
so every solid was emitted again for each ancestor above it. And it recursed with `GetComponents`
on a *component*, which is a reference and has no components of its own — the structure lives on
the label it refers to — so the walk stopped one level down and the names of the parts themselves
never left the file.

The new walk follows a reference with `GetReferredShape`, emits an assembly entry where the tree
has structure and a body where it has a part, and carries a `TopLoc_Location` down so that a part's
global placement is the product of every location above it. The old walk got that for free by
reading solids out of the root compound, where OCCT had already applied them.

**`holds_structure` is the judgement the walk needs, and the one XDE does not make.** Pro/ENGINEER
writes every part in AS1 as a product holding two shape representations, a `SOLID` and a
`COMPOUND`, and XDE marks that product as an assembly. Taken at face value it puts a group around
every single part: the first run of the rewritten walk produced **28 assemblies** for a file with
ten, and named each part's body `=>[0:1:1:11]` — which is XDE's name for an instance label the file
left unnamed, not a name at all. The rule that separates them is that a file *names* the components
of a real assembly and leaves the representations of one product unnamed. `label_name` now refuses
the `=>[…]` names outright, and a label holds structure when at least one component keeps a name
after that.

**The document builds the tree, undoably.** `Document::import_step` creates a group node per
assembly, parents each body under its assembly, and returns the body nodes — they are what a user
selects, and `parent_of` reaches the groups. `insert_child` inserts a node already linked to its
parent and records the parent's side of the link as a `Replace` of the parent against itself, so
undoing an import leaves no group holding a child id that has been removed, and redoing one
restores the children lists rather than a set of nodes that look right in the document and empty in
the Outliner.

**`GROUP_BODY`.** A group used to carry `Body::from_raw(0)`, and `0` is the first id every backend
here hands out — `OcctKernel`'s counter starts there. So a group carried the handle of the *first
body in the document*. With ten groups arriving from an assembly that is ten phantom copies of
whatever that body is: drawn, measured by `visible_bounds`, and kept alive by `collect_garbage`
forever. It is `u32::MAX` now, with `Node::is_group()` beside it, and the three places that walk
every node and ask the kernel about each body filter on it.

**`reparent` refuses a cycle, and records history.** Both became reachable from the mouse when the
Outliner learned to draw a tree. The cycle check walks up from the new parent: refusing only
`child == parent` left the two-step version — drag A onto B, then B onto A — which produces a ring
of nodes that never reaches the root, and a walk down from the roots that never terminates. The
history was the last editing operation outside undo: a part dragged into the wrong group stayed
there and Ctrl-Z reversed whatever the user had done *before* the drag, which is worse than nothing
happening.

**The Outliner draws the tree.** It drew the arena in insertion order and marked a node that had a
parent with one fixed indent, which reads as a tree exactly while a tree is one level deep. An
imported assembly is three: a nut inside a nut-and-bolt inside a bracket sat level with the
bracket. `Editor::outline_rows` walks depth first from the roots and returns a depth per row;
`shell.rs` indents by it. The walk is in the editor rather than the panel because that is the half
that can be tested.

**`examples/assembly_tree.rs`**, run by `make step-check`: the AS1 tree weighed against what the
file contains, rather than against what the program produced.

## Bugs found by building, not by reading

- **Every solid was emitted once per ancestor assembly.** 36 bodies for 18 placements, 320 faces
  for 160. Eighteen of them named after the root product, which is how it went unnoticed: the
  names looked like product names, and were.
- **The walk never followed a reference**, so `L_BRACKET`, `NUT` and `BOLT` — the names a user
  looks for — never left the file, and no structure below the first level was visible.
- **XDE's placeholder names reached the document.** `=>[0:1:1:11]` is a debugging aid; it would
  have been a node title in the Outliner.
- **A product's shape representations look exactly like a subassembly** through
  `IsAssembly`/`GetComponents`, and taking them for one inflated a ten-assembly file to 28.
- **A group node aliased body 0.** Latent since groups existed, certain from the moment an import
  makes ten of them.
- **`reparent` could make a node its own ancestor**, in two steps, and nothing downstream survives
  that.
- **`reparent` recorded nothing in history.**
- **`format::save` asked the kernel to save a group's body.** With the old `0` it wrote the first
  body's geometry a second time under the group's name; with an honest sentinel it would refuse the
  whole document. Groups are skipped now — see `Loose ends`.
- **A placement invariant that is not one.** The first draft of `assembly_tree` required two
  placements of a part to have the same bounding box, and the two nuts on the rod are
  76.2 x 381 x 508 where the six on the bolts are 381 x 76.2 x 508: the rod runs along x and its
  nuts are turned a quarter turn. A box is not invariant under rotation. The check compares
  enclosed volume instead.

## Verified, and not

**Verified.**

- `make test`, `make test-occt` (tests and clippy), `make step-check`, `make app-test` and
  `make app-test-step` all pass, on rustc 1.98.1 and OCCT 7.6.3 from Ubuntu Noble.
- **AS1**: `make step-check` asserts five distinct part names placed eighteen times, ten
  assemblies, a deepest solid three assemblies down, exactly one root, no solid outside the
  assembly, no two placements of one part sharing a centre, and every placement of one part
  enclosing the same volume to within a tenth of a percent. Run against the *wrong* file it
  produces six separate failures, which is how it was checked for saying yes for a living.
- **A flat file stays flat**: `every_solid_in_a_file_becomes_a_body` in `kernel-occt/tests/step.rs`
  now also requires no assemblies and no parents from a file this kernel wrote.
- **The contract**: `Import::validate`'s four negative controls; and a new conformance check —
  "two solids in one file come back as two, in a tree that holds together" — which matches the
  imported solids to the exported ones *by size* and rejects the same solid arriving twice, which
  is the failure a count cannot see. It runs against every backend that does STEP.
- **The document**: three tests over a stub kernel that answers with a tree — the tree is built,
  one undo takes the groups with it and redo puts the children lists back, and a tree that is not
  one is refused with nothing landing and nothing to undo. The redo test was confirmed to fail when
  the parent-side `Replace` is removed.
- **Undo of a move**, the cycle refusal, and the Outliner walk each have a test.

**Not verified, and the risk taken.**

- **`holds_structure` is a judgement about how STEP is written, not a rule STEP states.** It is
  right on the one multi-level assembly in `samples/`, and wrong on a file whose assembly
  components are *entirely* unnamed: that assembly collapses into one node. Every solid under it
  still arrives, still in the right place, and there was no name in the file to label the level
  with — but it is a heuristic, exercised against one writer's output.
- **One file, one writer.** AS1 is Pro/ENGINEER AP203. Nothing here has read a multi-level assembly
  from NX, from SolidWorks, or in AP242, and the register's item 1 still stands: no second
  *geometry* kernel has opened what this one writes.
- **The placements are checked against each other, not against the file.** Two placements of a part
  are asserted to differ and to enclose the same volume; nothing asserts that a particular bolt is
  at the coordinate the STEP file says. That would need numbers read out of the file by something
  that is not OCCT.
- **Instancing is not represented, deliberately.** Eighteen placements of five parts are eighteen
  independent bodies with eighteen tessellations: the tree says how they are arranged, not that any
  two of them are the same thing. A `Body` is what the seam deals in and an instance of one is not
  a thing the contract has. It is also what a large assembly costs, and nothing has measured that
  cost — the 15 MB sample beside AS1 is still unopened here.
- **The colours and materials that the register said "arrive by the same road" did not travel it.**
  `SetColorMode(true)` has always been set and nothing reads a colour.
- **Nothing measures the import's cost.** 18 bodies and 51,920 triangles arrive on the thread that
  asked, synchronously, as they did before.

## Loose ends, deliberately left

- **A tree does not survive a save.** A version-1 `.w3d` has a flat `nodes[]` with nowhere to say
  what is inside what, and a group node is not written at all — it has no geometry, and an entry
  without geometry is not something a version-1 reader can read. So an imported assembly saves as
  its parts, flat. Putting the tree in a file needs a node identity a parent can refer to, which is
  the same version-2 conversation as units; `FORMAT.md` now says so, and
  `a_group_does_not_survive_a_save` in `format/tests/roundtrip.rs` pins it so that changing it is a
  deliberate act with a version number attached. Cost: the manifest work, plus the version rule.
- **An empty assembly arrives as an empty group.** A subassembly with no solids under it becomes a
  group node with no children. No sample has one, so pruning them would be code with no fixture
  behind it.
- **A product with both real subassemblies and its own representations** would put its unnamed
  representation leaves in as bodies with no name, falling back to `<file> N`. No sample has one.
- **`Document::import_step` still returns only the body nodes.** A caller that wants to select or
  frame the assembly it just imported has to find the groups through `parent_of`.
- **The app's status line still counts bodies** — "imported 18 bodies" — and says nothing about the
  ten groups beside them.
