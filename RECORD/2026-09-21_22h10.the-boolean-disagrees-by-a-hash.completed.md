# 2026-09-21 22h10 · The boolean disagrees by a hash, not by a float

Takes register **item 4** — *"One boolean, two architectures, two different
solids"* — and answers the question it was deliberately written as. The item
had a number and a suspicion; it now has a cause, a proof, and a demonstrated
fix, and the suspicion was wrong.

The item's own words were:

> `truck-shapeops` divides an intersection curve into a polyline at a sag
> tolerance, so a float difference of an ulp plausibly moves a segment count —
> but nothing has looked, and *plausibly* is the whole of what is known.

Nothing about that is true except the last clause. **No floating-point
operation differs between the two architectures anywhere in this path.** The
divergence is an iteration order, and the pointer width is what changes it.

## Where this repo actually was

Since 2026-09-15 the browser boots on a document: `make web-scene` cuts the
plate natively and writes `web/scene.w3d`, and the page loads it. The same
scene compiled into `w3d-web` is cut in wasm32. The two meshes were measured at
**6294** and **6290** triangles, and the drift check between the two copies of
the demo scene was written to a 1% tolerance *because of it* — equality was not
available.

Three record files closed earlier today left the register as the only open file
in `RECORD/`, and this is the first body of work opened against it since.

## Walkthrough · as built

Nothing landed in the tree. What was built is a harness, outside it, and the
method is the part worth keeping.

**One program, two architectures, aligned by index.** A crate with a `lib.rs`
that computes a list of `(name, f64)`, a `main.rs` that prints it, and a
`cdylib` that exposes `prepare()` / `value(i)` to a host. The wasm side is
**not** wasm-bindgen: it is `wasm32-unknown-unknown` instantiated by ten lines
of node, with every import stubbed by a function that *throws*, so a probe that
quietly called into JS would void its own run rather than return a number
nobody could trust. Nothing threw.

**Bit patterns, not values.** Every number is compared as `to_bits()` — `{:016x}`
on one side, a `DataView` on the other. A probe that compares `4.71480120534`
to `4.71480120534` is a probe that cannot see this bug.

**The operands, in `f64` and not through a mesh.** `Mesh.positions` is `f32`, so
"the tessellations agree" is a claim `f32` cannot carry — a 1e-14 difference
vanishes into it. So the probe also reconstructs both solids with `truck`'s own
builder, exactly as `TruckKernel` does, and hashes `solid.triangulation(tol)`'s
`f64` vertices directly. That is what the boolean actually consumes:
`process_one_pair_of_shells` triangulates both shells *first* and finds the
intersection from the polygons.

**Interposition, to rule out the library.** `f64::cos` on x86-64-linux lowers to
a call to the C symbol `cos`. A definition of that symbol **in the executable**
wins over glibc's, for every call in the program — so the native build was made
to compute what the wasm build computes by defining `cos`, `sin`, `tan`, `exp`,
`acos`, `asin`, `atan`, `atan2`, `pow`, `hypot`, `fma` and `sincos` over the
`libm` crate, which is what `wasm32-unknown-unknown` links. No patch to
`truck`, `cgmath` or anything else. `sincos` is in that list on purpose: it is
the one asymmetry that is not an implementation difference but a *shape* one —
`f64::sin_cos` is one call on x86-64 and two on wasm32.

**Then a vendored `truck`, instrumented.** The nine `truck` crates copied out of
the registry cache and wired in with `[patch.crates-io]`, carrying a
`pub mod trace` and a hash of the intermediate state at each stage of
`truck_shapeops::and`. The baseline was re-measured first: the vendored,
un-modified build gives the same 6294.

## The measurements

The demo scene: a 40x40x10 plate minus a ø12x20 drill at x = 8, at the
tolerance `Document` hands the boolean — `max(1e-7, 40 * 1e-3)` = **0.04**.

**Stage by stage, x86-64 against wasm32:**

| Stage | Native | wasm32 | |
| --- | ---: | ---: | --- |
| plate, drill as `save_body` JSON | *hash* | *same hash* | same |
| `solid.triangulation(0.04)`, `f64` vertices | *hash* | *same hash* | same |
| `triangulation` at 0.02, 0.01, 0.005 | *hash* | *same hash* | same |
| `poly_shell0` / `poly_shell1` inside `and` | 24 / 873 verts | same | same |
| `extract_interference`, the segment list | 39, 70, 38, 69, 39, 68 | same | **same, and in the same order** |
| `construct_polylines`, points | 26, 26, 25, 26, 26, 25 | same counts | **different values** |
| `construct_polylines`, points *sorted* | *hash* | *same hash* | same |
| the loops store after `create_loops_stores` | 36 / 42 verts | same counts | different values |
| the cut solid | 9 faces, 42 edges, 42 vertices | same | same |
| the cut solid's numbers | 1353 | 1353 | **44 differ** |
| the cut, tessellated | **6294** tris | **6290** tris | differ |

**The first divergence is `construct_polylines`, and its input is identical.**
The segments going in are the same segments in the same order; the polyline
coming out has the same points in a different rotation. Printed rather than
inferred — the first point of the same loop:

| | x | y | z |
| --- | ---: | ---: | ---: |
| x86-64 | 5.000000000020702 | 5.196152422718583 | −5 |
| wasm32 | 14 | 7.967771854008938e−12 | −5 |

Four of the six non-empty intersection loops start somewhere else on wasm32;
two start in the same place, by luck.

**What the difference is worth, geometrically:** the largest disagreement
between the two solids, over all 1353 numbers, is **1.24e-14 mm** — a relative
3.7e-14. The shape is the same shape. The visible consequence is four triangles,
because a curve whose parameterization starts elsewhere is divided into a
different number of spans.

**The cause.** `construct_polylines` builds a graph of the segments in an
`FxHashMap<PointIndex, Node>` whose nodes hold an `FxHashSet<PointIndex>`, and
then:

```rust
fn get_one(&self) -> (PointIndex, &Node) { self.iter().next().unwrap() }
fn pop_one_adjacency(&mut self) -> PointIndex { *self.adjacency.iter().next().unwrap() }
```

Where the polyline starts, and which way it goes, is *the first thing the
iterator yields* — a bucket order. And `rustc-hash`'s multiplier is declared
like this:

```rust
#[cfg(target_pointer_width = "64")] const K: usize = 0xf1357aea2e62a9c5;
#[cfg(target_pointer_width = "32")] const K: usize = 0x93d765dd;
```

`PointIndex` is `[i64; 3]`. On a 32-bit target each `i64` is hashed as two
32-bit halves against a different constant, so the bucket order is a property of
**the target's pointer width**.

**The fix, demonstrated.** Replacing those two containers with `BTreeMap` and
`BTreeSet` over the same `PointIndex` — a total order on `[i64; 3]`, the same
everywhere — makes the two architectures agree exactly: every polyline starts at
the same point, and the cut meshes to **6292 triangles on both**, with identical
positions. Two lines and a derive, upstream.

Note the number: **6292, which is neither 6294 nor 6290.** The ordered map picks
a third starting vertex. Agreeing and being right are different properties, and
nothing here establishes the second.

## Bugs found by building, not by reading

- **`TruckKernel::save_body` is not byte-stable across runs.** The same document
  saved in two processes gives two different files: same length, same numbers,
  **different vertex order**. Two saves *inside* one process are identical, and
  the geometry is identical across runs — measured over ten. The order comes
  from a pointer-keyed, randomly-seeded `HashMap` in `truck-topology`; wasm32 is
  stable only because its addresses are deterministic. The register has an item
  about `.w3d` blobs not being byte-stable across a *reopen*, on the OCCT side,
  which says explicitly that "two saves of one document are identical". That
  claim is true of OpenCASCADE and **false of `truck`**, in a way no test here
  asks about.
- **The first probe compared a hash of the saved JSON and was worthless**, for
  exactly that reason: it varied run to run, and it had already produced one
  confident wrong reading — that overriding libm "changed the geometry" — before
  the run-to-run check caught it. The measurement that replaced it compares the
  *multiset of numbers*, which is invariant to the ordering and sensitive to
  every digit.
- **`f32` hides this class of bug completely.** The probe's first pass reported
  "tessellation agrees on both architectures at four tolerances", which is true
  and means nothing: `Mesh.positions` is `f32`, and the differences are at 1e-14.

## Verified, and not

**Verified.**

| What | How |
| --- | --- |
| The number in item 4 is real and reproduces | 6294 native, 6290 in wasm32, from one source built twice |
| It is deterministic within each architecture | Ten native runs, two wasm runs: identical geometry every time |
| The operands are bit-identical | `save_body` JSON and `f64` `triangulation()` at 0.04, 0.02, 0.01, 0.005 |
| The mesh the boolean consumes is bit-identical | `poly_shell0/1` hashed *inside* `and` |
| It is not the math library | Every libm symbol the path can reach, `sincos` included, replaced natively by the `libm` crate wasm links — and the battery of 130 probes flipped to the wasm values while the cut did not move at all |
| It is not the optimizer | A debug build and an LTO release build give identical geometry natively |
| It is not the segment extraction | `extract_interference` returns the same segments in the same order on both |
| It **is** the polyline's starting point | Same points sorted, different in sequence, first point printed for each |
| The mechanism is `usize` width | `rustc-hash`'s `K` is declared per `target_pointer_width`, and the two containers are read through `.iter().next()` |
| An ordered map fixes it | `BTreeMap`/`BTreeSet` over the same key: 6292 on both, identical mesh hash |
| The geometric size of the disagreement | 1.24e-14 mm, worst of 1353 numbers |

**Not verified, and the risk taken with each.**

- **None of this is in the tree, and nothing re-checks it.** The harness is a
  scratch crate with a vendored, hand-instrumented `truck` behind it. The claim
  "these two builds disagree" is today a measurement in a record file, not a
  check that fails when it changes — and it is exactly the kind of claim that
  rots. What it would cost is under `Loose ends`.
- **One scene, one pair of solids, one tolerance.** A plate and a cylinder, cut
  at 0.04. The mechanism is general — any boolean whose intersection loop is
  chained through that graph — but the only *evidence* is this cut. Nothing was
  run on the four degenerate fixtures, on the off-axis plate, or on an assembly.
- **`BTreeMap` is shown to make two architectures agree; it is not shown to be
  correct.** It changes the answer on both (6292), it was measured on this one
  cut, and it was not run against the conformance suite — which is where a
  change to a boolean has to be argued, and which cannot run against a vendored
  patch anyway.
- **The 32-bit half of the mechanism is inferred from the constant, not run.**
  `rustc-hash`'s two `K`s were read in the source and the wasm32 behaviour
  matches what they predict; no 32-bit *native* target was built to confirm that
  a 32-bit ARM desktop build diverges the same way. It is the same `cfg`, so the
  prediction is strong, and it is still a prediction.
- **`f64::sin_cos` was ruled out by interposition, not by tracing.** The
  `sincos` override is a `#[no_mangle] extern "C"` definition; that it actually
  displaced glibc's was confirmed only indirectly, by the whole battery moving
  to the wasm values.
- **Nothing was measured in a browser.** Node's V8 and Chromium's V8 are the
  same engine but not the same build, and this says nothing about the page.
- **Nothing here touched `make test`, `make web-test` or CI.** No code changed,
  so nothing could regress — which is also why nothing was run.

## Loose ends, deliberately left

- **The finding is not a fix, and the fix is upstream.** `truck-shapeops` is a
  crates.io dependency; the change is two lines and a derive in
  `polyline_construction`. The routes are: carry a patched fork, pin a
  `[patch.crates-io]` in the workspace, or report it upstream. Each is a
  decision about a dependency rather than a defect with one answer, and none of
  them is this session's to take unilaterally.
- **A check that would fail today cannot land.** The obvious artifact — a `make`
  target that builds the same measurement for both targets and requires them to
  agree — asserts something that is *false* in this tree until the dependency
  moves. What can land now is the weaker, true claim: that each build is
  deterministic in itself, and that the operands and the interference segments
  agree across the two. That is worth having and is not free: it needs the probe
  crate, `wasm32-unknown-unknown` in CI, and a node harness.
- **`save_body`'s ordering was found, not fixed.** Sorting the topology on the
  way out would make a `.w3d` byte-stable across runs on `truck`, which is what
  the format's own reproducibility claim assumes. It is a change to a kernel's
  blob writer, and it belongs with the item the register already carries about
  blob stability rather than bolted onto this.

## Walkthrough · as completed

Closed the same day it opened. It changed no code and that is the whole of what
it is: a question the register had been carrying since 2026-09-15, answered, and
answered against the guess the register itself had written down.

What stands: **the two builds disagree for a reason that has nothing to do with
floating point.** The operands are bit-identical, the polygons the boolean
consumes are bit-identical, the intersection segments come out identical and in
the same order — and then the polyline chained from them starts at a different
vertex, because the graph it is chained through is an `FxHashMap` and
`rustc-hash` multiplies by a different constant when `usize` is 32 bits wide.
Everything downstream — a curve parameterized from elsewhere, a refinement that
converges 1e-14 away, four triangles — follows from that one choice of where to
start. Replacing the two containers with ordered ones makes both architectures
agree, on a third answer.

Two things it leaves standing, and both are in the register as of today: the
dependency decision, which is what would actually close the gap between the
desktop and the browser, and `TruckKernel::save_body`'s vertex order, which it
found on the way past and which makes a `.w3d` differ from run to run on the
one backend the browser uses.

The register's item 4 does **not** move to `## Taken`, and saying why is the
point: what it asked has been answered, and what it is *about* is still true.
The desktop and the browser still disagree. So it is rewritten in place, keeping
its number — the precedent the register set for itself on 2026-09-15 — with the
guess it carried marked wrong, the mechanism written down, and what is left of
it stated as what it now is: a decision about a dependency.
