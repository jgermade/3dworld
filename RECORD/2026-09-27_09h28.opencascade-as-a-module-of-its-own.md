# 2026-09-27 09h28 · OpenCASCADE as a module of its own

Takes register **item 3** — *"An OCCT build for Emscripten"* — and gets its first half done: an
OpenCASCADE that runs in wasm, built from a pinned source, and shown to agree with the desktop's.
The page does not load it yet; that is the second half and this file's `Next`.

## Where this repo actually was

- `kernel-occt` was excluded from `make wasm`, and the browser's only kernel was `truck`, which has
  no fillet, chamfer or shell and a narrow boolean.
- An "Emscripten pipeline" had been recorded as landed on 2026-08-27:
  `kernel-occt/native/CMakeLists.txt` and `tools/build_occt_wasm.py`. Read today, it could not
  have produced a browser module. The script **exited 0 when Emscripten was missing**, printing a
  notice; the CMake file looked for an installed OpenCASCADE with `find_package`, which no
  Emscripten environment has, and built only a static library of the shim — nothing linked it
  into a module. Its record says "execution verified on macOS", which the first property explains.
- `native/UPSTREAM` named OCCT 7.6.3 and enforced nothing, and the register said two things had to
  be *decided*: `-fwasm-exceptions` against `-fexceptions`, and a real pin.
- The container had no Emscripten, no OCCT source and no native OCCT. `git clone` from GitHub
  worked and GitHub's archive downloads did not; `storage.googleapis.com`, where emsdk fetches
  its toolchains, did.

## Walkthrough · as built

**The shape of it: a second wasm module.** The browser's Rust is `wasm32-unknown-unknown` built by
wasm-bindgen, and OCCT cannot be linked into it — OCCT needs a libc, a libc++ and C++ exceptions,
and that target has none of them; moving the Rust to `wasm32-unknown-emscripten` would lose
wasm-bindgen. So OCCT is its own module, built by Emscripten, exporting exactly
`kernel-occt/native/w3d_occt.h` — the C seam the desktop links, and nothing OCCT-shaped. The
header is the export list: `tools/occt_wasm.py` reads the entry points out of it, so a new
entry point is exported by being declared, which is what the header's own comment asks for.

**The two decisions.**

- **`-fwasm-exceptions`.** The shim catches `Standard_Failure` at every entry point and OCCT
  throws for input it dislikes, so exceptions are not optional; `-fexceptions` emulates them
  through JS with an invoke wrapper around every call that might throw, which on code this
  call-heavy is size and speed paid everywhere. Native wasm exceptions are in every engine the page
  already requires.
- **A pin that is checked.** `tools/occt_wasm.py src` clones the `V7_6_3` tag and refuses it unless
  it is commit `b079fb98…` — a tag can be moved — and every later step refuses an `emcc` that is
  not 4.0.15, because a different compiler is a different binary. `native/UPSTREAM` records the
  commit.

**`tools/occt_wasm.py`**, in four steps, each a subcommand so a failure names its step: `src`,
`emsdk` (the pinned Emscripten into `tools/.emsdk/`), `build` (OCCT's CMake, static, with every
optional dependency off, and **every toolkit named** — asking for the leaves built the leaves and
nothing under them, because a static library's dependencies are not build dependencies to CMake;
the first build produced six archives and no `TKernel`), and `link` (the shim and 28 toolkits
into `web/dist/occt/w3d_occt.{mjs,wasm}`, with a 4 MiB stack — Emscripten's default is 64 KiB,
and a stack overflow is a trap the shim cannot catch). `make occt-wasm-src`, `occt-wasm-emsdk`,
`occt-wasm` and `occt-wasm-check`. The two network steps are separate targets, as
`occt-headers` and `binaryen` are. The old script and CMake file are removed.

**The first module was invalid wasm.** It linked, and then `wasm-opt` could not parse it; V8
refused it outright: *"Compiling function `ShapeUpgrade_ShapeDivide::Perform(bool)` failed:
br_table: label arity inconsistent"*. Recompiling that file at `-O0` did not help, so it was not an
optimiser bug. The cause is `OCC_CATCH_SIGNALS`: OCCT defines `OCC_CONVERT_SIGNALS` on every
non-Windows build, which turns that macro into a `setjmp`, and a `setjmp` in a function that also
holds a wasm `try` generated invalid code. With the define removed from that one file, the next
such function failed — the class, not the instance. Wasm has no signals to convert (a trap is not
a signal), so the build passes `-UOCC_CONVERT_SIGNALS` after OCCT's own `-D` rather than paying for
`-sSUPPORT_LONGJMP=wasm`. The toolkits took 18 minutes on four cores; the link 79 seconds.

**The check.** `make occt-wasm-check` runs `kernel-occt/examples/occt_wasm_reference.rs` against
this machine's OCCT and `tools/occt_wasm_check.mjs` against the module — the same scenes, the
second through the C seam itself, from Node, with pointers into the module's own memory — and
compares the rows: topology, bounds, body counts and which operations fail **exactly**, meshes
**reported**, since the two are different compilers against different maths libraries. And one row
only the module has: an OCCT exception thrown and caught inside wasm.

That row took two attempts. A zero revolve axis was the first probe — `gp_Dir(0,0,0)` throws — and
it cannot: OCCT's release build defines **`No_Exception`**, which compiles its `Raise_if` checks
out, so most of what OCCT documents as exceptions never throw in a release build of either kind.
`StdFail_NotDone` from `BRepBuilderAPI_Command::Check()` is thrown unconditionally, and a polygon
of one repeated point reaches it through `MakePolygon::Wire()`. The Rust side refuses such a
profile before the shim sees it, so only a direct call gets there.

## Bugs found by building, not by reading

- **The 2026-08-27 pipeline could not build a module**, and its script reported success when it
  could not start. Cause above; removed.
- **`OCC_CONVERT_SIGNALS` makes invalid wasm under `-fwasm-exceptions`.** Cause above.
- **A static toolkit build does not build its dependencies.** Cause above.
- **The shim accepts two solids that are not solids**, found by the native reference, on the
  desktop as much as in the browser:
  - a fillet of r = 15 on a 20 mm cube succeeds, with 26 faces, **78 edges and 40 vertices** where
    a filleted cube has 56 and 24. At r = 10 OCCT says it cannot; at r = 12 and 15 it returns this.
  - a transform by a zero scale succeeds and returns a solid with a cube's topology.
  The shim checks `IsDone()` and never `BRepCheck_Analyzer`, so anything OCCT builds and calls done
  is accepted. Both are in the register.

## Verified, and not

**Verified** — OCCT 7.6.3 at `b079fb98`, Emscripten 4.0.15, Node 22, this container's four cores:

| | native (Ubuntu's OCCT) | wasm32 (this build) |
| --- | --- | --- |
| cube, cut, fillet, chamfer, shell topology | 5 rows | **identical** |
| the drilled plate's bounds, to 9 places | | **identical** |
| cut and fillet meshes (triangles, vertices, segments) | 324 / 2612 triangles | **identical** — a reported row that happens to agree |
| fillet r = 10, r = 15 | fails; the 78-edge solid | **identical** |
| BREP save and load, STEP export and import | 1 body, same topology | **identical** |
| an OCCT exception inside wasm | — | caught: *"BRep_API: command not done"* |

- The module is **15.11 MiB raw, 5.12 MiB gzipped, 3.59 MiB brotli**, plus 20 KiB of gzipped JS.
  It instantiates in 85 ms in Node and builds every scene above in 666 ms.

**Not verified**

- **The negative control for the exception row.** A module built without working exceptions would
  trap there — that is the argument — and none was built to show it: it is another 18-minute build
  of every toolkit.
- **In a browser.** Everything ran in Node's V8. The page does not load the module, so Chromium has
  never instantiated it.
- **Anywhere but here.** `make occt-wasm` is not in CI — 18 minutes, a toolchain download and a
  native OCCT for the comparison — and has run on this container only.
- **Degenerate input, assemblies, and the conformance suite.** The check is thirteen rows over nine scenes. The
  conformance suite runs against the Rust `OcctKernel`, and nothing runs it against the module;
  that needs the bridge below.
- **Memory.** A 64 MiB initial heap that grows; nothing measured how far a real assembly takes it.

## Loose ends, deliberately left

- **The page does not load it.** The Rust side reaches OCCT through one `unsafe extern "C"` block
  in `kernel-occt/src/lib.rs`; on wasm32 that block can be implemented in Rust by forwarding each
  call to this module through JS in the same worker and copying buffers between the two linear
  memories, which would reuse all of `OcctKernel` — its conversions, errors and the conformance
  suite — unchanged. Not started.
- **5 MiB gzipped** is four times what a first visit costs today, and it would be paid before the
  first frame unless it is loaded after the page is up.
- **The shim's warnings** under clang — six helpers with C linkage returning C++ types — are
  pre-existing and harmless, and left.
