# 2026-09-18 03h22 · A blend that names its edge

Takes the first item of the `Next` block in
[`2026-09-16_02h35.the-manipulators-that-move-the-part.md`](./2026-09-16_02h35.the-manipulators-that-move-the-part.md)
— "Per-edge fillet and chamfer in the kernel trait" — and the loose end beside
it, which said why the edge handles' own label had to admit what they did.

## Where this repo actually was

The manipulators file describes an edge handle that a user grabs, drags, and
reads a radius off. What it issued was `Command::FilletRadius`, which reaches
`Document::fillet` → `kernel.fillet(body, radius)`, and that method rounds
**every edge of the solid** by contract. The handle was drawn on one edge of one
part and blended twelve; the previous session's honest answer was to say so in
the widget — `"Redondear (todo el sólido)"` — because the seam had no other
operation to call.

It was not only the label. The seam had no way to *name* an edge at all:

- `GeometryKernel` had `fillet(body, radius)` and `chamfer(body, distance)`, both
  whole-solid, and `shell(body, face_id, thickness)` — so a sub-entity id
  crossing the seam had a precedent, for faces, and nothing for edges.
- `Topology` carried `edges: u32`, a count. `Mesh` carried `face_of_triangle`,
  which is what per-face selection and ID-buffer picking are stored against, and
  nothing of the kind for its wireframe.
- The editor's `EdgeHit` is `(NodeId, u32, [f32; 3], [f32; 3])`, and that `u32`
  is `(i / 2)` from `find_closest_edge` — **an index into the mesh's line list**.
  It is a tessellation's idea of an edge: it moves with the sag, and it is what
  the status bar was calling "Edge #37". Nothing could turn it into a topological
  edge, so nothing could blend one.

`truck`'s `fillet` and `chamfer` have answered `Unsupported` since 2026-09-14,
so on the default build the handles could not do anything at all; OpenCASCADE's
`w3d_occt_fillet` explored `TopAbs_EDGE` and added every edge it found.

**Two environment facts, because they cost the first hour.** This container's
toolchain was rustc 1.94.1 and `egui 0.36.1` requires 1.95, so `make test` could
not run *at all* — it failed in `check`, before any test. `rustup update stable`
(to 1.98.1) fixed it. OpenCASCADE, `libxkbcommon-x11-0` and Mesa's software
rasterisers were all absent and all installable; `make app-test` needs the last
two or the window panics before it draws.

## Walkthrough · as built

1. **An edge identity on the mesh (`kernel/src/lib.rs`).** `Mesh.edge_of_line` —
   one topological edge id per wireframe segment, which is the promise
   `face_of_triangle` makes one dimension down. It is **empty or exactly
   `line_count()` long, never partly filled**, because a caller that has to test
   every lookup stops testing; `Mesh::edge_of_line(i)` enforces that by returning
   `None` unless the lengths agree. `None` is the honest answer for a mesh whose
   lines came from `line_edges()`'s fallback, which invents segments from
   triangle boundaries: those are not edges, and a blend asked for one would
   round something nobody picked.
2. **Two methods on the seam, declared before anything implemented them.**
   `fillet_edges(body, &[u32], radius)` and `chamfer_edges(body, &[u32], distance)`.
   The contract that took the most thought is the empty case: **an empty `edges`
   is `Degenerate`, not "all of them"**. The permissive reading is the bug the
   whole change exists to remove — it is what a user sees when a selection came
   back empty and the part lost every corner. An unknown id is `Degenerate` too
   (a bad argument, not an unsupported operation), and repeats name one edge
   once, because a caller mapping picked segments to edges produces them by the
   dozen. Declinable exactly as `fillet` is, and only with it.
3. **OpenCASCADE, which can actually blend (`kernel-occt/`).** The C ABI header
   first, per the rule that it is the specification: `w3d_occt_fillet_edges` and
   `w3d_occt_chamfer_edges`, plus `edge_of_line` on `W3dOcctMesh`. `resolve_edges`
   maps ids through `TopTools_IndexedMapOfShape` — **the same map
   `w3d_occt_tessellate` already numbered the wireframe against**, which is what
   makes an id from a mesh mean the same edge to a blend — then sorts and
   deduplicates, so the same selection gives the same solid whatever order it was
   clicked in. `BRepFilletAPI_MakeFillet::Add` takes it from there.
4. **`truck` declines, and still reports identity (`kernel-truck/`).** It has a
   topology; what it has no builder for is a rolling-ball surface. So
   `fillet_edges` checks its arguments and *then* declines, keeping "this build
   cannot blend" and "that is not an edge of this body" two different sentences
   to two different mistakes. `number_edges` numbers the solid's distinct edges
   from the **sorted** faces on the calling thread, and `mesh_face` reads the id
   off the untriangulated face zipped alongside the meshed one — `triangulation`
   rebuilds the wires, so an id taken from the copy is an id in a numbering
   nothing else shares.
5. **The determinism rule extended to cover it
   (`kernel-truck/tests/tessellation.rs`).** `edge_of_line` is tessellation
   output, so "a tessellation may be parallel; its output may not depend on that"
   applies to it. The pinned fingerprint grew a sixth component and the three
   literals were re-recorded in the same act — they moved because the function
   grew, not because a mesh changed — and both `parallel` settings produce
   byte-identical edge ids.
6. **The document layer (`core/src/document.rs`).** `fillet_edges` /
   `chamfer_edges`, one kernel call and one undo step each, labelled "Fillet
   edge" and "Chamfer edge" apart from the whole-solid "Fillet": a user who just
   rounded one corner and one who just rounded every corner want different words
   in their history.
7. **The handle does what it is drawn on (`app/`).** `Editor::blend_selected_edge`
   is where the translation happens: picked segment → `mesh.edge_of_line(segment)`
   → topological edge → `doc.fillet_edges(id, &[edge], size)`. Where a backend
   draws no such map it refuses in words. A blend renumbers edges, so the
   selection is dropped afterwards rather than kept pointing at something that
   moved — the same hazard a pull has with a face id, answered the same way. The
   gizmo issues `FilletSelectedEdge` / `ChamferSelectedEdge`, and the label is
   `"Redondear arista"`.

## Bugs found by building, not by reading

- **`truck`'s `Topology::edges` is not a count of edges.** It sums
  `wire.len()` over every face's boundaries, so it counts each edge *once per
  face that uses it*: a cube reports **24** where it has 12. Nothing here
  depended on it, and a per-edge blend does — an id space validated against it
  would accept twice the ids that exist. `distinct_edges` counts them the way
  `number_edges` numbers them instead. **The reported count is left as it was**:
  changing it is a change to what every existing conformance expectation means,
  and it is now written down rather than fixed in passing.
- **A `u32::MAX` id is the one that will actually arrive.** `edge_of_line`'s
  unknown-edge sentinel and an empty map both produce it, so the conformance
  check for "an id no edge has" uses that value rather than an arbitrary large
  one, and asserts no segment reports it while others report real ids.
- **Edge identity does not survive the worker boundary, and that is now
  explicit.** `sub_mesh` carries `edge_of_line` for an in-process split, and
  `WIRE.md` has no section for it, so a mesh encoded and decoded comes back with
  it **empty** — which `Mesh::edge_of_line` reports as "this backend does not
  say" rather than as a wrong id. Honest degradation was available only because
  the "empty or full, never partial" rule was written first.
- The first version zipped the *meshed* face's boundaries against nothing and
  read ids off them. They are ids of wires `triangulation` built, stable within
  one mesh and meaningless to a kernel — it would have blended a plausible wrong
  edge rather than failing.
- **The fix for that introduced a silent failure mode of its own**, which is why
  `edge_identity.rs` exists. Reading the id off the original face zipped
  alongside the meshed one is right while the two walks have the same shape, and
  `zip` says nothing when they do not: it stops at the shorter. The comment in
  the code asserted the shapes match; the test is what checks it, by grouping a
  box's segments and counting twelve collinear edges.

## Verified, and not

**Verified.**

- `make test` — check, clippy (`-D warnings`), `fmt --check`, licence and notice
  checks, the suite, and the `parallel` build: passes, **203 tests**.
  `make test-occt` passes, **28**. `cargo test -p w3d-app --features occt`
  passes, **68**.
- **A blend that rounds one edge, in arithmetic, on OpenCASCADE**
  (`app/tests/blend_edges.rs`). Rounding one edge of a 20 mm cube at r = 2
  removes **17.3474** against the closed form `l·r²·(1 − π/4)` = **17.1681**;
  the residual is the tessellation under-representing the new cylindrical face,
  and the tolerance is 1.0. Faces go **6 → 7** — exactly one blend surface,
  where rounding every edge adds twelve and eight more at the corners — and the
  solid's extent in x does not move. The whole-solid `fillet` at the same radius
  leaves **7802.76** against the one edge's **7982.65**, so the two operations
  are measurably different rather than a rename.
- **The empty selection, as a number.** `fillet_edges(id, &[], 2.0)` is refused
  and the volume is unchanged; if it had meant "all of them" the same assertion
  would have caught 197 of removed material.
- **The edge id travels the path the editor walks.** The test finds its edge by
  geometry — the segment where the `+y` and `+z` faces meet — and then through
  `Mesh::edge_of_line`, which is the map a click goes through, rather than
  guessing an index.
- **`truck` finds the id and then refuses**, asserted the other way in the same
  file: the refusal names the missing capability, and a refused blend leaves the
  solid untouched.
- **The ids are the right edges, not merely well-formed ones**
  (`kernel-truck/tests/edge_identity.rs`). This is the check the zip in
  `mesh_face` needed: `zip` truncates rather than complaining, so a structural
  mismatch between the meshed and the untriangulated walk would hand back ids
  that are plausible and wrong on a backend that declines the blend and never
  finds out. A 2x3x4 box's segments group into **exactly twelve** ids — not "at
  most twelve", because a slip merges two edges or invents a thirteenth — and
  every segment under one id is parallel to one axis and pinned to the same two
  coordinates on the others, which is what separates a correct grouping from a
  consistent-looking permutation. A cylinder's ids stay inside its own edge
  count and no id spans more than the height, that being the shape a mismatch
  takes on a curved body where one edge is many segments. Both hold under
  `parallel` and without it.
- The conformance suite gained both halves and **both real backends pass them**:
  the argument contract (empty, unknown id, non-positive size, declinable only
  as a set of four) and `edge_of_line`'s well-formedness (empty or one per
  segment, no sentinel among real ids, and no id past the body's edge count).
  The first draft of that check also required the ids *used* to be contiguous
  from zero, and it was wrong to: an edge can be degenerate or carry no
  polyline and so contribute no wireframe segment, which makes a gap the mark
  of a backend describing its own solid rather than of a bug. It passed on both
  backends and would have failed correct code later, which is the worse of the
  two ways for a check to be wrong.
- Determinism: the same edge ids under `parallel` and without it, held to a
  pinned literal.
- It runs: `make app-test` — window, egui, and the scene drawn on llvmpipe.

**Not verified.**

- **Nobody has grabbed one of these with a mouse.** Unchanged from the previous
  session and now the second body of work resting on it: there is no pointer in
  this environment. The drag arithmetic and the command it issues are tested;
  the gesture is not.
- **Only one edge, and only on a box.** Every geometric assertion here blends a
  single straight edge of a cube. `fillet_edges` takes a slice and OCCT is handed
  all of it at once, but **a multi-edge selection is untested**, and so is a
  curved edge, two edges meeting at a vertex — the case where blends must
  interact, and the one a real kernel finds hard — and any radius large enough
  for the blend surfaces to collide. The refusal path for an impossible radius
  is OCCT's `IsDone()` being false, which is reported and not exercised.
- **The chamfer's geometry is unmeasured.** `chamfer_edges` is verified as a
  contract — declinable with its three siblings, refuses an empty selection and
  a bad id — and no test weighs the material a bevel removes the way the fillet's
  is weighed. The C++ differs from the fillet's only in the maker type.
- **`edge_of_line` is unverified against a boolean's output.** Ids are documented
  to renumber across one, and the editor drops its selection accordingly, but no
  fixture cuts a solid and then blends an edge of the result.
- **The browser cannot use any of this**, and not only because `truck` declines:
  the wire format drops edge ids, so even a browser backend that could blend
  would arrive with no identity to blend against.

## Loose ends, deliberately left

- **`WIRE.md` carries no edge ids.** Deliberate: the browser's backend refuses
  every blend, so ids would cross the boundary to be declined at the other end,
  and widening a versioned cross-boundary format ahead of a caller is how the
  format stops meaning anything. The comment in `wire/src/chunk.rs` names this
  as the line that has to change the day the browser has a kernel that blends.
- **`truck`'s `Topology::edges` still counts face-uses.** Described above. A
  correction is a change to what existing expectations mean and belongs to
  whoever is reading that suite, not to this change.
- **The whole-solid `fillet` and `chamfer` are untouched**, and the Ribbon still
  drives them. Both forms now exist on the seam; nothing decides which a button
  should offer, because that is the capability query item 8 of the register has
  been asking for.
- **A multi-edge selection has no UI.** The seam takes a slice, the editor passes
  a slice of one, and there is no way for a user to pick two edges and blend
  both — which is the ordinary thing to want after doing it once.
- The blend size on the handle is a drag distance snapped to 1 mm; there is still
  no numeric entry for a radius.

## Walkthrough · as completed

A blend can name an edge, on a seam that had no way to name one at all.
`Mesh.edge_of_line` carries one topological edge id per wireframe segment —
**empty or exactly one per segment, never partly filled** — and
`fillet_edges` / `chamfer_edges` take a slice of those ids, with an empty
selection `Degenerate` rather than "all of them", because the permissive
reading is the bug the whole change existed to remove. OpenCASCADE resolves ids
through the same `TopTools_IndexedMapOfShape` its wireframe was numbered
against; `truck` checks the argument and *then* declines, keeping "this build
cannot" and "that is not an edge" two sentences to two mistakes. Rounding one
edge of a 20 mm cube at r = 2 removes 17.3474 against the closed form's
17.1681, takes faces 6 → 7, and is measurably not the whole-solid fillet's 197.
