# 2026-09-16 02h35 · The manipulators, and the operation underneath them

## Where this repo actually was

`RECORD/2026-09-16_02h40.hierarchical-selection-and-manipulator-gizmos.completed.md` records five
extensions of work on the viewport manipulators, every one of them ending in a green
`cargo test` / `cargo clippy` / `cargo fmt`. Those runs were real — re-run here, they pass — and
none of them touched a line of the gizmo code: it lived inside `chrome()`, a 1,300-line function
that no test constructs. What the user could see, and the suite could not, was this:

- **"Extrude face" did not extrude.** `Document::push_pull_face` took the face's normal and called
  `self.transform(id, &m)` — it translated *the whole solid*, and `Editor` reported "extruded face
  #n by 10.0 mm" while doing so. `Alt` ("displace the object") ran the identical arithmetic, so the
  modifier changed nothing. A box moved and a box grown have the same bounds, which is why nothing
  caught it.
- **The blend handles were not on the selected edge.** `FilletRadius` → `Document::fillet` →
  `kernel.fillet(body, r)`, which by contract rounds *every* edge of the solid. On the default
  build (`truck`) both `fillet` and `chamfer` answer `Unsupported`, so the edge handles could not
  do anything at all, and said nothing when they didn't.
- **A kernel call per mouse-move.** The drag loop called `transform` / `push_pull_face` on every
  frame: a new `Body`, a fresh tessellation and a history edit each time, with the mesh cache keyed
  by body and never swept. A three-second drag left some two hundred dead bodies and meshes behind
  it, and got slower as it went.
- **Handles were grabbed by their bounding box.** `Rect::from_two_pos(base, tip).expand(14.0)` plus
  `Response::drag_started()`: for a diagonal arrow that is a square most of which is not the arrow.
  A second start condition, `primary_down && !is_any_drag`, fired even when the press had begun
  somewhere else, so orbiting past a handle started modelling.
- **Those rects killed the viewport.** Each was a registered `egui` widget, so `response.consumed`
  in `Shell::window_event` swallowed presses in a wide region around the part: no orbit, no pick. In
  object mode there was one such rect *per visible face*.
- **There was no rotation manipulator.** Three buttons of a fixed +15° in a floating `Area`. The
  X/Y/Z translate triad the record describes was not in the code either; per-face arrows had
  replaced it.
- **Cancelling ate the previous operation.** `Escape` in the readout ran `commit_transaction()` and
  then `Command::Undo` unconditionally. The fillet path applies nothing during the drag, so the
  transaction was empty and the undo took whatever the user had done *before*.

## Walkthrough · as built

1. **A push/pull that pulls (`core/src/face.rs`, `core/src/document.rs`).** The kernel trait has no
   local face operation, so one is built from what it does have. `face_loop` takes the triangles
   carrying a face id, welds their vertices onto a grid, cancels the edges walked twice and chains
   what is left into one loop; `FaceLoop::projected` hands that loop back as `(u, v)` on a
   right-handed frame around the pull direction. `Document::push_pull_face` extrudes it to a prism,
   places it on the face, and unions it (outward) or subtracts it (inward). A curved face, a face
   with a hole and a face id nothing carries are refused by name — never a silent fall back to
   moving the part.
2. **The slack, declared (`core/src/document.rs`).** A prism standing on a face has its sides
   *coplanar* with the solid's. `truck-shapeops` panics on that whatever tolerance it is handed
   (measured: every skew of 0 failed, on both the union and the difference). So the operation is
   attempted exactly first, and only on a geometric failure retried with the prism's sides moved off
   those planes by a tenth of the tolerance the backend runs the boolean at — inward when adding
   material, outward when cutting, so the error is never invented material. `push_pull_face` returns
   `PushPull { distance, slack }` and the status line says the number out loud.
3. **The selection follows the geometry (`app/src/editor.rs`).** A boolean rebuilds the solid and
   renumbers its faces, so after a pull the editor re-finds the pulled face by normal and position
   and re-selects it — or drops the selection and says the face is gone. Keeping the old number is
   how a second pull lands on a face nobody chose.
4. **`crate::gizmo`, which is testable (`app/src/gizmo.rs`).** `ScreenAxis` measures a 3D ray's
   direction and scale where the handle actually is, so a drag reads `f(start, cursor)` rather than
   integrating per-frame deltas; `Session` holds `value` and `applied` apart, which is what makes
   "what is still owed" a value (`Pending`) and "is there anything to undo" a question with an
   answer. `Shift` snaps (5 mm, 1 mm on a blend, 15°), `Ctrl` slows to ×0.1, and both can be pressed
   or released mid-drag without moving the anchor.
5. **The manipulators themselves (`app/src/shell.rs`).** One set per selection: a body gets the
   X/Y/Z triad and three rotation rings (far half culled), a face gets the two push/pull arrows, an
   edge gets fillet and chamfer — labelled *todo el sólido*, because that is what the backend does.
   They are sized in screen points, not in model units, so they neither run off the window on a
   framed part nor vanish on an assembly. A handle is hit-tested against its shaft or its ring, and
   only then does one cursor-sized widget tell `egui` the pointer is spoken for. Drawing is clipped
   to the viewport, so nothing paints over the ribbon.
6. **A drag is a number until it is let go.** During the drag the document is untouched and the
   preview is drawn instead: the face's outline where it would land, or the selection's box
   translated or turned. On release it becomes one command — `TranslateSelection`,
   `RotateSelection`, `PushPullFace`, `FilletRadius`, `ChamferDistance` — which is one kernel call
   and one undo step. The old viewport drag (`Editor::drag_face_extrude`) accumulates the same way
   and applies on `Input::Up`.
7. **Cancelling cancels only itself.** `Escape` or `✕` undoes what *this* session applied, and
   nothing when it applied nothing. An open readout claims the `Escape` key (`GizmoStatus::open`)
   without claiming the pointer, so the viewport still orbits while it is up.

## Bugs found by building, not by reading

- `truck-shapeops` cannot union or subtract a prism whose sides are coplanar with the solid's,
  at any tolerance: measured across skews of 0, 1e-5, 1e-4, 1e-3 and 1e-2 of the size, only the
  zero case failed, and it failed in both directions. This is what the `slack` retry exists for,
  and why the API says so instead of rounding it away.
- The difference case comes back *exact* even with the cutter skewed outward (volume 600.0000 of a
  wanted 600), because the extra sits outside the solid. The union does not: a 1e-4 skew costs
  1.6e-4 of the volume and splits the side into more faces. The direction of the skew is therefore
  not cosmetic and is chosen per operation.
- Face ids do not survive a boolean. The first pull worked and the second landed on an unrelated
  face until the editor started re-finding the face by its geometry.
- `egui` learns that a handle is under the cursor a frame *after* it is, so the press that starts a
  drag still reaches the editor. Cancelling the editor's drag at the moment a handle is grabbed is
  what stops a grab from also orbiting, and stops the release from being read as a click on
  whatever is behind the handle.

## Verified, and not

**Verified.**

- `make test` — check, clippy (`-D warnings`), `fmt --check`, the licence and notice checks, and the
  suite, including the `parallel` feature build: passes. 182 tests.
- Real geometry, on the backend the default build runs (`app/tests/push_pull.rs`, `truck`): pulling
  a 10×10 face of a 10 mm cube by 4 adds 400.0 ± 1.0 of volume and moves only the pulled side;
  pushing it by 3 removes 300.0 ± 1.0 and leaves the far side where it was — which is what tells a
  pull from the translation this replaced. A cylinder's side is refused and the part does not move.
  A second pull lands on the same face of the same part.
- The outline recovery, on its own (`core/src/face.rs`): a box face comes back as four corners, the
  winding is counter-clockwise seen from outside on all six, a vertex left partway along a side is
  dropped, a curved face and a face with a hole are refused, the projected frame is right-handed
  around either pull direction, and an offset square is a smaller square.
- The drag arithmetic, on its own (`app/src/gizmo.rs`): a drag measures where the cursor is and not
  how it got there, an end-on axis has no drag direction rather than a wild one, the tip lands under
  the cursor, snapping and the fine modifier do not move the anchor, a handle is grabbed by its
  shaft and not by its bounding box, a turn is signed by which way its axis faces, and a session
  that applied nothing has nothing to undo.
- It runs: `xvfb-run cargo run -p w3d-app -- --frames 12 --screenshot` on `llvmpipe`, with the body
  triad and rings, and with `--test-pick-face` for the push/pull arrows. The arrows leave the face's
  projected centroid — checked against the projection, not by eye.

**Not verified.**

- **No backend with a real blender was exercised.** `fillet` and `chamfer` are `Unsupported` on
  `truck`, and OpenCASCADE is not installed here, so the edge handles were verified only as far as
  "the command is issued, once, inside its own transaction, and the backend's refusal reaches the
  status line". The blend itself is untested by this work.
- **The exact (slack-free) push/pull path has never succeeded here.** It is attempted first, and on
  `truck` it always loses; only OpenCASCADE would take it. Whether it does is unknown until someone
  runs `--features occt`.
- **Push/pull is planar-only, and the planarity test is a tolerance.** `face_loop` accepts a face
  whose vertices sit within the weld distance of one plane, scaled up by the coordinates' own `f32`
  noise. A very finely tessellated curved face, far from the origin, could in principle pass it; no
  such case was constructed.
- **A face with a hole is refused rather than handled.** The loop chaining insists on exactly one
  loop, so pulling the face of a plate with a bore through it will not work. That is a refusal, not
  a wrong answer.
- **No interactive testing.** There is no display and no input in this environment: every drag was
  exercised through `crate::gizmo`'s arithmetic and the commands it issues, and the drawing was
  checked in screenshots. Nobody has yet grabbed one of these with a mouse.

## Loose ends, deliberately left

- The rotation rings turn about the selection's bounding-box centre. There is no way to put the
  centre somewhere else, and no numeric entry for the centre.
- The blend handles apply to the whole solid. Per-edge blending needs `fillet`/`chamfer` to take an
  edge in the kernel trait and `BRepFilletAPI` behind it — a separate body of work, and the reason
  the handle says so in its own label rather than implying otherwise.
- `Editor::drag_face_extrude` (drag on a selected face in the viewport, with no handle) now
  accumulates and applies on release, but draws no preview of its own; the manipulator's arrow is
  the path with the preview.
- Multi-selection turns each body about the selection's shared centre via `RotateSelection`, which
  rotates each body about *its own* centre. Untouched by this work and still wrong for a group.

## Extension · 2026-09-16 · What CI said, and what OpenCASCADE said

### The smoke test was already red, and the manipulators were why

`make app-test` failed on the first CI run of this branch — and on `main` at
c9fa085, the commit this work builds on, while it passed on the commit before
that (3e0981d). `tools/app_smoke.py` runs the demo for thirty frames under a
software rasteriser and gives it three minutes; it timed out.

Measured rather than guessed, on the solid the demo builds (a 20 mm box minus a
cylinder, 6,334 triangles):

| | |
| --- | --- |
| the boolean | 6.6 s, once |
| the first tessellation | 4.7 s, once |
| five cached meshes | 5 µs |
| **five `Document::bounds`** | **12.2 s — 2.4 s each** |

`TruckKernel::bounds` tessellates the solid again at a sag finer than any
viewport asks for, and the manipulators asked for it *every frame* to know where
to stand — the version before this one asked twice. Thirty frames of that is
seventy seconds of pure re-tessellation on top of the rendering, which is the
timeout.

`Document::mesh_bounds` is the box around the tessellation that the renderer has
already paid for: a walk over vertices, exact to the tessellation's own chordal
error, which is a fraction of a pixel where a gizmo stands. The handles use it;
`bounds` stays what it was for everything that needs the kernel's exact answer.
The demo's smoke test goes from over three minutes to **38.6 s**, so this PR
also takes the base branch's failure with it.

### OpenCASCADE, installed and asked

`apt install libocct-*-dev` is all it needed — the same four packages the
Makefile names. `app/tests/push_pull.rs` now runs against whichever backend the
build has, and the two backends are pinned *apart* where they differ:

- **OpenCASCADE takes the exact path.** `done.is_exact()` is asserted under
  `--features occt`: it joins the prism's sides to the solid's coplanar ones,
  so no slack is needed. The claim that the exact attempt is worth making is no
  longer theoretical.
- **`truck` takes the slack path**, asserted the other way: `slack > 0` and
  under the tolerance the boolean itself runs at.
- The same volumes on both: +400 for a 10×10 face pulled 4, −300 for one pushed
  3, with the far side unmoved.
- **A blend now has a backend that can do one.** `Command::FilletRadius(1.0)` —
  what the edge handle issues — rounds a 20 mm box on OpenCASCADE: the volume
  drops a little, the bounds do not move, and it is one undo step labelled
  "Fillet". On `truck` the same command reaches the status line as that
  backend's own refusal. Both are asserted.

### Bugs found by building, not by reading

- A cylinder's side has no average normal: the outward directions cancel around
  the axis, so `face_metrics` on it returns something arbitrary. The first
  version of the curved-face test looked for the side *by* that normal and
  could not find it on OpenCASCADE — the test was wrong, not the refusal. It
  now finds curved faces by asking whether a face's own triangles disagree
  about which way they point, which is an opinion formed without the code under
  test, and asserts the refusal for every one of them.

### Verified, and not · revised

Moved from "not verified" to verified: the exact push/pull path (OpenCASCADE
takes it), and the blend handles' command against a backend that blends.

Still not verified: **nobody has grabbed a handle with a mouse.** There is still
no display and no pointer in this environment. And `mesh_bounds` places the
handles by the tessellation rather than the solid, which is a chordal error
below a pixel at any zoom the gizmo is legible at — and is an approximation, not
an identity.
