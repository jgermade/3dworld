## Where this repo actually was

The cause was known, measured and written down: `truck-shapeops` 0.4.0 chains the boolean's
intersection segments through an `FxHashMap<PointIndex, Node>` and reads the first node and each
next direction with `iter().next()`; `rustc-hash` multiplies by a different constant when `usize`
is 32 bits, so the same closed loop is entered at a different vertex on wasm32. The browser's demo
plate cut to **6294** triangles natively and **6290** in wasm32. A `BTreeMap`/`BTreeSet` over the
same key had been shown, in a scratch crate, to give **6292 on both**.

What was in the tree: `make xarch` asserting everything *before* the boolean bit for bit and
holding the cut's mesh to 1% and its saved length as `Report`; `make web-test` comparing the
document's triangle count with the page's own to 1%; and a register item saying the remaining
step was a decision about a dependency — fork, `[patch.crates-io]`, or report and wait.

The container's stable `rustc` was 1.94.1, below the 1.95 egui 0.36 needs, so `make test` did not
start at all before `rustup update`. That is the environment, not the tree, and is noted only
because a reader re-running this on an old toolchain will meet it first.

## Walkthrough · as built

**The decision: vendor the crate, patch it, wire it with `[patch.crates-io]`.** There is no
GitHub fork to point a git dependency at from here, and a path in the tree is the smaller thing to
review anyway: the whole fork is visible in one diff. `vendor/truck-shapeops/` is the published
0.4.0 package — same checksum's contents, minus `.cargo-ok`, `.cargo_vcs_info.json`, `Cargo.lock`
and `Cargo.toml.orig` — with two files changed, each marked in place, and a `PATCHED.md` that says
what differs, why, what is not claimed, and what lets the patch be dropped. `vendor/` is
`exclude`d from the workspace: it is not ours to lint or format, and a workspace member would be.

**The fix is what the record demonstrated, and nothing more.** In
`src/transversal/polyline_construction/mod.rs` the import becomes
`std::collections::{BTreeMap as HashMap, BTreeSet as HashSet}` and `PointIndex` derives
`PartialOrd, Ord`. `PointIndex` is `[i64; 3]`, whose order is the same on every target. The
aliases keep the rest of the function byte-for-byte upstream.

**A second change, forced and harmless.** `src/lib.rs` carries
`#![cfg_attr(not(debug_assertions), deny(warnings))]`, and the published crate has a dead
`Alternative` enum. On crates.io that is invisible, because Cargo passes `--cap-lints` to a
registry dependency; it does not pass it to a path dependency, so the first release build here
failed. The attribute is removed. Every build now prints the one `dead_code` warning upstream
would have printed for itself.

**Licence.** `truck-shapeops` is Apache-2.0 and the published package carries no licence text,
so `vendor/truck-shapeops/LICENSE` is the Apache-2.0 text; Apache-2.0 §4(b) is why each changed
file says so. `NOTICE` picked the file up and now carries the full text where it used to say
*"No license file found in crate package"* — an improvement the tool made on its own. AGENTS.md
gains the rule beside the one about OCCT's modifications: a vendored crate keeps its licence,
carries the text, marks its changes, and has a `PATCHED.md`.

**`make xarch` asserts every row.** `Rule::Close` is gone — it existed for this item's 1% and
nothing else — and the cut's rows are `Rule::Exact`: triangles, vertices, lines, and two new rows.
`cut.mesh.hash` is the `f32` positions, in order. `cut.blob.numbers` is the one that matters: the
saved cut's bytes still vary run to run (`truck-topology`'s pointer-keyed map orders the vertices),
so it hashes **every number in the JSON, sorted by bit pattern** — a multiset, invariant to that
order and sensitive to every digit. It is the `f64` evidence the mesh rows cannot be, and it is
exactly what the 2026-09-21 file measured by hand ("44 of 1353 numbers differ"). `Rule::Report`
stays with no row using it, documented as the place the next known disagreement goes. The
controls are four now: the close-row control went with the rule.

**`make web-test` holds the scene to equality.** The document the page loads was cut natively;
the page's reference is cut in wasm32; *"the same scene as the one compiled in"* is now `===`.

**One golden moved, on purpose.** `kernel-truck/tests/tessellation.rs` fingerprints the drilled
plate, and the fingerprint was of the old cut (3425 vertices). Re-recorded to the new one (3423,
6292 triangles), with a comment naming the patch, and asserted against both the sequential and the
`parallel` path as before — which is the property that test exists for, and it still holds.

## Bugs found by building, not by reading

- **A path dependency is not lint-capped, and a published crate can carry `deny(warnings)`.** It
  cost one failed build and would cost one in anybody's fork: vendoring a crate changes which of
  its attributes are live, before a line of its code is touched.
- **The first number extractor read JSON keys as numbers.** It split the blob on
  non-number characters, and `truck`'s keys have digits and `e`s in them; it panicked on the first
  one. It now blanks string contents before splitting, and a unit test holds it to a key like
  `"Curve3e1"`, an escaped quote and a `true`. A second test holds it to a real `save_body`: a
  multiset of nothing would agree with anything, so the reader has to be shown to find a box's
  bounds among what it returns.

## Verified, and not

**Verified.**

| What | How |
| --- | --- |
| The two architectures cut the same solid | `make xarch`: all 31 rows bit-identical, native and wasm32, each build deterministic across two processes — including `cut.blob.numbers`, every `f64` in the saved cut |
| The check can fail on the thing it is for | `[patch.crates-io]` commented out and `make xarch` rerun: **6294 against 6290** again, and all six `cut.*` rows `DIFFER` and fail. Restored afterwards |
| The conformance suite passes against the patch | `make test` — check, clippy `-D warnings`, fmt, licences, notice, every test, and `w3d-kernel-truck` again with `parallel` |
| The browser agrees with the desktop | `make web-test` in headless Chromium: *"6292 from the document, 6292 built here"*, all checks passed, threaded variant built and running a pool of 4 |
| The patch is the published crate plus two marked changes | `diff` against the registry copy of `truck-shapeops-0.4.0` |

**Not verified, and the risk taken with each.**

- **Agreement is not correctness.** 6292 is a third answer, neither of the two before. The
  conformance suite passing is what a boolean change has to be argued against, and that is what
  it has; whether the ordered map's starting vertex gives a *better* curve is not asked.
- **One map was changed; four modules use `FxHash` containers.** `healing/`, `divide_face/`,
  `loops_store/` and `faces_classification/` iterate `FxHashMap`s too. Nothing measured shows their
  order reaching a result, and `make xarch` is one plate and one drill. A cut that goes through a
  path those maps order — a heal on import, a face divided more than once — could still differ,
  and nothing here would see it.
- **Not reported upstream.** This session's GitHub scope is this repository; the issue for
  `ricosjp/truck` is not filed. Until it is, the patch has no route to being dropped.
- **Only on this container and, once pushed, on CI's runner.** The same limits as before: no
  32-bit native desktop build was made, and the browser run is headless Chromium's software path.
- **`TruckKernel::save_body` is still not byte-stable across runs.** Untouched, and the small item
  about it stands: it is a different map in a different crate (`truck-topology`), and sorting the
  topology on the way out is a change to a kernel's blob writer.

## Loose ends, deliberately left

- **The upstream report.** Two lines and a derive, with the diagnosis in the 2026-09-21 file. It
  needs somebody with an account on `ricosjp/truck`'s tracker; this is written into
  `PATCHED.md`'s *Dropping it*.
- **The other `FxHash` containers in `truck-shapeops`.** Converting them all would be a larger
  fork on no evidence; auditing which of them are iterated would cost an afternoon and is the
  cheaper step. Moved into the register's small items.
- **The vendored crate's `dead_code` warning.** Silencing it means a third change to upstream code
  or a `[lints]` table in its manifest. Left printing: it is upstream's warning, and hiding it
  makes the fork look cleaner than it is.
