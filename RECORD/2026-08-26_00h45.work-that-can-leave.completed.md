# 2026-08-26 00h45 · Work that can leave

Took item 1 from [the register](./2026-08-25_21h59.what-is-not-built-yet.md): **STEP, in and out**.

## Where this repo actually was

Eight crates. `make test` ran 62 tests with no setup, `make test-occt` 11 more against real
OpenCASCADE, `make app-test` opened a window under Xvfb and asserted that chrome and scene had
drawn separately. A person could add primitives, select them, run a boolean on real geometry,
orbit, undo, save a `.w3d` and reopen it.

And nothing they made could leave. The `.w3d` is deliberately unreadable by any other kernel —
the manifest names the writing kernel and a different build refuses the file by name — so the
whole design rested on a sentence in an error message that was not true yet:

> `this document's geometry was written by kernel "occt-brep-1". Export it to STEP from a build
> that can open it.`

There was no export to STEP from any build. The instruction pointed at a door that did not exist.

## Walkthrough · as built

### Two methods, named for STEP

`GeometryKernel` gained `export_step(&[Body]) -> Vec<u8>` and `import_step(&[u8]) -> Vec<Body>`,
declared on the trait before either was implemented, as the seam rule requires.

Named for STEP, and not `export(format, …)` over an `ExchangeFormat` enum with one variant. The
argument for the abstraction is that a second format will come; the argument against it is what a
caller has to know to use this one — that the file states a unit and the document does not have
one, that names and history and structure do not cross, that a solid comes back with its faces
renumbered. None of that is knowledge about "an exchange format", all of it is knowledge about
STEP, and an interface that hides which format it is hides the paragraph that says what it costs.
A second format, when one is owed, gets its own pair and its own paragraph.

The other half of that decision is what STEP is *not*: `save_body`/`load_body` already move
geometry across, and it would have been one flag away to reuse them. They are the opposite
operation. `save_body` is lossless and unreadable anywhere else; `export_step` is readable
everywhere and lossy. A caller choosing between them is choosing between those two sentences, and
a flag would have made that choice look like a detail.

### The conditional check that does not skip

The register named this as the design point to settle: a backend may honestly not know STEP, so
the conformance suite has to be conditional, and it has never had a conditional check before.

The obvious shape — skip the check when the backend answers `Unsupported` — was rejected, because
this repository has already written down that **a skipped test looks like a passed test**
(`w3d-render`'s adapter-less tests print `SKIPPED:` and `cargo test` still says `ok`). A skip
would have meant the fake kernel silently passing four checks it never ran, in the suite whose
whole job is to be run against every backend.

So the four new checks are conditional and none of them skips. Every branch asserts something:

| Check | If the backend does STEP | If it does not |
| --- | --- | --- |
| offered in both directions, or neither | both answer | both refuse — and this is the assertion |
| a solid survives a round-trip | export, re-import, compare | refusal, already pinned by the check above |
| bytes that are not STEP are refused by the right name | must be `Failed` | must be `Unsupported` |
| nothing, or a deleted body, is refused before writing | `Degenerate` / `UnknownBody` | `Unsupported` |

The third is the one with a user behind it. `Unsupported` and `Failed` are two different sentences
— "this build cannot read STEP" and "this file is not STEP" — and they send somebody to two
different places. A backend that answers `Unsupported` for a corrupt file sends a user looking for
a different build of the program, and would pass any check that only asked whether the call
failed.

The first is a claim about what a half-implementation is worth: a kernel that reads STEP but
cannot write it leaves a user's work inside it, and one that writes but cannot read is a door that
only opens outwards. Half a bridge is not a bridge, so the suite refuses to call it one.

**What the round-trip check deliberately does not assert is the topology.** Faces, edges and
vertices are compared nowhere; the solid count and the bounds are. STEP is a boundary description
and nothing in it obliges a reader to split faces the way the writer did — a cylindrical face may
arrive as two halves, a seam may move. Asserting face counts would be asserting that two
implementations of a 700-page standard agree about something the standard does not require, and
the first failure would be a correct kernel failing an incorrect check.

### `FakeKernel` refuses, in writing

Both directions return `Unsupported` with a sentence saying why: a STEP file is a boundary
representation with surfaces under its faces, and the fake kernel is a CSG tree that is never
evaluated. It has nothing to write and nowhere to put what it read. That is not a stub awaiting
work — filling it in means evaluating the tree, which is the whole of what a real kernel does.

### The C ABI, and the one lock in the shim

Three new entry points in `native/w3d_occt.h`: `export_step`, `import_step`, and a
`bodies_free` for the `W3dOcctBodies` the second answers with. A STEP file holds any number of
solids and nobody knows how many until it has been read, so it is the one call in the shim that
answers with a list rather than a handle.

The header's own prose said "sixteen entry points", the Rust doc comment said thirteen, and both
were written when they were true. Both now say that the file *is* the list and give no number.

**STEP is the only thing in this shim that touches process-global state.** Its unit and schema
live in OCCT's `Interface_Static`, which is one table for the whole program, and its diagnostics
go to one default messenger. Everything else in the shim is per-context precisely so that
`cargo test`'s threads cannot race — the first version of this backend kept one static map and
was found out that way. So both STEP entry points take a **process-wide mutex**, the only lock in
the file, and the header says so where somebody parallelising tessellation will read it.

### OCCT prints its errors and returns a number

The reader reports a syntax error by *printing* it —

```
**** ERR StepFile : Undefined Parsing: Line 2: Incorrect syntax: unexpected TYPE, expecting STEP
```

— and returning a status code with nothing in it. The writer prints a statistics banner on every
export. A library writing to somebody's terminal is bad on a desktop and worse in a browser
console, and throwing the text away would have meant `KernelError::Failed` with no reason in it,
which is the failure mode this repository keeps arguing against.

So the shim installs its own `Message_Printer` for the duration of a STEP call, collects
everything at warning level and above, and puts the real printers back — including when an OCCT
exception unwinds through it. The statistics stop existing; the parse error becomes the message
behind `Failed`, which is where a user can read it. That is the whole reason the discrimination
between "not STEP" and "cannot do STEP" carries a useful sentence rather than a shrug.

### Two decisions the file has to state, because the document cannot

- **Millimetres**, written into the file and read back as the same unit. The document has no
  units at all — item in the register, and unchanged by this work — so a number in it is just a
  number, and exporting is the moment somebody has to decide what those numbers meant. This is
  that decision, and it is now written down in a place another program reads.
- **AP214 IS**, not AP242. AP242 is the newer schema and the one to move to when a document holds
  something worth carrying that AP214 cannot — colours, assemblies, tolerances. It does not yet,
  and AP214 is what everything in the list this format exists to reach has read for twenty years.

The file also names this program in `FILE_NAME`'s originating system, because OCCT's default
answer is "Open CASCADE Shape Model", which is a true statement about the library and a useless
one about the program that wrote it.

### Above the seam

`Document::export_step(&[NodeId])` and `Document::import_step(&[u8], name)`. Import **appends** —
a `.w3d` carries a document and replaces one, a STEP file carries solids and adds them — and it is
**one transaction**, so an import of forty solids is one undo. That is not the general fix for
grouping that the register asks for; it is that an import has an obvious boundary and undoing half
of one is not a state anybody asked for.

In the modeller: `Command::ExportStep`, ctrl-E, and a button; the selection, or everything when
nothing is selected. `--import-step FILE` and `--export-step FILE` on the command line.

**There is deliberately no `ImportStep` command.** Export can invent a name from the document's
own; import needs a file that already exists and there is no file dialogue to name one with. A
menu item that cannot be clicked is worse than one that is not there, so import is a command-line
option until there is a dialogue.

Exporting does **not** remember the path. A `.w3d` is where the document lives and a `.step` is a
copy that left; making ctrl-S follow an export would quietly move the document into a format that
cannot hold it.

### `make app-test-step`

The kernel tests prove a kernel can read what a kernel wrote. That is not the claim: the claim is
that the *program* can open what the program saved. So `tools/app_smoke.py --step` runs the
modeller twice — one process exports a STEP file, a second process imports it — and asserts on the
second one's frame, with the same chrome-and-viewport-separately check the existing smoke test
uses. It needs OCCT and a display, so it is its own target and part of neither `make test` nor
`make app-test`.

```
wrote 19146 bytes of STEP
imported 1 body from /tmp/…/roundtrip.step
1100x720 · chrome 89 colours · viewport 271
ok    a STEP file left one process and was drawn by another
```

## Bugs found by building, not by reading

- **`clippy` has never covered `kernel-occt`.** `make clippy` is `cargo clippy --all-targets`, and
  this crate is outside `default-members` — which is what keeps `make test` free of setup, and
  also what has kept every lint in the FFI crate unreported since it was written. Running it by
  hand found one waiting (`chunks_exact` with a constant size). Fixed, and `make test-occt` now
  ends with `cargo clippy -p w3d-kernel-occt --all-targets -- -D warnings`: the command that
  already requires OCCT is the one place that can lint the crate that requires OCCT.
- **`STEPControl_Writer` in OCCT 7.6 cannot write to a stream.** It takes a filename and nothing
  else; `WriteStream` arrives in a later version. A temporary file would have put a filesystem
  dependency inside the kernel, which the browser does not have and which the trait's `Vec<u8>`
  exists to avoid. The route round it is one level down — `StepData_StepWriter` over the model the
  writer built, `SendModel(StepAP214::Protocol())`, `Print(ostream)` — and it was found by
  compiling a forty-line probe against the installed headers rather than by reading them.
- **The reader, by contrast, has `ReadStream`.** The asymmetry is the sort of thing only building
  reveals, and it is why the import side is straightforward and the export side is not.
- **`StepAP214::Protocol()` does not compile without `StepAP214_Protocol.hxx`.** The declaring
  header forward-declares the class, so the handle conversion fails on an incomplete type and the
  error is about `std::is_base_of`, which names nothing a reader can act on.
- **The container's Rust was 1.94.1 and this workspace needs 1.95** for egui 0.36 — `cargo test`
  refused before compiling anything. `rustup toolchain install stable` (1.98) fixed it. Not a
  repository bug; recorded because "clean on Rust 1.98" in the register is a claim about a
  toolchain nobody pins, and this is the second environment where the toolchain was the first
  thing to go wrong.

## Verified, and not

**Verified.**

| | |
| --- | --- |
| `make test` | 65 native tests, no setup — 62 before, plus three in the editor that assert the *refusal*: a build whose kernel does not do STEP says so in the status line, writes no file, and leaves the document alone when an import fails. |
| `make test-occt` | 17 against real OpenCASCADE — 11 before, plus six in `kernel-occt/tests/step.rs`. Now also lints the crate. |
| conformance | Four new checks, run against **both** backends: the fake refusing consistently, OCCT round-tripping a drilled plate. |
| `make app-test-step` | The two-process round trip above: 19 146 bytes of STEP out of one, a drawn scene out of the other. |
| `make app-test`, `make wasm`, `make licences` | Unchanged and green. 177 third-party crates across both targets, all compatible with GPL-3.0-or-later. |
| clippy, fmt | `-D warnings`, no allow-list, now including `w3d-kernel-occt`. |

The six tests in `step.rs` are worth naming, because they are the ones that assert something a
round-trip cannot:

- **the bytes are a STEP file by inspection**: begins `ISO-10303-21;`, ends `END-ISO-10303-21;`,
  `HEADER;` before `DATA;`, `AUTOMOTIVE_DESIGN` as the schema, `SI_UNIT(.MILLI.,.METRE.)`,
  `ADVANCED_BREP_SHAPE_REPRESENTATION` and `MANIFOLD_SOLID_BREP` — the last two being the
  difference between a file another program can model with and a bag of surfaces it can only look
  at;
- **a kernel that never saw the geometry reads what another wrote** — two `OcctKernel` instances,
  the writer dropped before the reader is built;
- **every solid in a file becomes a body** — three in, three out, and the reading kernel holds
  exactly three;
- **each format refuses the other's bytes by the right name** — BREP into `import_step` is
  `Failed`, STEP into `load_body` is `Unsupported`;
- **a file with no solids is refused with a reason** — a hand-written, valid, empty part-21 file;
- **an import is one undo step and names what it added**.

**Not verified, and the risk taken with each.**

- **No other program has ever opened a file this writes.** This is the caveat, and it is bigger
  than everything else here put together. Every assertion above is a string this repository looks
  for in a file this repository also parses. Fusion, FreeCAD, SolidWorks and Onshape are the
  entire reason STEP was chosen, and not one of them has seen one of these files. The structural
  assertions were written to be the ones a receiving program actually keys on, which reduces the
  odds of a silent nonsense file; it does not make this verified.
- **No STEP file written by anything else has ever been imported.** Every file read back here was
  written minutes earlier by this program's own OCCT. The wild is where STEP files are strange:
  AP203 and AP242, inches, assemblies with transforms, nested compounds, files from CATIA that
  every other reader special-cases. The reader is untested against all of it.
- **The unit conversion is asserted as a string, not exercised.** `SI_UNIT(.MILLI.,.METRE.)` is
  checked to be in the file. No file in inches has ever been imported, so the path that scales one
  has never run.
- **The lock is exercised, not proven.** Six tests call STEP from parallel threads and three runs
  in a row were clean. That is exercise. `Interface_Static` is a global table and nothing here
  proves the absence of a race in it.
- **The export is synchronous and on the frame**, like saving — and a STEP export is far slower
  than a `.w3d` save, because it rebuilds the model into another representation. A large document
  will stall the window for longer, and nothing has measured how long.
- **Nothing is measured at all.** No import time, no export time, no file size against body count.
  Nineteen kilobytes for one drilled plate is the only number in this file, and it is one plate.
- **The exported bytes are not deterministic.** `FILE_NAME` carries a timestamp, so two exports of
  the same body differ. No test asserts byte equality, deliberately; it is worth knowing before
  somebody writes a golden-file test and cannot understand why it fails.
- **Face identity does not survive.** Faces come back renumbered, so a document that exports and
  re-imports loses every per-face selection. That is STEP, not a defect here, but it is the second
  time face ids have come up as a gap — the first is the register's item about edges.
- **AP214 over AP242 was decided on reach, not measured.** Nobody counted which programs read
  which; the claim rests on twenty years of AP214 being the safe answer.
- **Five more OCCT toolkits are now in the link**: `TKXSBase`, `TKSTEPBase`, `TKSTEPAttr`,
  `TKSTEP209`, `TKSTEP`. `TKSTEP209` is wanted by nothing here and refuses to link without. Every
  one of them is a thing an Emscripten build has to compile, and the payload cost of that is
  unknown and unestimated.

## Loose ends, deliberately left

- **Assembly structure is flattened.** A STEP file carries product names and a hierarchy;
  `import_step` produces one flat body per solid, named after the file. Reading the structure means
  `STEPCAFControl_Reader` and XDE — another set of toolkits, a document model that is not ours,
  and a mapping onto a node graph that has no hierarchy to map onto. It would be the natural time
  to give the document one.
- **Colours and materials are ignored**, for the same reason and at the same cost.
- **No file dialogue**, so import is a command-line option and export invents a name beside the
  document. Everything about files in this program is waiting on this one dependency.
- **No progress, no cancel.** A large import blocks the frame with no way to stop it.
- **The camera only reframes when the document was empty.** Importing into a populated document
  can put the new bodies off screen, which looks exactly like an import that did nothing.
- **No IGES, no STL.** IGES is one more OCCT toolkit and reaches nowhere STEP does not; STL is a
  different question — it is what a printer wants, and it is a mesh, so it is `tessellate` with a
  file around it rather than an interchange format.

## Walkthrough · as completed

STEP goes in and out of the modeller, on real OpenCASCADE geometry, through two methods declared
on the seam first and implemented behind it. The conformance suite holds every backend to both
directions or neither, without skipping a check on the backend that refuses. The C ABI grew three
entry points, one lock, and a printer that turns OCCT's stdout into an error message. The document
imports as one undo step and appends rather than replaces; the modeller exports with ctrl-E and
imports from the command line; and `make app-test-step` proves a file leaves one process and is
drawn by another.

What this file leaves owed has moved to
[the register](./2026-08-25_21h59.what-is-not-built-yet.md), which took: STEP against files this
program did not write and programs that did not write ours — the one that decides whether any of
this works; assembly structure and product names; the flattening, the colours, the missing file
dialogue, the reframing, the synchronous export, and the five toolkits the Emscripten build now
owes. The register's item 1 is closed there with a pointer here.
