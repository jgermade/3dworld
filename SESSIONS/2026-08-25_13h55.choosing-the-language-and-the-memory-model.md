# 2026-08-25 13h55 · Choosing the language, and the memory model

The first file. Nothing was built; what was decided is the architecture, and this records it
along with the two reversals it took to get there.

## Where this repo actually was

Empty. `git log` on `claude/plasticity-mydeje` reported no commits at all. There was a
directory name, `3dworld`, and an intent: an alternative to Plasticity, in WebAssembly.

The name is not settled either. `3dworld` is the repository, not a decision.

## What was asked

Four questions in sequence, each of which turned out to constrain the next:

1. Rust or Go?
2. Is wasm64 not mature yet?
3. Could one thread run in wasm32 and another in wasm64?
4. Can hardware acceleration be used where it exists?

The order matters. The language question looks like the big one and is the easy one; the memory
model is where the architecture actually got decided.

## Walkthrough · as built

Nothing was built. What follows is what was settled, and it is written down here because the
reasoning is worth more than the conclusion — a later reader who disagrees needs to be able to
disagree with the argument, not just overturn a verdict.

### 1 — Rust, and the reason is not the one usually given

The reasons that get cited (speed, safety) are not the deciding ones. The deciding ones are:

- **No GC.** Go's pauses land in the interaction loop of a real-time modeller.
- **Threads exist.** `GOOS=js/GOARCH=wasm` is single-threaded. There is no rayon equivalent, and
  a kernel that cannot use cores is not competitive.
- **C++ interop.** Any path that wraps OpenCASCADE needs it, and from Go under wasm it is
  impractical.
- **One source, two columns.** Rust compiles the same core to `wasm32-unknown-unknown` and to a
  native desktop binary. Plasticity is a desktop application; a web-only answer is a different,
  smaller product. Go would have meant Wails or Electron over the top.

Binary size and SIMD also favour Rust but were not needed to decide it.

### 2 — the kernel is the project, and it is not the language

Recorded because it is the thing most likely to be forgotten under enthusiasm: Plasticity is good
because it sits on **Parasolid**. Robust booleans, and fillets that do not fall over on
degenerate input, are decades of work. Parasolid is a commercial Siemens licence with no
WebAssembly distribution, so it is not available at any price that matters here.

That leaves OpenCASCADE (mature, LGPL-with-exception, 5–40 MB of wasm, unpleasant API, fillets
short of Parasolid), `truck` (Rust, permissive, booleans not production-ready), or writing one.

**The decision was to not decide**, and to make not-deciding structural: `kernel::GeometryKernel`
exists from the first commit, OCCT goes behind it to get something usable quickly, and a kernel
of our own replaces it from underneath without the modeller noticing. This is the single most
load-bearing decision in the file, and the rule that protects it — nothing below the seam leaks
above it — is in AGENTS.md as a rule rather than a preference for that reason.

### 3 — wasm32, and the sharding that makes it enough

wasm64 was rejected. Not for availability — see the correction below — but because 64-bit memory
gives up the 4 GB guard-page trick, so every access is bounds-checked, at a cost SpiderMonkey
measured between 10% and over 100%. A B-rep kernel is memory-bound and pointer-chasing, which is
the wrong end of that range. Rust's `wasm64-unknown-unknown` is Tier 3 besides, and the JS API
caps a memory at 16 GB anyway.

The question that followed — one thread in wasm32, another in wasm64 — does not typecheck, and
the reason is worth keeping: **the address width belongs to the memory, not to the thread.**
Threads are N workers instantiating the same module against the same shared `WebAssembly.Memory`,
whose index type is fixed in the module type. Two separate modules can of course differ, but they
cannot share linear memory at all — a wasm32 module importing an `i64` memory is a `LinkError`.
And in Rust, one binary is one target is one `usize`.

There is a real loophole: multi-memory (also Wasm 3.0) makes index types per-memory, so a wasm64
module could declare an `i32` shared memory alongside its 64-bit one and exchange with a wasm32
module without copying. LLVM and Rust cannot emit usable multi-memory modules, so it stays
theoretical. **Recorded so nobody re-derives it and thinks they have found something.**

What survived from that question is the good half of the instinct, and it became the memory
model: **shard across wasm32 heaps.** One shared memory for the interactive document with a rayon
pool over it; separate workers with their own memory for bulk work, each with its own 4 GB;
transferable `ArrayBuffer` between them, which is a move rather than a copy. Total addressable
exceeds the ceiling and nothing pays for 64-bit pointers.

This is what forces arenas and `u32` indices. A pointer is meaningless in another worker's heap;
an index is valid in any of them.

### 4 — acceleration, and the two traps specific to this domain

The general answer is that wasm exposes acceleration in three layers — WebGPU, SIMD128, threads —
and that **there is no CPUID**: a module cannot ask what the machine can do, so detection happens
in JS before instantiation via `WebAssembly.validate()` on probe modules. That means a build
matrix. It was kept to two entries: SIMD128 is universal enough since Safari 16.4 to be the
baseline, and threads are the axis actually worth branching on — they depend on the *host's*
COOP/COEP headers, not on the user's hardware.

The two traps are CAD-specific and both became rules:

- **WGSL has no `f64`.** So the kernel never moves to the GPU, whatever a benchmark says. The GPU
  gets display tessellation, BVH, culling, ID-buffer picking, silhouettes, instance transforms.
- **Relaxed SIMD is non-deterministic across platforms.** Fine for rendering, poison in a
  predicate: the same document would produce different topology on different machines and the
  fixture suite would stop meaning anything. The rule is per-crate — `kernel/` builds without it.

Also noted, and easy to miss: the WebGL2 fallback has **no compute shaders**. Anything built on
compute degrades to the CPU, not to a slower GPU.

### Correction · 2026-08-25 · wasm64 is mature, and the conclusion is unchanged

The first answer given was that wasm64 "is not viable yet". That was wrong on the facts. Memory64
was standardised in **Wasm 3.0** (September 2025) and ships in **Chrome 133+** and **Firefox
143+**; `wasm-bindgen` has since added `wasm64-unknown-unknown` support, lowering `usize` and raw
pointers through an `f64` JS number ABI and inspecting the module's memory type to pick codegen.

The original text is left standing above because the correction is the interesting part: the
maturity objection had *moved*, and the reasons to still say no are entirely different from the
reasons first given. It is now bounds-check cost, Rust Tier 3, and Safari — not absence.

Kept as the worked example for AGENTS.md § Always append, never rewrite.

- **The 4 GB ceiling has not been tested against a real document.** The claim that sharding is

- **OCCT's wasm size, licence exception and fillet quality are all reported, not confirmed.** The

- **`wgpu`'s WebGL2 fallback has not been exercised.** "No compute" is from its documentation.

## Loose ends, deliberately left

- **The name.** `3dworld` is a directory. Costs nothing now, costs a rename later.
- **The licence**, which is the kernel decision wearing a different hat. Left open on purpose —
  deciding it early would have meant deciding the kernel early. It is in AGENTS.md as blocking any
  dependency.
- **The UI layer**: `egui` (one canvas, both targets, unfamiliar idiom) versus a TypeScript shell
  over the wasm boundary (idiomatic web, two UIs to maintain). Not decided because nothing yet

- **The tessellation format across the worker boundary** was hand-waved as "transferable

## Walkthrough · as built

Three crates, 2,188 lines, **no dependencies at all** — not even `glam`. The linear algebra the
contract needs is about 200 lines and writing it avoided having any dependency-licence
conversation before the kernel licence is settled.

### `w3d-kernel` — the seam

The trait is thirteen methods and that is on purpose: every one is something a backend has to
implement *well*, so a short list is a short list of things that can be wrong. Two properties of
it turned out to be load-bearing enough to be written into the crate docs rather than assumed:

- **Bodies are immutable.** Every operation returns a new `Body` and leaves its operands intact.
  This is not a stylistic preference about value semantics — it is what makes undo implementable.
  Nothing can invert a boolean, so state-based undo is the only honest kind, and state-based undo
  needs the previous state to still be addressable.
- **Tolerance is an argument.** `Tolerance` is passed into every operation that compares. There
  is one constant, `Tolerance::document_default()`, and it is described in its own doc comment as
  what a *document* starts with rather than something a predicate may reach for.

`Body` is an opaque `u32` newtype with `from_raw` documented as backends-only. That is what makes
"nothing below the seam leaks above it" mechanical instead of aspirational: there is no OCCT type
a caller *could* name, so the rule cannot be broken by accident, only by editing this crate.

### The conformance suite is the interesting part

`w3d_kernel::conformance` is a non-dev feature on purpose, so a backend crate can run it from its
own tests without depending on this crate's dev-dependencies. Thirteen checks, and the discipline
that shaped them is that **every assertion has to be true of any correct kernel** — which throws
out most of the interesting ones. Nothing checks that a boolean is geometrically right; that
needs golden fixtures and a real kernel.

What survived is the contract itself: bounds relate to their operands the way set operations
require (a union contains both, a difference stays inside the minuend, an intersection inside
both); a boolean leaves its operands valid; a copy outlives its original's deletion; a deleted
handle is an error at every entry point and deleting twice fails; tessellation is well-formed,
lies inside its body's bounds, is deterministic, and finer quality never yields fewer triangles.

Two of those are there because of decisions in the first half of this file. **"A boolean leaves
its operands valid"** is history's foundation, and a backend that failed it would break undo in a
way that looks like a document bug for weeks. **"Tessellation is deterministic"** is the property
relaxed SIMD below the seam would quietly destroy, so the rule now has a test that fails when
somebody adds `+relaxed-simd` to the wrong crate.

`Report::assert_passed` prints every failure rather than the first. A backend under development
fails five checks for one reason, and seeing them together is what tells you it is one reason.

### `w3d-kernel-fake` — honest about shape, silent about geometry

A CSG tree that is never evaluated. Bounds are exact for primitives and combined by the rules set
operations obey; tessellation returns the bounding box, subdivided by quality. So its answers are
true statements about the real answer, just weak ones — which is exactly the split the conformance
suite tests, and the reason the fake can pass a suite a real kernel must also pass.

Its subdivision count is clamped to 16 and monotone in `sag`, which is the whole of what
"finer quality never yields fewer triangles" needs from it.

### `w3d-core` — the document

`Document<K: GeometryKernel>` and nothing in the file names a backend. History is a stack of
transactions of `Insert` / `Remove` / `Replace` edits over a generational arena, and a boolean is
one transaction of three edits: remove both operand nodes, insert the result.

Two things fell out of building it that were not obvious from the design:

- **There is no `History::abort`.** It was written, and then it was never called, because the
  document does every kernel call — everything that can fail — *before* opening a transaction. A
  transaction that has begun cannot fail partway. Deleting the method was better than keeping a
  path for a state that cannot occur; the invariant is now a doc comment on `begin`.
- **The mesh cache is keyed by body, not by node**, which makes it permanently valid: bodies are
  immutable, so a body's mesh at a given quality never changes. Only a quality change or garbage
  collection evicts. A node-keyed cache would have needed invalidation on every edit.

### The cost of state-based undo, made visible

Because history holds previous states, the kernel holds every intermediate body for as long as
something can undo back to it. `Document::collect_garbage` walks live nodes plus every retained
edit and deletes the rest, and `clear_history` is the other half. Nothing calls either
automatically — when to pay is a policy the application owns.

The trait deliberately cannot enumerate its own bodies, so the document remembers what it asked
for in a `created: Vec<Body>`. That is the price of a narrow trait, and it is the right price.
`history_holds_bodies_alive_and_clearing_it_lets_them_go` asserts the whole cycle: three bodies
after a union, nothing collectable while undo or redo can reach them, two collectable once history
is cleared.

## Bugs found by building, not by reading

**The free list ate undo.** The arena was written with a free list, because that is what a
generational arena is for. `a_boolean_consumes_its_nodes_and_undo_puts_them_back` failed:
`d.len()` was 1 after the undo, not 2.

The mechanism: `A` is slot 0, `B` is slot 1. The union removes both — freeing slots 0 and 1 — and
inserts the result, which pops slot 1 off the free list. Undo removes the result and then tries to
restore `B` into slot 1, whose generation has now moved twice. `restore` refuses, and refuses
*silently*, so one node simply never came back.

**The fix is that slots are never reused.** Undo restores a node into the slot it came from, so
any free list means a later insert can take a slot an undo still needs. The price is an arena that
grows with the nodes a session ever created rather than the number alive, and `Arena::slot_count`
exists so that cost is observable rather than theoretical.

This is recorded at this length because it is the kind of bug someone reintroduces in good faith
while optimising memory. Compaction — renumbering with history cleared — is the honest fix and is
not written. The rule is now in AGENTS.md, and the test that caught it asserts the *opposite* of
what it originally asserted.

**Verified.** `cargo test --workspace` is 19 tests, all passing: 4 on the arena's identity rules,
14 on the document, 1 running the conformance suite against `FakeKernel`. `cargo clippy --workspace
--all-targets -- -D warnings` is clean with no allow-list. `cargo fmt --check` is clean. The
workspace compiles for `wasm32-unknown-unknown`, and again with `-C target-feature=+simd128`.

**Not verified, and the risk taken with each.**

- **No geometry has been tested, because none has been written.** Every "correct" in this
  extension means "satisfies the contract". The fake's bounds for a difference are its minuend's,
  which is true and nearly useless. A real backend passing this suite is a backend that is
  *wired up* correctly, not one that is right.
- **`make wasm` type-checks; it has never been run.** `cargo check --target wasm32-unknown-unknown`
  passes, which proves no host assumption has crept in. It does not prove anything instantiates,
  because there is nothing to instantiate yet and no `web/`.
- **Threads, COOP/COEP, `wgpu` and the two-variant loader are all still unwritten**, so every
  claim in STACK.md about them remains an argument rather than a result.
- **The conformance suite has never been run against a second backend**, which is the only way to
  find out whether it encodes the contract or encodes the fake. That is the single most valuable
  thing the next backend will tell us, and it should be read that way when it fails.
- **`collect_garbage` is O(created × 1) per call with a `HashSet` rebuild each time.** Fine at
  this size, unmeasured at any other.

## Loose ends, deliberately left

- **Arena compaction.** Named above. Safe only with history cleared, renumbers every id.
- **Transactions are not user-grouped.** One edit is one undo step, so a drag that transforms
  twenty nodes would be twenty steps. `History::begin`/`commit` already take a label and would
  support grouping; nothing exposes it.
- **`set_tolerance` does not re-evaluate existing geometry**, and says so in its doc comment.
  Retrofitting a tolerance is a rebuild, and a rebuild is a feature that does not exist.
- **No serialisation.** The arena's ids are stable and `u32`, which is most of what a format needs,
  but there is no format.
- **`Topology` is counts only.** Anything richer — face ids, edge loops, the things selection and
  filleting will want — is a widening of the trait, and it should happen when there is a caller,
  not before.
