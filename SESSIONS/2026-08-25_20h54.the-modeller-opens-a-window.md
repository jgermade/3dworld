# 2026-08-25 20h54 · The modeller opens a window

Took **item 1** from `2026-08-25_19h22.what-is-not-built-yet.md`: `app/` — a winit window, a
swapchain, egui in the same pass as the scene, and the event loop that turns a drag into an orbit
and a click into a selection.

It works, on a real window under a virtual framebuffer, with OpenCASCADE behind it: a box, a
cylinder, a difference, and a drilled solid you can rotate. **Something you can model with**,
which is what every session before this one was building toward.

## Where this repo actually was

Six crates. A viewport that drew into textures and answered clicks, and two shells that were not
one: `w3d-web` in a browser, and nothing at all on the desktop. Rust 1.94.1. The register's first
item had been `app/` since the register existed.

## Walkthrough · as built

### The toolchain moved, and that was decided rather than discovered

`egui-wgpu` pins a wgpu version, so the first question was whether egui could join a tree already
on wgpu 30. It can — **egui 0.36 is built on wgpu 30** — but 0.36's MSRV is Rust 1.95 and this
project was on 1.94.1. egui **0.35** would have worked on 1.94 and dragged in **wgpu 29**, which
is worse than it sounds: two incompatible `wgpu::Device` types in one tree, and egui unable to
take ours.

So the toolchain moved. `rustup update stable` went to **1.98**, which is a bigger jump than the
1.95 the constraint asked for, so it was verified on its own **before** egui was added — a
toolchain bump and a new crate failing together is two problems wearing one hat. One new clippy
lint fired (`chunks_exact_to_as_chunks`), and was fixed rather than allowed, because there is no
allow-list.

### `w3d-app`, split where a test can reach

The whole design decision is one line: **the editor has no window in it.**

- **`editor.rs`** — commands, selection, camera manipulation, and the rules that are easy to get
  wrong. No `wgpu`, no `winit`. Twelve tests drive it directly.
- **`scene.rs`** — the map from the document to the GPU, which is the thing the register said
  nothing owned. Keyed **by body, not by node**, for the same reason the document's own mesh cache
  is: bodies are immutable, so their buffers are permanently valid and a transform produces a new
  entry rather than a stale one. A body that fails to tessellate is remembered as refused, so it
  is not retried sixty times a second.
- **`shell.rs`** — winit, egui, the surface. Thin by construction: everything that could be wrong
  and could be caught has been moved out of it.

`Reaction` is what makes the split hold. The editor cannot pick — that needs a GPU — so
`Input::Up` on an unmoved left button returns `Reaction::Pick { x, y, additive }`, the shell does
the readback, and `Editor::picked` takes the answer. The rule *"a drag is not a click"* is
therefore a unit test rather than something you notice when every rotation selects whatever the
cursor stopped over.

Three rules that are asserted rather than hoped for:

- **A press that barely moves is still a click**, and the pick is at the *press*, not the release.
- **A plain click replaces the selection; only shift toggles.** Written the other way round first
  — see below.
- **The first body added is framed**, and the second is not. "I added a box and nothing happened"
  is not a bug report anyone should have to file, and reframing under someone mid-edit is worse
  than leaving them where they are.

### egui draws in the scene's pass

`STACK.md` has claimed since the licence session that this is why egui was chosen over a DOM
framework: one surface, one loop, nothing composited. It had never been run.

Making it true needed one change in `w3d-render`: `draw` was split into **`prepare`** (writes the
uniforms) and **`draw_into`** (records into a pass the caller opened). The order matters and is in
the doc comment — a render pass borrows the encoder, so nothing may touch the queue while it is
open.

`Camera::pan` was added at the same time, because a modeller without pan is not one. It is scaled
by distance and field of view, so a drag moves what is under the cursor by roughly that many
pixels at any zoom, and there is a test asserting the ten-times-distance-ten-times-movement
property.

### It runs, and the run is a check

`make app-test` drives the binary under `xvfb-run` with a software rasteriser, for thirty frames,
and reads back the frame that was **presented**. Two assertions rather than one, and the second is
the one worth having: the chrome and the viewport are measured **separately**, because a run where
egui drew and the scene did not looks identical in a whole-frame colour count.

It carries negative controls — a synthetic flat frame must be rejected and a synthetic gradient
accepted — and they were verified by sabotage, the same discipline as `tools/licences.py`.

## Bugs found by building, not by reading

### The licence check fired on the very first dependency added after it

`epaint_default_fonts` — `(MIT OR Apache-2.0) AND OFL-1.1 AND Ubuntu-font-1.0` — failed
`make licences` the moment egui entered the tree. That is the entire argument for having done the
audit *before* `app/` rather than after, arriving one session later than the argument.

The decision, since `AGENTS.md` requires widening the allowlist to come with an argument:

- **The font licences are allowed only for crates that are font data**, in a separate
  `ALLOWED_FONT_DATA` set gated by a named `FONT_DATA` list. Scoped rather than merged into the
  main allowlist because the argument is about fonts and would not survive being applied to code.
- **OFL-1.1** is a copyleft licence written so fonts can be bundled with software under any
  licence; its conditions are all satisfiable by a GPL-3 work.
- **Ubuntu-font-1.0** is DFSG-free and in Debian main, and the FSF has never ruled on it — which
  is why it is *not* in the general allowlist. The reason it is acceptable here is narrower than
  "compatible": a font is data this program displays, not code linked into it, so the font keeps
  its licence and the program keeps GPL-3.
- **Both require their notices to be preserved in a distribution.** The register's NOTICE item was
  "owed"; it is now a requirement, and that is recorded there.

The self-test gained two cases: the same expression must **fail** for code and **pass** for font
data.

### `app/` broke `make wasm`, which is correct

winit is a native window and does not build for `wasm32`; the browser's shell is `w3d-web`. The
fix is an explicit `--exclude w3d-app` with a comment saying why, rather than dropping the crate
from `default-members` — which would also have stopped `make test` running the editor's tests.

### A test that asserted the wrong interaction

`a_click_selects_and_a_second_click_deselects` failed, and the code was right: a plain click
*replaces* the selection and only shift toggles, which is what every modeller does. The test
asserted that clicking the thing you just selected throws it away. Rewritten to assert the real
rule, both halves of it.

Second time in three sessions that a test encoded a wrong belief about the domain rather than a
defect in the code — the first was the through-hole that is background when viewed down its axis.

### An edit that silently did nothing

The `--demo` startup was supposed to run a boolean. It did not, and the screenshot showed two
bodies sitting on each other rather than one drilled solid. The cause was not in Rust: a
string-replacement edit had been written against text that `cargo fmt` had already reformatted, so
it matched nothing and changed nothing, quietly.

Recorded because the failure mode is invisible: the code compiled, the tests passed, and only
*looking at the picture* showed that the operation everything was arranged around had never run.

### Two things only a screenshot could show

- **`∪ − ∩` are not in egui's default font** and rendered as three identical empty boxes. Replaced
  with `Unite` / `Subtract` / `Intersect`.
- **"1 bodies"**, in the status line.

Neither is a crash, neither would ever fail a test, and both are the first thing a person sees.

### Two missing runtime libraries, and a texture that was already destroyed

`libxkbcommon-x11-0` is a runtime dependency of winit on X11 and is not pulled in by anything;
without it the process panics inside `xkbcommon-dl` before a window exists. Documented in the
README as a desktop prerequisite.

And the first `--screenshot` read back the *presented* surface texture, which wgpu rejects with
`Texture with '<Surface Texture>' label has been destroyed` — presenting destroys it. The copy has
to happen in the same encoder that drew the frame, which is also what makes the capture exactly
what was shown rather than something rendered a second time.

## Verified, and not

**Verified.** `make test` is 47 tests (32 before) plus the licence check — thirteen for the editor, two for `Camera::pan`. `make test-occt` is 8.
`make wasm` type-checks the crates that are meant to reach wasm and asserts the WebGL2 backend is
in the tree. `make web-test` is 17 checks in Chromium. `make app-test` opens a real X11 window
under Xvfb, runs thirty frames and asserts the chrome and the scene both drew. clippy `-D
warnings` and fmt are clean on Rust 1.98.

The screenshots in this session are a real window: the fake kernel's bounding boxes at 6,144
triangles, and OpenCASCADE's drilled solid at 372 — the same binary, one `--features occt` apart.

**Not verified, and the risk taken with each.**

- **Nothing about how it *feels*.** Thirty frames under a software rasteriser says the pipeline
  runs. It says nothing about latency while dragging, which is the only thing that matters in a
  modeller and the thing this environment cannot measure.
- **One windowing system, one compositor.** X11 under Xvfb. No Wayland, no macOS, no Windows, and
  no HiDPI — `scale_factor` is read and has only ever been 1.
- **Resize is wired and untested.** `Live::resize` reconfigures the surface, the depth texture and
  the capture target; nothing exercises it. It is the most likely thing here to be wrong.
- **The pick path in the shell has no test.** `Reaction::Pick` → `pick_begin` → `collect` →
  `Editor::picked` is asserted at both ends and not in the middle, where the shell holds a
  `PickPending` across frames.
- **WebGPU still has never rendered a pixel** anywhere in this project. The desktop run is Vulkan
  through lavapipe.
- **No document survives the process.** Closing the window loses everything; there is no format.
- **The editor's tests all run against the fake kernel**, so they prove the machinery and say
  nothing about geometry. The OCCT screenshot is a demonstration, not an assertion.
- **`Scene::sync` walks every node every frame** to find what is missing. Fine at three bodies,
  unmeasured at three thousand.

## Loose ends, deliberately left

- **No pan with the right button, no orbit-about-cursor, no view cube, no grid, no axes.** The
  viewport is a lit solid in space with nothing to orient against.
- **Selection is still a tint**, and there are still no edges — which is the loudest thing missing
  from the screenshots and is register item 11.
- **The chrome is one file and one function.** It is a list, six buttons and a status line, and it
  will not survive becoming a real UI in that shape.
- **Keyboard shortcuts are hard-coded** in `map_key`, with no way to see or change them beyond
  `--help`.
- **`--demo` is a fixed sequence of commands**, which is a poor substitute for opening a file.
